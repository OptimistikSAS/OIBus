# Export / Import Configuration

OIBus can export its entire configuration as a single, portable JSON file, and later import that
file — on the same instance or a different one — to recreate the configuration from scratch. This
is useful for backups, disaster recovery, or cloning a configuration onto a new instance.

Both actions are available from **Engine > Settings**, via the **Export configuration** and
**Import configuration** buttons.

## What gets exported {#what-gets-exported}

The export file (`oibus-config-export.json`) has three top-level fields:

- `oibusVersion`: the version of the OIBus the configuration comes from.
- `exportedAt`: when the file was produced, for information only.
- `config`: the configuration itself, made of the same sections OIBus sends to OIAnalytics:
  - Scan modes
  - IP filters
  - Certificates
  - Transformers
  - South connectors (including items, groups and configuration workflows)
  - North connectors
  - History queries
  - Users
  - The engine settings and the OIAnalytics registration settings, for information only: they are
    never imported (see [Registration](#registration-is-not-imported) below)

Because `config` uses the same format as the configuration OIBus sends to OIAnalytics, a file
produced by OIAnalytics from the configuration it holds for an OIBus can be imported the same way
as a file exported by OIBus. Its `oibusVersion` is then the version of that OIBus, not of
OIAnalytics.

### Secrets are always stripped {#secrets-are-always-stripped}

No secret is ever written to the export file — not in plaintext, not encrypted. This applies to
every secret-shaped field across the configuration: connector credentials (passwords, API keys,
tokens), proxy passwords, the Loki logging password, certificate private keys, and user passwords.
An exported file can therefore be shared or stored without exposing any credential, but it also
means those fields must be re-entered manually after an import — see
[Manual steps after import](#manual-steps-after-import).

## Import is a full replace, not a merge {#import-is-a-full-replace-not-a-merge}

Importing a configuration file **wipes every in-scope section of the target instance's local
configuration and recreates it from the file**, preserving each entity's original internal ID.
This is destructive and cannot be undone: every south connector, north connector, history query,
configuration workflow, scan mode, IP filter, transformer, certificate and user currently on the
instance is deleted before the imported ones are created. The UI requires an explicit confirmation, restating this, before an
import is submitted.

The engine's own settings and the OIAnalytics registration are never wiped or overwritten by an
import — see [Registration](#registration-is-not-imported).

If the uploaded file is malformed, or is rejected for any of the reasons below, **nothing is
written**: the import is all-or-nothing.

## Supported versions {#supported-versions}

Configuration export is available from OIBus 3.10.0 onwards, but a file can hold the configuration
of an OIBus as old as 3.9.0 (for example a file produced by OIAnalytics). A file can be imported into
any OIBus at least as recent as the one its `oibusVersion` names:

- **Newer files are rejected**: an import is rejected outright if the file's `oibusVersion` is
  newer than the importing OIBus instance, since it may contain settings this version does not know.
  A pre-release counts as older than its release (`3.10.0-beta-2` is older than `3.10.0`).
- **Files older than 3.9.0 are rejected**, including files from 3.9.0 pre-releases.
- **Older files are upgraded**: before validating the file, OIBus brings its configuration from its
  `oibusVersion` to the shape the importing version expects, applying in order every configuration
  upgrade step of the versions in between. These steps do to the configuration what the database
  migrations of those versions do to an existing installation. The import result lists every upgrade
  that was applied.

After the upgrades, the whole configuration is validated: its structure (every section, entity and
field), then every connector and item settings against the current connector manifests. If
anything fails validation, the whole import is rejected with a per-entity list of errors and, again,
nothing is written.

## Manual steps after import {#manual-steps-after-import}

Because secrets are never exported, an imported configuration is not immediately usable as-is:

- **South and north connectors are imported with `enabled: false`**, regardless of their exported
  value. Their settings otherwise import as exported, but with every secret-shaped field empty, so
  leaving them enabled would either fail to connect with empty credentials or — for a write-capable
  protocol — connect with no meaningful settings. Credentials must be re-entered and each connector
  re-enabled manually before it will run again.
- **Certificates are imported without their private key.** The certificate entry itself (name,
  public key, certificate, certificate chain, expiry) is recreated under its original ID so anything
  referencing it keeps resolving, but the private key must be re-imported manually before the
  certificate can be used for TLS.
- **Users are recreated with a random password**, since passwords are never exported. Every
  imported user must have their password reset before they can sign in again.
- **Configuration workflows are imported disabled**, with the items they created still attached to
  them. Their run history is not exported. Re-enable each one once its south connector is configured.
- **Standard transformers are matched by function name**, not recreated — they are seeded once when
  OIBus starts and matched to the imported configuration by their `functionName`. If the target
  instance doesn't have a standard transformer with a matching function name (for example, an older
  or newer OIBus build), links to it are skipped and reported as a warning. Custom transformers are
  always recreated under their original ID.

The import response (and the corresponding UI panel) lists every upgrade that was applied and every
warning raised during the import — including the ones above — so this stays visible after the
import completes rather than in a toast that disappears.

### Registration is not imported {#registration-is-not-imported}

The OIAnalytics registration settings are included in the export for informational/reference
purposes only. Importing a file never writes registration state — registering the target instance
with OIAnalytics (or re-registering it) must be done manually, the same way as on a fresh instance.
