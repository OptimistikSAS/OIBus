# Transformers

A **Transformer** sits between a data source and a North connector. It converts incoming data into the format the
North connector expects before it is placed in the connector's cache. Beyond format conversion, transformers are
also the mechanism for **filtering** which data a North connector receives — see
[Data Filtering](../north-connectors/common-settings.md#data-filtering) for details.

Transformers are configured **on the North connector**, in the **Transformers** section of its settings page.

## The sources of a North connector {#the-sources-of-a-north-connector}

The Transformers section lists every source of data — each South connector, the OIBus API and the OIAnalytics
setpoints — with the transformer its data goes through, in a green tag when all its data is sent; in a green outlined
tag (**Partly sent**) when only some of its items, or some OIBus API data sources, are; in a grey tag (**Dropped**) when
none is. A South connector whose items all have a transformer, through their group or their own one, is **Sent**. A source no standard
transformer can send to this North connector is dropped too: a custom transformer can still send it. Filter the list by what
reaches the North connector, by the status or the type of the South connectors, or search a source by name.

- **Add a transformer to a source** from its line: the button named after a transformer adds it in one click (the
  obvious transformer for its data, when its default options are valid), and **Other…** opens the configuration modal
  for that source.
- **Expand a South connector** to see its groups, then their items, each with the transformer its data goes through:
  its own one, the one of its group (**from its group**), the one of all the items (**from all items**), or
  **Dropped**. From there:
  - **Add** a transformer to a group, or to an item without one;
  - **Override** the transformer an item inherits: when the transformer and options chosen are those of another item,
    the item is added to that transformer rather than getting its own copy;
  - **Exclude** an item from the transformer it inherits (see **Except some items** below);
  - remove an item from its own transformer (deleting the transformer when it was its last item).

A transformer that is never used, another one before it in the list applying to the same data, is struck through.

---

## Configuring a Transformer {#configuring-a-transformer}

Click **Add a transformer** in the Transformers section (or a button of a source) to open the configuration modal.
The modal has three steps, as the item modals: **Source & transformer** (where the data comes from, the items of a South
connector it applies to, and the transformer, new or copied), **Options** (those of the chosen transformer), then
**Test**. A new transformer can be saved from the Options step, an edited one from any step. Opened from the line of a
source (or of one of its groups or items), the modal shows that source, and the scope, already set.

### 1 — Source {#1--source}

Choose where the data comes from.

| Source                   | Description                                                                                                     |
| ------------------------ | --------------------------------------------------------------------------------------------------------------- |
| **South connector**      | Data collected by one of the configured South connectors                                                        |
| **OIBus API**            | Data pushed to OIBus via the REST API, from the **Data Source ID** given, or from every data source without one |
| **OIAnalytics Setpoint** | Write-back commands sent from OIAnalytics                                                                       |

### 2 — Item Scope (South connectors only) {#2--item-scope-south-connectors-only}

When the source is a South connector, you can restrict which of its items the transformer applies to.

| Scope              | Description                                                              |
| ------------------ | ------------------------------------------------------------------------ |
| **All items**      | Every item of the selected South connector goes through this transformer |
| **By group**       | Only items belonging to a specific group are processed                   |
| **Specific items** | Hand-pick individual items from the search list                          |

With **All items** or **By group**, check **Except some items** to leave a few items out: the transformer applies to
every other item of the South connector (or of the group), including the items added later. **Specific items** needs at
least one item: a transformer without item would apply to all of them.

Below the scope, the modal tells how many items the transformer would send, given the other transformers of the North
connector and their order: how many are currently dropped, how many it takes over from another transformer, and how
many keep a transformer applying first. It warns when a transformer applying first already sends all the selected items.

:::tip
A single North connector can have **multiple transformers** with different sources and scopes. This lets you apply
different conversions to different parts of the same South connector — for example, one transformer for a group of
temperature sensors and another for flow meters. When an incoming batch mixes items covered by different
transformers, OIBus automatically splits it so each part is processed by the transformer that actually targets it.
:::

If more than one transformer could match the same item (e.g. one scoped to a group and another to "All items" of
the same South connector), OIBus resolves it with this priority, most specific first:

1. A transformer scoped to that **specific item**.
2. A transformer scoped to the item's **group**.
3. A transformer scoped to **all items** of the South connector (no group, no specific items selected) —
   the fallback.

The first configured transformer that matches, in that order, is used; ties within the same level are broken by
the transformer's position in the list. A transformer leaving an item out (**Except some items**) is skipped for that
item, which falls back to the next level.

### 3 — Transformer {#3--transformer}

Once a source is selected, the list is automatically filtered to show only compatible transformers, and the obvious
one is preselected: **File (as is)** for files sent to a North connector accepting files, otherwise the only standard
transformer producing the North connector's own format (e.g. OIAnalytics values, MQTT payloads), otherwise the
passthrough of the data (**JSON**). The available choices depend on the type of South connector chosen:

| South connector type                                                                                                                                 | Compatible standard transformers                                                                     |
| ---------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| **OPC UA, OPC Classic, Modbus, ADS, S7, BACnet, OSIsoft PI, MySQL, PostgreSQL, MSSQL, Oracle, SQLite, MongoDB, ODBC, OLEDB, InfluxDB** (record list) | CSV, JSON, MQTT payloads, Modbus values, OIAnalytics payload, OPCUA values                           |
| **MQTT, REST, SFTP, FTP, Folder Scanner, OIAnalytics** (file-based)                                                                                  | File (as is), Records (from CSV), MQTT payloads (from CSV), CSV (from JSON), OIAnalytics (from JSON) |
| **OIBus API**                                                                                                                                        | File (as is), Records (from CSV), MQTT payloads (from CSV), CSV (from JSON), OIAnalytics (from JSON) |
| **OIAnalytics Setpoint**                                                                                                                             | JSON, MQTT payloads, Modbus values, OPCUA values                                                     |

Custom transformers are also shown in this list and are always named by the user.

:::info Data without transformer
A North connector ignores the data no transformer is configured for: such sources (and items) are shown as **Dropped**
in the Transformers section (see [The sources of a North connector](#the-sources-of-a-north-connector)).
:::

After choosing a transformer, its settings form appears directly in the modal.

## Standard Transformers {#standard-transformers}

Standard transformers are built-in and require only configuration — no coding.

:::info Record lists sent to OIAnalytics
The OIAnalytics North only accepts files and OIAnalytics values: record lists are sent through the
[OIAnalytics payload](#oianalytics-payload) transformer. When upgrading to 3.10, this
transformer is added to every OIAnalytics North for the point-based South connectors (OPC UA, OPC Classic, Modbus,
ADS, S7, BACnet, OSIsoft PI) and history queries, whose values it used to receive without transformer.
:::

### For record lists {#for-record-list-south-connectors}

Most South connectors send **record lists**: arrays of flat records.

- **Point-based connectors** (OPC UA, OPC Classic, Modbus, TwinCAT ADS, Siemens S7, BACnet, OSIsoft PI) send
  **point records**: the point, the timestamp and the value of each reading, possibly with extra fields depending on
  the protocol (e.g. the OPC UA `quality`).

  ```json
  { "pointId": "plant/temp1", "timestamp": "2024-01-15T10:00:00.000Z", "value": 23.5, "quality": "Good" }
  ```

- **Query-based connectors** (MySQL, PostgreSQL, MSSQL, Oracle, SQLite, MongoDB, ODBC, OLEDB, InfluxDB) send each
  row (or document) exactly as the database returned it.

  ```json
  { "deviceId": "sensor-1", "readingTime": "2024-01-15T10:00:00.000Z", "reading": 23.5 }
  ```

The transformers below render a record list into the shape a North connector expects. Those needing a point, a
timestamp or a value read them from configurable columns, which default to `pointId`, `timestamp` and `value`: point
records work without changing them, while for query rows you name the columns of your query.

---

#### CSV {#csv}

Converts the records into a CSV file. Every field of a record becomes a column automatically — there's no need to
declare a field just to have it appear in the output. Declaring a field (via **Fields Mapping**, using the same
per-field mapping model as [CSV (from JSON)](#csv-from-json)) is only needed when a column must be renamed, cast to a
specific type, reformatted (dates), or passed through a JavaScript expression. With **Keep the other fields** off,
only the configured fields are written, in their configured order.

##### Settings {#settings}

| Setting                   | Description                                                                                                                                                                                        |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Filename**              | Output filename; supports `@CurrentDate` (current UTC timestamp), and, for content coming from a South history query, `@QueryStartTime`/`@QueryEndTime` (the queried time window, empty otherwise) |
| **Encoding**              | Output character encoding (`UTF_8`, `UTF_8_BOM`, `LATIN_1`, `UTF_16_LE`)                                                                                                                           |
| **First row as header**   | Whether to write a header row with the column names                                                                                                                                                |
| **Compression**           | Gzip-compress the output file                                                                                                                                                                      |
| **Delimiter**             | Column separator (`COMMA`, `SEMI_COLON`, `TAB`, etc.)                                                                                                                                              |
| **Newline**               | Row separator (`CRLF`, `LF`, `CR`)                                                                                                                                                                 |
| **Quote character**       | Character used to quote fields (`DOUBLE_QUOTE`, `SINGLE_QUOTE`, `NONE`)                                                                                                                            |
| **Escape character**      | Character used to escape a quote character inside a quoted field (`BACKSLASH`, `DOUBLE_QUOTE`)                                                                                                     |
| **Null value**            | Value written out when a configured field is `null` or missing from the record                                                                                                                     |
| **Keep the other fields** | Write the fields that are not configured in **Fields Mapping** unchanged (enabled by default)                                                                                                      |
| **Fields Mapping**        | A list of per-column overrides (rename, cast, reformat, or process) — see below                                                                                                                    |

Each entry in **Fields Mapping** targets one column, by its name in the records:

| Setting               | Description                                                                                          |
| --------------------- | ---------------------------------------------------------------------------------------------------- |
| **Field Name**        | Name of the field to configure, matching a key in the records                                        |
| **Column Name**       | Header for this column in the output CSV. Leave empty to keep the original field name.               |
| **Data Type**         | How to cast the value: `string`, `number`, `boolean`, `datetime`, `array`, or `object`               |
| **Field Process**     | Optional JavaScript expression applied after casting (e.g. `value.toUpperCase()`)                    |
| **Datetime Settings** | Shown only when Data Type is `datetime` — input/output type, timezone, format and locale (see below) |

When **Data Type** is `datetime`, **Datetime Settings** describes how to parse the raw value and how to render
it:

| Setting                               | Description                                                                        |
| ------------------------------------- | ---------------------------------------------------------------------------------- |
| **Timestamp input type**              | How to parse the raw value (`string`, `iso-string`, `unix-epoch`, `unix-epoch-ms`) |
| **Input timezone / format / locale**  | Used to parse the raw value when its input type is `string`                        |
| **Timestamp output type**             | How to render the value (`string`, `iso-string`, `unix-epoch`, `unix-epoch-ms`)    |
| **Output timezone / format / locale** | Used to render the value when its output type is `string`                          |

##### Example — Point records {#example}

**Input (OPC UA items: temp1, pressure1)**

```json
[
  { "pointId": "plant/temp1", "timestamp": "2024-01-15T10:00:00.000Z", "value": 23.5, "quality": "Good" },
  { "pointId": "plant/pressure1", "timestamp": "2024-01-15T10:00:00.000Z", "value": 102.1, "quality": "Good" }
]
```

With **Keep the other fields** off, Delimiter `SEMI_COLON`, and three fields: `pointId` (column `Reference`, field
process `value.split('/').pop()`), `timestamp` (column `Timestamp`, datetime from `iso-string` to `string` with format
`yyyy-MM-dd HH:mm:ss` and timezone `Europe/Paris`) and `value` (column `Value`):

**Output CSV** — `quality` is not written

```csv
Reference;Timestamp;Value
temp1;2024-01-15 11:00:00;23.5
pressure1;2024-01-15 11:00:00;102.1
```

##### Example — Query rows {#example-7}

**Input** (record list from a MySQL item)

```json
[
  { "deviceId": "sensor-1", "readingTime": "2024-01-15T10:00:00.000Z", "value": 23.5 },
  { "deviceId": "sensor-1", "readingTime": "2024-01-15T10:01:00.000Z", "value": 23.8 }
]
```

With a single field configured (`readingTime`, data type `datetime`, input type `iso-string`, output type
`string` with format `yyyy-MM-dd HH:mm:ss` and timezone `Europe/Paris`) — `deviceId` and `value` are not
configured, so they pass through unchanged:

**Output CSV**

```csv
deviceId,value,readingTime
sensor-1,23.5,2024-01-15 11:00:00
sensor-1,23.8,2024-01-15 11:01:00
```

#### JSON {#json}

Writes the records as a JSON file, unchanged. Use this when the North connector expects files (e.g. a file-based North
like Azure Blob, Amazon S3, SFTP or REST).

This transformer has **no configuration options**.

##### Example {#example-1}

**Input** — the point records of an OPC UA or Modbus South connector, or the rows of a SQL query.

**Output** — the same records saved as a `.json` file.

---

#### MQTT payloads {#mqtt-payloads}

Maps each record to an MQTT message using a **point ID → topic** mapping table. Records whose point ID has no match
are silently dropped. The payload is the record without its point column, as a JSON string.

##### Settings {#settings-1}

| Setting             | Description                                                   |
| ------------------- | ------------------------------------------------------------- |
| **Point ID column** | Field of the records holding the point ID (default `pointId`) |
| **Mapping**         | List of `{ pointId, topic }` pairs                            |

##### Example {#example-2}

Mapping: `plant/temp1 → sensors/temperature`, `plant/pressure1 → sensors/pressure`

**Input**

```json
[
  { "pointId": "plant/temp1", "timestamp": "2024-01-15T10:00:00.000Z", "value": "23.5" },
  { "pointId": "plant/pressure1", "timestamp": "2024-01-15T10:00:00.000Z", "value": "102.1" },
  { "pointId": "plant/unknown", "timestamp": "2024-01-15T10:00:00.000Z", "value": "0" }
]
```

**Output** — `plant/unknown` is dropped (no mapping)

```json
[
  { "topic": "sensors/temperature", "payload": "{\"timestamp\":\"2024-01-15T10:00:00.000Z\",\"value\":\"23.5\"}" },
  { "topic": "sensors/pressure", "payload": "{\"timestamp\":\"2024-01-15T10:00:00.000Z\",\"value\":\"102.1\"}" }
]
```

#### Modbus values {#modbus-values}

Maps each record to a Modbus write command using a **point ID → address** mapping table. The value is cast to the
appropriate type (see [Modbus value conversion](#modbus-value-conversion)). Records with no match are dropped.

##### Modbus value conversion {#modbus-value-conversion}

Booleans, numbers and their text forms (`true`, `false`, `1`, `0`, `12.5`...) are accepted. A coil is set for `true`
or any non-zero number, and cleared for `false` or `0`. A register receives the integer part of the number (`12.7` →
`12`), and `1` / `0` for `true` / `false`. Any other value (e.g. `on`, an empty text) is skipped with a warning.

##### Settings {#settings-2}

| Setting             | Description                                                                           |
| ------------------- | ------------------------------------------------------------------------------------- |
| **Point ID column** | Field of the records holding the point ID (default `pointId`)                         |
| **Value column**    | Field of the records holding the value to write (default `value`)                     |
| **Mapping**         | List of `{ pointId, address, modbusType }` pairs (`modbusType`: `coil` or `register`) |

##### Example {#example-3}

Mapping: `plant/valve1 → 0x0010 (coil)`, `plant/speed → 0x0020 (register)`

**Input**

```json
[
  { "pointId": "plant/valve1", "timestamp": "2024-01-15T10:00:00.000Z", "value": "true" },
  { "pointId": "plant/speed", "timestamp": "2024-01-15T10:00:00.000Z", "value": "1450" }
]
```

**Output**

```json
[
  { "address": "0x0010", "value": true, "modbusType": "coil" },
  { "address": "0x0020", "value": 1450, "modbusType": "register" }
]
```

#### OIAnalytics payload {#oianalytics-payload}

Prepares records for the OIAnalytics North connector, which needs it to receive record lists. Only the point ID, the
timestamp and the value of each record are forwarded — extra fields such as the quality are stripped — and the
timestamps can be truncated (in UTC) to a chosen precision to reduce storage footprint. To save bandwidth, the values are written in the OIAnalytics **compact
format**: three parallel arrays of the same size (`timestamps`, `values`, `references`), the i-th value being made of
the i-th element of each array.

Records without point ID, value or valid timestamp are skipped, with a single warning per batch. A date column
returned by a database driver as a date object is used as is; other timestamps are parsed with the timestamp
settings.

##### Settings {#settings-3}

| Setting                        | Description                                                                                                                                                               |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Point ID column**            | Field of the records holding the point ID (default `pointId`)                                                                                                             |
| **Timestamp column**           | Field of the records holding the timestamp (default `timestamp`)                                                                                                          |
| **Value column**               | Field of the records holding the value (default `value`)                                                                                                                  |
| **Timestamp type**             | Format of the raw timestamp: `iso-string` (default, as in point records), `unix-epoch`, `unix-epoch-ms`, or `string`                                                      |
| **Timezone / Format / Locale** | Used to parse the raw timestamp when its type is `string`                                                                                                                 |
| **Precision**                  | Timestamp precision: `ms` (unchanged), `s`, `min`, or `hr`                                                                                                                |
| **Reference process**          | Optional JavaScript expression applied to each point ID to build the OIAnalytics reference, `value` being the point ID (e.g. `value.replace('plant/', '').toUpperCase()`) |

##### Example — Precision `s` {#example--precision-s}

**Input**

```json
[{ "pointId": "tag/temp1", "timestamp": "2024-01-15T10:00:00.523Z", "value": "23.5", "quality": "good" }]
```

**Output** — milliseconds are zeroed, `quality` is stripped

```json
{ "timestamps": ["2024-01-15T10:00:00.000Z"], "values": ["23.5"], "references": ["tag/temp1"] }
```

##### Example — Query rows {#example--query-rows}

**Input** (record list from a PostgreSQL item), with Point ID column `deviceId`, Timestamp column `readingTime`
(type `string`, format `yyyy-MM-dd HH:mm:ss`, timezone `Europe/Paris`) and Value column `reading`:

```json
[{ "deviceId": "sensor-1", "readingTime": "2024-01-15 11:00:00", "reading": 23.5 }]
```

**Output**

```json
{ "timestamps": ["2024-01-15T10:00:00.000Z"], "values": [23.5], "references": ["sensor-1"] }
```

---

#### OPCUA values {#opcua-values}

Maps each record to an OPC UA write command using a **point ID → node ID** mapping table. The value is forwarded
as-is. Records with no match, or without value, are dropped.

##### Settings {#settings-4}

| Setting             | Description                                                       |
| ------------------- | ----------------------------------------------------------------- |
| **Point ID column** | Field of the records holding the point ID (default `pointId`)     |
| **Value column**    | Field of the records holding the value to write (default `value`) |
| **Mapping**         | List of `{ pointId, nodeId }` pairs                               |

##### Example {#example-4}

Mapping: `plant/temp1 → ns=1;s=Temperature`, `plant/valve1 → ns=1;s=Valve1`

**Input**

```json
[
  { "pointId": "plant/temp1", "timestamp": "2024-01-15T10:00:00.000Z", "value": "23.5" },
  { "pointId": "plant/valve1", "timestamp": "2024-01-15T10:00:00.000Z", "value": "true" }
]
```

**Output**

```json
[
  { "nodeId": "ns=1;s=Temperature", "value": "23.5" },
  { "nodeId": "ns=1;s=Valve1", "value": "true" }
]
```

### For file-based South connectors {#for-file-and-query-based-south-connectors}

These transformers process files or JSON payloads produced by connectors such as MQTT, REST, SFTP, FTP, Folder
Scanner and OIAnalytics, as well as data injected via the **OIBus API**.

---

#### File (as is) {#file-as-is}

Sends the files as they are, keeping their name, to a North connector expecting files (Azure Blob, Amazon S3, SFTP,
REST, File Writer, OIAnalytics...). The JSON payloads of the MQTT South connector and of the OIBus API are saved as
`.json` files.

This transformer has **no configuration options**.

---

#### Records (from CSV) {#records-from-csv}

Parses a CSV file and maps each row to a point record `{ pointId, timestamp, value }`. The transformer converts the
raw timestamp string to ISO-8601 according to the configured format.

##### Settings {#settings-5}

| Setting              | Description                                                                           |
| -------------------- | ------------------------------------------------------------------------------------- |
| **Has header**       | Whether the first row is a header row                                                 |
| **Delimiter**        | Column separator (`COMMA`, `SEMI_COLON`, `TAB`, etc.)                                 |
| **Point ID column**  | Column name (header mode) or zero-based index holding the point identifier            |
| **Timestamp column** | Column name or index holding the timestamp                                            |
| **Value column**     | Column name or index holding the value                                                |
| **Timestamp type**   | Format of the raw timestamp (`iso-string`, `unix-epoch`, `unix-epoch-ms`, `string`)   |
| **Timezone**         | Timezone for parsing (only used when type is `string`)                                |
| **Format**           | Custom datetime pattern (only used when type is `string`, e.g. `yyyy-MM-dd HH:mm:ss`) |

##### Example {#example-5}

This transformer is useful when a REST South connector fetches CSV exports from an API, or when a Folder Scanner
South connector picks up CSV files dropped by another system.

**Input CSV** (fetched by a REST item)

```csv
SensorID,Timestamp,Reading
tag/temp1,2024-01-15T10:00:00.000Z,23.5
tag/temp1,2024-01-15T10:01:00.000Z,23.8
tag/pressure1,2024-01-15T10:00:00.000Z,102.1
```

**Output (point records)**

```json
[
  { "pointId": "tag/temp1", "timestamp": "2024-01-15T10:00:00.000Z", "value": 23.5 },
  { "pointId": "tag/temp1", "timestamp": "2024-01-15T10:01:00.000Z", "value": 23.8 },
  { "pointId": "tag/pressure1", "timestamp": "2024-01-15T10:00:00.000Z", "value": 102.1 }
]
```

These records can then be forwarded to the North connectors that accept record lists (Console, File Writer).

---

#### MQTT payloads (from CSV) {#mqtt-payloads-from-csv}

Parses a CSV file and converts each row into an MQTT message with a topic and a payload. Two payload modes are
supported:

- **Simple** — a single column becomes the payload, cast to the configured type.
- **Object** — multiple columns are assembled into a JSON object payload.

##### Settings {#settings-6}

| Setting               | Description                                                                           |
| --------------------- | ------------------------------------------------------------------------------------- |
| **Has header**        | Whether the first row is a header row                                                 |
| **Delimiter**         | Column separator                                                                      |
| **Topic column**      | Column name or index holding the MQTT topic                                           |
| **Payload type**      | `string`, `number`, `boolean`, `datetime`, or `object`                                |
| **Value column**      | Column for the value (simple payload types only)                                      |
| **Object fields**     | List of `{ key, column, dataType }` mappings (object payload only)                    |
| **Datetime settings** | Input/output datetime conversion (applies when payload type or a field is `datetime`) |

##### Example — Simple payload {#example--simple-payload}

**Input CSV**

```csv
topic,value
plant/pump1/speed,1450
plant/pump1/running,true
```

**Output (MQTT messages)**

```json
[
  { "topic": "plant/pump1/speed", "payload": "1450" },
  { "topic": "plant/pump1/running", "payload": "true" }
]
```

##### Example — Object payload {#example--object-payload}

**Input CSV**

```csv
topic,value,quality,timestamp
plant/sensor1,23.5,good,2024-01-15T10:00:00.000Z
plant/sensor2,48.0,good,2024-01-15T10:00:00.000Z
```

Object fields: `value → number`, `quality → string`, `timestamp → datetime`

**Output (MQTT messages)**

```json
[
  { "topic": "plant/sensor1", "payload": "{\"value\":23.5,\"quality\":\"good\",\"timestamp\":\"2024-01-15T10:00:00.000Z\"}" },
  { "topic": "plant/sensor2", "payload": "{\"value\":48.0,\"quality\":\"good\",\"timestamp\":\"2024-01-15T10:00:00.000Z\"}" }
]
```

---

#### CSV (from JSON) {#csv-from-json}

Parses a JSON structure and writes a CSV file. A **row iterator path** (JSONPath expression) identifies the array
of objects that become rows, and each configured **field** maps a path within each row to a CSV column. Fields
support datetime conversion, type casting, and optional per-field JavaScript post-processing expressions.

##### Settings {#settings-7}

| Setting               | Description                                                                                                                                                                                        |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Filename**          | Output filename; supports `@CurrentDate` (current UTC timestamp), and, for content coming from a South history query, `@QueryStartTime`/`@QueryEndTime` (the queried time window, empty otherwise) |
| **Encoding**          | `UTF_8`, `UTF_8_BOM`, `LATIN_1`, or `UTF_16_LE`                                                                                                                                                    |
| **Header**            | Whether to include the column header row                                                                                                                                                           |
| **Delimiter**         | Column separator                                                                                                                                                                                   |
| **Newline**           | Line ending (`LF`, `CRLF`, `CR`)                                                                                                                                                                   |
| **Quote char**        | `DOUBLE_QUOTE`, `SINGLE_QUOTE`, or `NONE`                                                                                                                                                          |
| **Escape char**       | `DOUBLE_QUOTE` or `BACKSLASH`                                                                                                                                                                      |
| **Null value**        | String written when a field is missing or null (defaults to empty string)                                                                                                                          |
| **Row iterator path** | JSONPath pointing to the array of rows (e.g. `$.data[*]`)                                                                                                                                          |
| **Fields**            | One entry per CSV column (see below)                                                                                                                                                               |

Each **field** entry:

| Setting               | Description                                                                             |
| --------------------- | --------------------------------------------------------------------------------------- |
| **Column name**       | Header label in the CSV                                                                 |
| **JSON path**         | JSONPath to the value within the current row (e.g. `$.timestamp`)                       |
| **Data type**         | `string`, `number`, `boolean`, `datetime`, `array`, or `object`                         |
| **Datetime settings** | Input and output format/timezone/type when data type is `datetime`                      |
| **Field process**     | Optional JS expression to post-process the extracted value (e.g. `value.toUpperCase()`) |

##### Example {#example-6}

A REST South connector fetches a JSON report from an API. The **CSV (from JSON)** transformer extracts the
relevant fields and reformats them for a File Writer North connector.

**Input JSON** (returned by the REST item)

```json
{
  "data": [
    { "ts": "2024-01-15T10:00:00.000Z", "tag": "temp1", "val": 23.5, "ok": true },
    { "ts": "2024-01-15T10:01:00.000Z", "tag": "temp1", "val": 23.8, "ok": true },
    { "ts": "2024-01-15T10:00:00.000Z", "tag": "pressure1", "val": 102.1, "ok": false }
  ]
}
```

Configuration:

- Row iterator path: `$.data[*]`
- Fields: `Timestamp` (`$.ts`, datetime), `Tag` (`$.tag`, string), `Value` (`$.val`, number), `OK` (`$.ok`, boolean)

**Output CSV**

```csv
Timestamp,Tag,Value,OK
2024-01-15T10:00:00.000Z,temp1,23.5,true
2024-01-15T10:01:00.000Z,temp1,23.8,true
2024-01-15T10:00:00.000Z,pressure1,102.1,false
```

:::info Nested JSON strings
Both **CSV (from JSON)** and **OIAnalytics (from JSON)** (below) can automatically parse JSON-stringified
intermediate nodes — for example an MQTT South connector whose messages carry a JSON payload as a raw string. If a
path segment resolves to a string that itself contains JSON, the rest of the path is resolved against the parsed
value. This also applies to the **row iterator path** itself: it can cross that string boundary and still produce
one row per nested match, so a single message holding several readings splits into several rows. See the
[OIAnalytics (from JSON)](#oianalytics-from-json) example below for a worked-through case.
:::

#### OIAnalytics (from JSON) {#oianalytics-from-json}

Extracts point ID, value, and timestamp from an arbitrary JSON structure via JSONPath expressions and produces
values in the OIAnalytics compact format (`timestamps`, `values` and `references` parallel arrays) — the same
output as the [OIAnalytics payload](#oianalytics-payload) transformer. A **row iterator
path** identifies which part of the payload becomes one row (one value) per match; the point ID, value, and
timestamp paths are then resolved relative to that row.

This is the transformer to reach for when a South connector (typically MQTT, REST, or Folder Scanner) delivers raw
JSON that doesn't already match OIBus's point records, and you want to feed it straight to an
OIAnalytics North connector without writing a custom transformer.

##### Settings {#settings-8}

| Setting                   | Description                                                                                                                                                                                                                                                                     |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Row Iterator JSONPath** | JSONPath to the array of rows that become values (e.g. `$[*]`). Automatically parses a JSON-stringified intermediate node when direct traversal fails, so the path may cross into a field holding raw JSON text (e.g. an MQTT payload) and still yield one row per nested match |
| **Point ID JSONPath**     | JSONPath to the point identifier within the current row (e.g. `$[*].id`); wildcards (`[*]`) are resolved to the current row's indices                                                                                                                                           |
| **Value JSONPath**        | JSONPath to the value within the current row                                                                                                                                                                                                                                    |
| **Timestamp JSONPath**    | JSONPath to the raw timestamp within the current row. Falls back to the current time if it cannot be resolved                                                                                                                                                                   |
| **Reference process**     | Optional JavaScript expression applied to each resolved point ID to build the OIAnalytics reference, `value` being the point ID (e.g. `value.replace('plant/', '').toUpperCase()`)                                                                                              |
| **Timestamp input type**  | Format of the raw timestamp: `String`, `ISO string`, `Unix epoch (s)`, or `Unix epoch (ms)`                                                                                                                                                                                     |
| **Timezone**              | Timezone used when parsing (only used when input type is `String`)                                                                                                                                                                                                              |
| **Format**                | Custom datetime pattern (only used when input type is `String`, e.g. `yyyy-MM-dd HH:mm:ss`)                                                                                                                                                                                     |
| **Locale**                | Locale used for parsing month/day names (only used when input type is `String`)                                                                                                                                                                                                 |
| **Timestamp precision**   | Output precision the resulting ISO timestamp is truncated to: `Millisecond`, `Second`, `Minute`, or `Hour`                                                                                                                                                                      |

##### Example — MQTT messages with a JSON-stringified payload {#example--mqtt-messages-with-a-json-stringified-payload}

An MQTT South connector delivers each message as `{ message, timestamp, item }`, where `message` is the **raw
MQTT payload string**. A single message can carry more than one metric, so the row iterator uses **two**
wildcards — one for the outer array of messages, one for the metrics inside each message's (JSON-stringified)
payload — and fans out one row per metric, whether a given message holds one reading or several.

**Input** — the first message carries two metrics, the second carries one

```json
[
  {
    "message": "{\"metrics\":[{\"name\":\"PLANT.UNIT1.TANK3.LEVEL\",\"value\":52.2936,\"timestamp\":\"2026-07-16T08:50:18.808Z\"},{\"name\":\"PLANT.UNIT1.TANK3.TEMP\",\"value\":18.4,\"timestamp\":\"2026-07-16T08:50:19.001Z\"}]}"
  },
  { "message": "{\"metrics\":[{\"name\":\"PLANT.UNIT2.PUMP1.SPEED\",\"value\":1450,\"timestamp\":\"2026-07-16T08:50:20.500Z\"}]}" }
]
```

Configuration:

- Row Iterator JSONPath: `$[*].message.metrics[*]`
- Point ID JSONPath: `$[*].message.metrics[*].name`
- Value JSONPath: `$[*].message.metrics[*].value`
- Timestamp JSONPath: `$[*].message.metrics[*].timestamp`
- Timestamp input type: `ISO string`, Timestamp precision: `Millisecond`

The first `[*]` walks the outer array of messages; the second crosses the `message` string boundary (parsed
automatically) to walk the metrics inside it. Both are resolved together for each row, so the same configuration
handles a single-metric message and a multi-metric message alike.

**Output** — three rows: two from the first message, one from the second

```json
{
  "timestamps": ["2026-07-16T08:50:18.808Z", "2026-07-16T08:50:19.001Z", "2026-07-16T08:50:20.500Z"],
  "values": [52.2936, 18.4, 1450],
  "references": ["PLANT.UNIT1.TANK3.LEVEL", "PLANT.UNIT1.TANK3.TEMP", "PLANT.UNIT2.PUMP1.SPEED"]
}
```

## Custom Transformers {#custom-transformers}

When no standard transformer fits your use case, you can write a **Custom Transformer** in JavaScript or
TypeScript. Custom code runs inside a secure isolated sandbox with no access to the host file system, Node.js
modules, or the network.

Custom transformers are created in the **Engine → Transformers** page and are then available in the transformer
selection list of any North connector. Their **input type** is `any` (files and payloads), `record-list` or
`setpoint`; their **output type** is `any`, `record-list`, `mqtt`, `opcua`, `modbus` or `oianalytics`.

:::info Custom transformers from OIBus 3.9
The `time-values` data type no longer exists: custom transformers taking or producing time-values were switched to
`record-list` on upgrade. Their code must now read and write flat point records (`{ pointId, timestamp, value }`,
e.g. `record.value`) instead of `{ pointId, timestamp, data: { value } }`.
:::

### Transform Function {#transform-function}

Your code must export a `transform` function (or a default export). It receives four arguments and must return a
result object.

```typescript
/**
 * @param content  - The raw input data as a UTF-8 string (JSON, CSV, XML…)
 * @param source   - Metadata about the data source ({ type, dataSourceId, … })
 * @param filename - The original filename (or a generated ID if no file was involved)
 * @param options  - The transformer options as configured in the UI
 */
export function transform(
  content: string,
  source: object,
  filename: string,
  options: object
): { data: unknown; filename: string; numberOfElement?: number } {
  // …
}
```

| Return field      | Description                                                                                 |
| ----------------- | ------------------------------------------------------------------------------------------- |
| `data`            | The content written to the cache file (see below): a string, raw binary, or any other value |
| `filename`        | The filename used when the output is stored in the North cache                              |
| `numberOfElement` | Optional count of processed records, shown in logs and metrics                              |

The transformer's output is **written to the cache file as it is**, then read back by the North
according to its content type. `data` is handled by kind:

| `data` returned                              | Stored as                    | Use with                                                |
| -------------------------------------------- | ---------------------------- | ------------------------------------------------------- |
| a **string**                                 | the string verbatim (UTF-8)  | any output type — you control the exact text            |
| a **`Uint8Array` / `ArrayBuffer`** (binary)  | the raw bytes, byte-for-byte | the **`any`** output type only (file Norths)            |
| any **other value** (object, array, number…) | `JSON.stringify(data)`       | typed outputs (`record-list`, `mqtt`, …) that read JSON |

:::caution Match `data` to the output type; keep `filename` a string

- For **typed** output types (`record-list`, `mqtt`, `oianalytics`, `modbus`, `opcua`) the North reads
  the cache file as **JSON** — return a string or an object/array (which OIBus serializes to JSON).
  Returning binary here will not parse.
- **Binary** output (`Uint8Array`/`ArrayBuffer`) is for the **`any`** output type, where file Norths
  (File Writer, S3, Azure, OIAnalytics file upload) write/upload the bytes untouched.
- A non-string, non-binary value that `JSON.stringify` rejects (a circular structure, a `BigInt`) or
  drops (a function) fails the transform with a clear error rather than being cached.

`filename` **must be a string** — it becomes the cache filename and is recorded in the connector
metrics, so returning an object or array there can break metrics persistence. When you derive it from
input data (an MQTT topic, a payload field…), coerce it and strip path separators, e.g.
`` `mqtt_${String(topic).replace(/[\\/]/g, '_')}.json` ``.
:::

### Available Libraries {#available-libraries}

The following libraries are pre-loaded in the sandbox and available via `require`:

| Library                                                                | `require` name  | Description                                     |
| ---------------------------------------------------------------------- | --------------- | ----------------------------------------------- |
| **[Luxon](https://moment.github.io/luxon/)**                           | `luxon`         | Date/time parsing, formatting, and arithmetic   |
| **[JSONPath Plus](https://jsonpath-plus.github.io/JSONPath/docs/ts/)** | `jsonpath-plus` | JSONPath queries over arbitrary JSON structures |

### Logging {#logging}

logger. All messages appear prefixed with `CUSTOM TRANSFORMER:`.

### Limits {#limits}

| Limit         | Value                                            |

| Timeout       | Configurable in the transformer settings         |
| Module access | Only `luxon`, `jsonpath-plus`, `papaparse`       |

#### Example 1 — Reformat a JSON array to CSV (JavaScript) {#example-1--reformat-a-json-array-to-csv-javascript}

A REST South connector returns a JSON array. This transformer converts it to a semicolon-delimited CSV file
for a File Writer North connector.

**Input (`content`)**

```json
[
  { "ts": "2024-01-15T10:00:00.000Z", "id": "temp1", "val": 23.5 },
  { "ts": "2024-01-15T10:01:00.000Z", "id": "temp1", "val": 23.8 },
  { "ts": "2024-01-15T10:00:00.000Z", "id": "pressure1", "val": 102.1 }
]
```

**Output**

```csv
Timestamp;Tag;Value
2024-01-15T10:00:00.000Z;temp1;23.5
2024-01-15T10:01:00.000Z;temp1;23.8
2024-01-15T10:00:00.000Z;pressure1;102.1
```

**Code**

```javascript
export function transform(content, source, filename, options) {
  const Papa = require('papaparse');
  const rows = JSON.parse(content);

  const csv = Papa.unparse(
    rows.map(r => ({
      Timestamp: r.ts,
      Tag: r.id,
      Value: r.val
    })),
    { delimiter: ';', header: true }
  );

  return {
    data: csv,
    filename: `export_${filename.replace('.json', '.csv')}`,
    numberOfElement: rows.length
  };
}
```

#### Example 2 — Filter and enrich point records (TypeScript) {#example-2--filter-and-enrich-point-records-typescript}

Only keep readings above a configured threshold, and annotate each with a derived `status` field.

**Input (`content`)** — the point records of a point-based South connector, `options.threshold = 20`

```json
[
  { "pointId": "plant/temp1", "timestamp": "2024-01-15T10:00:00.000Z", "value": "23.5" },
  { "pointId": "plant/temp2", "timestamp": "2024-01-15T10:00:00.000Z", "value": "18.0" },
  { "pointId": "plant/pressure1", "timestamp": "2024-01-15T10:00:00.000Z", "value": "102.1" }
]
```

**Output** — `temp2` is dropped (18.0 ≤ 20), the others are annotated

```json
[
  { "pointId": "plant/temp1", "timestamp": "2024-01-15T10:00:00.000Z", "value": "23.5", "status": "NORMAL" },
  { "pointId": "plant/pressure1", "timestamp": "2024-01-15T10:00:00.000Z", "value": "102.1", "status": "HIGH" }
]
```

**Code**

```typescript
type PointRecord = { pointId: string; timestamp: string; value: string };

export function transform(
  content: string,
  _source: object,
  _filename: string,
  options: { threshold: number }
): { data: string; filename: string; numberOfElement: number } {
  const records: Array<PointRecord> = JSON.parse(content);
  const threshold = options.threshold ?? 0;

  const filtered = records
    .filter(record => parseFloat(record.value) > threshold)
    .map(record => ({
      ...record,
      status: parseFloat(record.value) > threshold * 2 ? 'HIGH' : 'NORMAL'
    }));

  console.info(`Kept ${filtered.length} / ${records.length} records above threshold ${threshold}`);

  return {
    data: JSON.stringify(filtered),
    filename: `filtered_${Date.now()}.json`,
    numberOfElement: filtered.length
  };
}
```

```javascript
export function transform(content, _source, _filename, _options) {
  const { JSONPath } = require('jsonpath-plus');
  const data = JSON.parse(content);

  const timestamps = JSONPath({ path: '$.records[*].header.ts', json: data });
  const tags = JSONPath({ path: '$.records[*].tag', json: data });
  const values = JSONPath({ path: '$.records[*].measurements.val', json: data });

  const records = timestamps.map((ts, i) => ({
    pointId: tags[i],
    timestamp: ts,
    value: values[i]
  }));

  return {
    data: JSON.stringify(records),
    filename: `extracted_${Date.now()}.json`,
    numberOfElement: records.length
  };
}
```

#### Example 5 — Normalize MQTT JSON messages to records (JavaScript) {#example-5--normalize-mqtt-json-messages-to-records-javascript}

An **MQTT South** connector delivers each batch of received messages as a single `any-content` payload:
a JSON array of `{ message, timestamp, item: { id, name, topic } }`, where `message` is the **raw MQTT
payload string**. That raw payload can be any shape — a bare number, a JSON string, a flat object, or
an array of readings (see the [JSON topics](../../developer/local-test-stack.md#json-topics) published
by the local test stack). This transformer normalizes all of them into point records (`record-list` output),
using the topic as the point ID.

**Input (`content`)** — three messages from different topics

```json
[
  {
    "message": "{\"value\":35.17,\"unit\":\"celsius\",\"timestamp\":\"2026-06-04T08:15:06.673+00:00\",\"quality\":\"good\"}",
    "timestamp": "2026-06-04T08:15:06.700Z",
    "item": { "id": "i1", "name": "flat", "topic": "workshop1/json/flat" }
  },
  {
    "message": "44.53",
    "timestamp": "2026-06-04T08:15:06.700Z",
    "item": { "id": "i2", "name": "number", "topic": "workshop2/json/number" }
  },
  {
    "message": "[{\"timestamp\":\"2026-06-04T08:15:06.673+00:00\",\"value\":34.95},{\"timestamp\":\"2026-06-04T08:15:08.673+00:00\",\"value\":35.48}]",
    "timestamp": "2026-06-04T08:15:06.700Z",
    "item": { "id": "i3", "name": "array", "topic": "workshop1/json/array" }
  }
]
```

**Output** — one point record per reading; the array message yields two

```json
[
  { "pointId": "workshop1/json/flat", "timestamp": "2026-06-04T08:15:06.673+00:00", "value": "35.17" },
  { "pointId": "workshop2/json/number", "timestamp": "2026-06-04T08:15:06.700Z", "value": "44.53" },
  { "pointId": "workshop1/json/array", "timestamp": "2026-06-04T08:15:06.673+00:00", "value": "34.95" },
  { "pointId": "workshop1/json/array", "timestamp": "2026-06-04T08:15:08.673+00:00", "value": "35.48" }
]
```

**Code**

```javascript
export function transform(content, _source, _filename, _options) {
  const messages = JSON.parse(content); // [{ message, timestamp, item: { topic } }, …]
  const records = [];

  // Extract a scalar value from one reading, whatever its shape.
  const toValue = reading => {
    if (reading !== null && typeof reading === 'object') {
      // Flat reading ({ value, … }); fall back to the whole object for nested shapes.
      return reading.value ?? JSON.stringify(reading);
    }
    return reading; // number, string or boolean
  };

  for (const { message, timestamp, item } of messages) {
    // The raw MQTT payload may be JSON (object/array/number/string) or plain text.
    let parsed;
    try {
      parsed = JSON.parse(message);
    } catch {
      parsed = message; // non-JSON payload: keep the raw string
    }

    const readings = Array.isArray(parsed) ? parsed : [parsed];
    for (const reading of readings) {
      records.push({
        pointId: item.topic,
        timestamp: (reading && reading.timestamp) || timestamp,
        value: String(toValue(reading))
      });
    }
  }

  return {
    data: JSON.stringify(records),
    // Always a plain string filename — never a payload object (see the caution above).
    filename: `mqtt_${Date.now()}.json`,
    numberOfElement: records.length
  };
}
```

:::tip Generate these payloads locally
The [local test stack](../../developer/local-test-stack.md#json-topics) publishes exactly these MQTT
JSON shapes (`flat`, `nested`, `array`, `mixed`, `string`, `number`), so you can point an MQTT South
connector at it and exercise a custom transformer against every case.
:::
