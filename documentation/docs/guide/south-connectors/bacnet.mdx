# BACnet®/IP

BACnet® (ASHRAE 135) is the standard communication protocol for building automation and control devices —
HVAC controllers, metering, lighting, and similar equipment. OIBus acts as a BACnet/IP client, communicating
over UDP, using the [@bacnet-js/client](https://github.com/bacnet-js/client) library.

## Specific Settings {#specific-settings}

### Connection {#connection}

| Setting               | Description                                                                                                                  | Example Value     |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------ | ------------------ |
| **Port**               | UDP port used for BACnet/IP communication. `47808` (`0xBAC0`) is the standard BACnet/IP port. Connectors on the same port and **Local interface** share one socket, so that a test or an **Explore** with unsaved settings gets its replies while the connector runs. | `47808`            |
| **APDU timeout**       | Maximum time, in milliseconds, to wait for a device's response to a request before treating it as failed.                   | `6000`             |
| **Retry interval**     | Time to wait, in milliseconds, before reconnecting after a transport-level failure (e.g. the local socket itself fails).    | `10000`            |
| **Discovery**          | How **Test settings** and the root level of **Explore** find devices: **Broadcast Who-Is** lists every device answering a broadcast `Who-Is`; **Target device (unicast)** goes straight to one device, without any `Who-Is`; **Router (unicast)** sends the `Who-Is` to one BACnet router alone, which forwards it to the networks behind it. | `Broadcast Who-Is` |
| **Target device address** | _(Shown with **Target device (unicast)**)_ IP address (and optional port) of the device. | `192.168.1.10`     |
| **Target device instance** | _(Shown with **Target device (unicast)**)_ Device instance of the device (`0` – `4194302`). | `201`              |
| **Router address**     | _(Shown with **Router (unicast)**)_ IP address (and optional port) of the BACnet router. | `192.168.1.20` |
| **Broadcast address**  | _(Shown with **Broadcast Who-Is**)_ Broadcast address of the `Who-Is` sent to discover devices. Ignored when BBMD is enabled: the `Who-Is` then goes through the BBMD. | `255.255.255.255`  |
| **Local interface**    | Optional. IP address of the local network card to bind the BACnet/IP socket to. Leave empty to use every network card (see [When to set the local interface](#when-to-set-the-local-interface)). | `192.168.1.50`     |
| **Max parallel queries** | Maximum number of items (or synchronized groups) OIBus reads at the same time, up to `16`. Requests to a single device are still sent one at a time, so a higher value only speeds up items spread over several devices. | `1` |

:::tip Target device instead of broadcast

Some networks don't forward BACnet broadcast traffic at all (routed segments, VLANs, or a policy that
simply disables it), and a device often answers `Who-Is` with an `I-Am` broadcast on its own subnet, which
never reaches OIBus from another subnet. Since `ReadProperty`, `ReadPropertyMultiple`, and `SubscribeCOV` are
unicast — sent directly to each item's configured **Device address** — actual data collection works
regardless of whether broadcast is available. Only **Test settings** and browsing the device list in
**Explore** rely on `Who-Is`/`I-Am`. The **Target device (unicast)** discovery skips them: given the device's address
and instance, as in YABE, it reads the device directly, which needs nothing more than plain IP routing — the
same reachability `ReadProperty` already requires, no BBMD involved.

For devices [behind a BACnet router](#devices-behind-a-bacnet-router), the **Router (unicast)** discovery sends
the `Who-Is` to the router alone. The devices still answer with an `I-Am`, which a router on another subnet
usually broadcasts on its own subnet: enable [BBMD](#bbmd-foreign-device-registration) too. The `Who-Is` still
goes to the router, and the BBMD brings the replies back to OIBus.

:::

### When to set the local interface {#when-to-set-the-local-interface}

OIBus opens one UDP socket on the BACnet port. With **Local interface** empty, the socket listens on every
network card, and the operating system picks the card each request leaves from. Set it to the IP address of
the card connected to the BACnet network when:

- **The OIBus host has several network cards** — an office network and an OT network, a VPN, Docker or
  Hyper-V virtual adapters. A `Who-Is` broadcast to `255.255.255.255` leaves from one card only, usually the
  one of the default route, and the devices on the other cards never see it.
- **Devices answer an address they cannot reach**, because the operating system picked another card's address
  as the source of the requests.

Leave it empty otherwise. Setting **Broadcast address** to the subnet's own broadcast address (for example
`172.27.23.255`) is often enough for the operating system to pick the right card.

:::caution Linux
On Linux, a socket bound to one IP address receives no broadcast: the `I-Am` replies and COV notifications
that devices broadcast are lost. Only set **Local interface** on Linux with the **Target device (unicast)**
discovery and polled items, or check that discovery and COV still work. Windows delivers broadcasts to a
socket bound to one of its cards.
:::

### Polling and COV Subscriptions {#polling-and-cov-subscriptions}

Each item's **Scan mode** decides how it is collected, exactly as for any other South connector:

- A regular schedule (e.g. `Every 1 min`) **polls** the item — OIBus issues a `ReadProperty` or
  `ReadPropertyMultiple` request each time the schedule fires.
- The reserved **Subscription** schedule switches the item to **Change of Value (COV)** — OIBus subscribes
  once and the device pushes a new value whenever it changes, instead of being polled.

Items due on the same poll tick are grouped per physical device and read together with a single
`ReadPropertyMultiple` request per chunk, instead of one request per point. A device that refuses
`ReadPropertyMultiple` (many small controllers don't implement it) is read one property at a time with
`ReadProperty` instead. When a device answers with an error for one property (unknown object or property),
only that item is skipped, with a warning in the logs; the other items of the request are still collected.

| Setting                     | Description                                                                                                                                   | Example Value |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | -------------- |
| **Max objects per request**  | Maximum number of object/property pairs OIBus packs into a single `ReadPropertyMultiple` request to one device, and of trend log records it asks for in a single `ReadRange` request. Lower this if a device rejects large requests (e.g. no APDU segmentation support). | `20`           |
| **COV subscription lifetime** | Lifetime, in seconds, requested for a COV subscription. `0` requests a subscription that never expires.                                     | `300`          |
| **COV renewal margin**       | How long, in seconds, before a finite-lifetime COV subscription expires that OIBus renews it — but never sooner than halfway through the lifetime. Has no effect when lifetime is `0`. | `60`           |

A COV subscription or renewal that fails (device offline, for example) is retried until it succeeds: after
**Retry interval**, then twice as late each time, up to every 10 minutes. Only the first failure is logged as a
warning; the following ones are logged at debug level, and a success after failures is logged again. Devices only hold a limited number of COV subscriptions, so OIBus cancels its
subscriptions when the connector stops, and renews the same ones (rather than adding new ones) when it
reconnects after a network failure.

### Data Throttling {#data-throttling}

Applies to items on the **Subscription** schedule — incoming COV notifications are buffered and flushed to
North caches in batches rather than one at a time.

| Setting                         | Description                                                                    | Example Value |
| -------------------------------- | ------------------------------------------------------------------------------ | -------------- |
| Number of messages before flush | Number of COV notifications to accumulate before flushing to North caches      | `1000`         |
| Delay between flush             | Time delay (in milliseconds) between automatic flushes of accumulated messages | `1000`         |

### BBMD / Foreign Device Registration {#bbmd-foreign-device-registration}

A **BBMD** (BACnet Broadcast Management Device) forwards broadcast messages — such as `Who-Is` discovery and
COV notifications — between separate BACnet/IP subnets. Enable this when OIBus and the target devices are
not on the same local IP broadcast domain (e.g. routed subnets, VLANs, or a VPN link).

| Setting              | Description                                                                                                          | Example Value           |
| --------------------- | --------------------------------------------------------------------------------------------------------------------- | ------------------------ |
| **Enabled**           | Registers OIBus as a foreign device with a remote BBMD instead of broadcasting on the local subnet.                  | Enabled/Disabled         |
| **BBMD address**      | _(Shown when enabled)_ IP address (and optional port) of the BBMD to register with.                                  | `10.0.0.1:47808`         |
| **Foreign device TTL** | _(Shown when enabled)_ Lifetime, in seconds, of the foreign device registration. OIBus renews it automatically before it expires. | `900`                    |

When enabled with the **Broadcast Who-Is** discovery, device discovery (**Test settings**, root-level
**Explore**) is routed through the BBMD instead of a plain local broadcast.

**Test settings** and **Test item** register OIBus as a foreign device first, even when the connector is not
running: the BBMD only forwards broadcasts to and from registered devices. If the BBMD refuses the
registration (or does not answer), the test fails with that error.

:::note BBMD is not just for discovery

Registering as a foreign device also matters for **COV subscriptions**: a device typically sends its
`UnconfirmedCOVNotification` as a local broadcast on its own subnet, not a targeted unicast to the
subscriber. Without a foreign device registration, those notifications never reach OIBus from a remote
subnet, even though the unicast `SubscribeCOV` request that set up the subscription worked fine. This means
BBMD can stay enabled with the **Target device (unicast)** discovery — the two settings address different
things: one is about how OIBus reaches out (discovery), the other about whether remote broadcast traffic can
reach OIBus (COV reception).

:::

## Item Settings {#item-settings}

Each item targets one BACnet object property on one device.

| Setting              | Description                                                                                                         | Example Value      |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------- | -------------------- |
| **Device address**    | IP address (and optional port) of the target device, or of its BACnet router for a [routed device](#devices-behind-a-bacnet-router). | `192.168.1.10`      |
| **Device instance**   | The device's BACnet instance number. Used for identification and logging; requests are addressed by IP, not by this number. | `10`                |
| **Object type**       | Type of the BACnet object to read.                                                                                  | `Analog input`      |
| **Object instance**   | Instance number of the object within the device.                                                                    | `1`                 |
| **Property**          | Object property to read.                                                                                            | `Present value`     |
| **Device time zone**  | _(Trend log)_ Time zone the device's clock is set to: its [trend log](#history-from-trend-logs) records are timestamped in the device's local time, and this setting turns them into exact instants. Each item has its own, as devices may be set differently. | `Europe/Paris` |
| **Routed device**     | The device is on another BACnet network, behind a router. Shows the two settings below.                            | Enabled/Disabled    |
| **Network number**    | _(Routed device)_ BACnet network number of the device's network.                                                    | `2`                 |
| **MAC address**       | _(Routed device)_ Address of the device on that network: decimal station number for MS/TP, or hexadecimal bytes separated by colons. | `5`                 |

:::note Object type

`Analog input`, `Analog output`, `Analog value`, `Binary input`, `Binary output`, `Binary value`,
`Multi-state input`, `Multi-state output`, `Multi-state value`, `Accumulator`, `Pulse converter`, `Loop`,
`Integer value`, `Positive integer value`, `Large analog value`, `Character string value`: objects read one
property at a time, by polling or COV.

`Trend log`: the item collects the records the trend log has logged — see
[History from trend logs](#history-from-trend-logs). **Property** does not apply and is hidden.

Other BACnet object types (schedules, calendars, files, etc.) are not supported by this connector.

:::

:::note Property

`Present value` (default), `Status flags`, `Reliability`, `Out of service`, `Units`.

`Status flags` is sent as four `0`/`1` characters, in the BACnet order in-alarm, fault, overridden,
out-of-service: `0100` means the object is in fault. `Reliability` and `Units` are sent as their BACnet
enumeration number.

For an item on the **Subscription** schedule, `Present value` and `Status flags` are subscribed with the
standard `SubscribeCOV` service, which every COV-capable device supports. Any other property uses
`SubscribeCOVProperty`, an optional service that many devices don't implement: when a device refuses it,
OIBus logs a warning suggesting to poll the item with a regular schedule instead. These property
subscriptions never expire on the device; OIBus still renews them on the same schedule as other COV
subscriptions, and cancels them when the item is removed or the connector stops.

:::

:::note Test item

Clicking **Test item** reads the item directly from its **Device address**, without any `Who-Is`. When the
device refuses the read, the test shows its error decoded, for example `OBJECT/UNKNOWN_OBJECT` for an object
the device does not have: check the item's object type and instance.

:::

## History from Trend Logs {#history-from-trend-logs}

A **Trend log** object records the values of another object in the device itself, at a fixed interval or
on change, in a buffer of timestamped records. An item whose **Object type** is `Trend log` collects these
records instead of reading a current value: OIBus reads the trend log's buffer (`ReadRange`) and sends each
record with the time it was logged.

- On a regular schedule, each run collects the records logged since the previous run, like any history
  item: the item's **Max read interval**, **Read delay** and time offsets apply.
- In a [history query](../history-queries.md), the trend logs of a BACnet south back-fill the
  requested time range, as long as the device still holds those records — a trend log buffer has a fixed
  size, and the oldest records are dropped first.
- A trend log item cannot use the **Subscription** schedule: it only logs a warning there.

The buffer is read backwards from its most recent record, **Max objects per request** records per
`ReadRange` request, until a record older than the requested range.

:::caution Device time zone
BACnet devices log their records in their own local time, without a time zone. Set each trend log item's
**Device time zone** to the time zone its device's clock is set to, or every record will be shifted by the time
difference.
:::

## Devices Behind a BACnet Router {#devices-behind-a-bacnet-router}

Many building controllers are not on the IP network themselves: they sit on an MS/TP (RS-485) trunk, or
another BACnet network, behind a BACnet router — often the supervisory controller of the building. Such a
device has no IP address; OIBus reaches it through the router, with these item settings:

| Setting            | Value                                                                                                                                                                              |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Device address** | The router's IP address (and port).                                                                                                                                                |
| **Routed device**  | Enabled.                                                                                                                                                                           |
| **Network number** | The BACnet network number of the device's network, as configured on the router (`1` – `65534`).                                                                                    |
| **MAC address**    | The device's address on that network: its station number for MS/TP, in decimal (`0` – `255`), or for other networks its address bytes in hexadecimal separated by colons (`0A:00:00:05:BA:C0` for a BACnet/IP device: IP address then port). |

The discovery `Who-Is` is a global broadcast, which routers forward to the networks behind them: **Explore**
lists routed devices along with their network number and MAC address, and **Test settings** shows them as
`192.168.1.20, network 2, MAC 5`. Through a BBMD, the `Who-Is` stays a local broadcast on each subnet, so
routed devices are not discovered that way: use the **Router (unicast)** discovery instead, with BBMD still
enabled when the router is on another subnet. The **Target device (unicast)** discovery does not reach routed
devices.

:::caution COV subscriptions to routed devices
The BACnet library OIBus uses (`@bacnet-js/client` 3.3.2) sends COV subscription requests, and the
`ReadRange` requests that read trend logs, with a hop count of `0`, which routers discard. It is fixed in the
library but not released yet: until OIBus ships the update, use a polling schedule for items on routed
devices — on the **Subscription** schedule, they only log a warning — and trend logs of routed devices cannot
be read.
:::

## Discovering Devices and Objects {#discovering-devices-and-objects}

Click **Explore** to browse the BACnet network interactively instead of entering device and object
identifiers by hand:

1. At the root level, OIBus lists the devices with their name and instance number. With the **Target device (unicast)**
   discovery, it is that one device, without any `Who-Is`. With the **Router (unicast)** discovery, OIBus sends
   a `Who-Is` request to the router alone; otherwise it broadcasts it (or routes it through the BBMD, if
   enabled). It then lists every device that responds. The `Who-Is` is a global broadcast, so devices
   [behind a BACnet router](#devices-behind-a-bacnet-router) are listed too.
2. Selecting a device reads its object list and shows every object it exposes, enriched with its current
   present value where available. A device that cannot send its whole object list in one reply (no
   segmentation support, common on MS/TP) has it read entry by entry instead.

Check devices or objects and click **Add as items** to create their items at once — each object gives one item
named `<device name> - <object name>`, reading its `present-value` — or **Keep in sync…** to create an
[items synchronisation](./common-settings.md#items-synchronisation) that adds the items of new objects and disables
those of removed ones on each run. A checked device stands for all its objects. See
[Selecting Nodes](./common-settings.md#selecting-nodes) and [Discovery Defaults](./common-settings.md#discovery-defaults).

Use **Test settings** on the connector's own settings to run the same device discovery as a quick
connectivity check, without opening the full browser. With the **Target device (unicast)** discovery, it reads the
device's name, and fails when the device does not answer as the configured device instance.
