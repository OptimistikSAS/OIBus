# OPC UA™

OPC Unified Architecture (OPC UA) protocol for secure industrial data access in read-only mode, supporting both Historical Access (HA) and Data Access (DA) modes.

:::info Technology Overview

- Modern successor to OPC Classic™ (see [OPC Classic™ connector](./opc.mdx))
- TCP/IP based with tree-like address space
- Uses node IDs for data referencing
- Implemented using [node-opcua library](https://github.com/node-opcua/node-opcua)
- Natively embedded in many industrial controllers
  :::

## OPC Classic vs OPC UA {#opc-classic-vs-opc-ua}

|                          | OPC Classic™                                                                                                        | OPC UA                                                                                     |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| **Standard**             | Three separate specs: **DA** (live values), **HDA** (historical data), **AE** (alarms &amp; events)                 | Single unified standard: **DA** (live values) + **HA** (historical access) + alarms        |
| **Historical mode name** | **HDA** — Historical Data Access                                                                                    | **HA** — Historical Access (OPC UA Part 11). Same concept, different name — see note below |
| **Transport**            | COM/DCOM — Windows inter-process communication only                                                                 | TCP/IP or HTTPS — works over any IP network                                                |
| **Platform**             | Windows only                                                                                                        | Cross-platform: Windows, Linux, macOS, embedded                                            |
| **Security**             | Relies on Windows domain/DCOM security                                                                              | Built-in: message signing, encryption, certificate-based auth                              |
| **Introduced**           | 1996                                                                                                                | 2006                                                                                       |
| **OIBus requirement**    | Requires an [OIBus Agent](../oibus-agent/installation.mdx) running on the Windows machine that hosts the OPC server | Connects directly from OIBus — no agent needed                                             |

:::note HDA vs HA — the naming confusion
Users coming from an OPC Classic background often look for **HDA** in OPC UA and cannot find it.
OPC UA renames the equivalent feature **HA** (Historical Access, defined in OPC UA Part 11).
The concept is identical — querying a server for values recorded in the past — but the acronym
changed. In OIBus, the OPC Classic connector calls the mode `HDA`, and the OPC UA connector calls
it `HA`. Do not confuse OPC UA HA with OPC Classic HDA: they are separate protocols and are **not
interoperable**.
:::

**Choose OPC Classic** when your infrastructure already runs OPC DA or OPC HDA servers that cannot be migrated. An OIBus Agent must be deployed on the Windows machine that hosts those servers.

**Choose OPC UA** for any new deployment. OPC UA is the current industry standard: platform-independent, network-friendly, and with native security built in.

## Specific Settings {#specific-settings}

### Connection Configuration {#connection-configuration}

| Setting                                     | Description                                                                                                                                                     | Example Value              |
| ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------- |
| **Endpoint URL**                            | URL of the OPC UA server.                                                                                                                                       | `opc.tcp://localhost:4840` |
| **Keep session alive**                      | Ping the server regularly so that it does not delete the session while it is idle. Enabled by default.                                                          | Enabled/Disabled           |
| **Connection timeout**                      | Maximum time in milliseconds to connect to the server: TCP connection, secure channel and session creation. The connector retries after the **Retry Interval**. | `15000`                    |
| **Retry Interval**                          | Delay in milliseconds between retries.                                                                                                                          | `5000`                     |
| **Max parallel queries** (`maxParallelRun`) | Maximum number of item/group queries OIBus may run concurrently against this server. From `1` (fully sequential) to `32`.                                       | `1`                        |
| **Read timeout**                            | Maximum time in milliseconds to wait for the response of a request (read, history read, browse...).                                                             | `15000`                    |

The OPC UA server deletes a session that stays idle for too long (60 seconds by default). When **Keep session alive** is
disabled and the scan mode of an item is longer than that, the session has expired by the next scan, which fails, and the
connector reconnects. Keep this setting enabled, unless the server does not support it.

### Parallel Queries {#parallel-queries}

By default (**Max parallel queries** = `1`), OIBus queries this connector's items and groups one at a
time, even if several of them are due at once. Raising this setting lets OIBus pipeline up to that many
queries concurrently instead, which helps when many items/groups are on short scan modes and waiting
their turn would otherwise fall behind.

All concurrent queries share the **same OPC UA session** — OIBus does not open a separate session per
query. A single session already supports overlapping running requests safely, and many OPC UA
servers (especially those embedded in PLCs) cap the number of concurrent sessions per client at a low
number, sometimes exactly one, so sharing one session avoids hitting that cap. **Max parallel queries**
only bounds how many requests get pipelined over that shared session at once — it does not open
additional sessions.

:::tip Raise gradually
Each concurrent query still adds load on the same underlying connection and on the server itself.
Increase **Max parallel queries** gradually and watch server response times and the connector's
logs — a server with limited processing capacity may respond better to a lower value even if more
concurrent queries would technically be allowed.
:::

### Subscription {#subscription}

These settings apply to the items in subscription mode.

| Setting                                               | Description                                                                                                              | Example Value |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ | ------------- |
| **Publishing interval**                               | Interval in milliseconds at which the server sends the notifications of the monitored items. The server may revise it.   | `150`         |
| **Max keep alive count**                              | Number of publishing intervals without data after which the server sends a keep alive message. The server may revise it. | `10`          |
| **Number of messages before flush** (data throttling) | Number of messages to accumulate before flushing to North caches.                                                        | `1000`        |
| **Delay between flush** (data throttling)             | Time delay (in milliseconds) between automatic flushes of accumulated messages.                                          | `1000`        |

The keep alive period is the **Publishing interval** multiplied by the **Max keep alive count**. The server drops the
subscription when it has not received a publish request for 10 keep alive periods: when the subscription is silent for as
long, OIBus considers it lost and reconnects. The **Read timeout** is not used for subscriptions.

| Setting             | Description                                                       | Example Value                                       |

| Basic128-RSA15         | ⚠️ **Deprecated.** AES-128 encryption, HMAC-SHA1 signing, RSA PKCS#1 v1.5 padding. Avoid — both SHA-1 and RSA-1.5 are weak. |

## Node Metadata {#node-metadata}

When browsing the server — with [**Explore**](./common-settings.md#exploring-the-data-source), or in an
[items synchronisation](./common-settings.md#items-synchronisation) run — OIBus reads the following fields for every
Variable node, when the server exposes them:

| Field         | Source in the OPC UA address space                                                      | Explore | Items synchronisation |
| ------------- | --------------------------------------------------------------------------------------- | :-----: | :-------------------: |
| `id`          | The node identifier, identifying the record across runs                                 |         |           ✓           |
| `nodeId`      | The node identifier                                                                     |    ✓    |           ✓           |
| `name`        | The node's display name                                                                 |    ✓    |           ✓           |
| `path`        | The display names from the discovery root down to the node, joined by `/`               |         |           ✓           |
| `type`        | The node class (`Variable`, `Object`, …)                                                |    ✓    |           ✓           |
| `description` | The node's `Description` attribute                                                      |    ✓    |           ✓           |
| `unit`        | Display name of the `EngineeringUnits` property (analog items)                          |    ✓    |           ✓           |
| `min` / `max` | Low / high bounds of the `EURange` property — the normal operating range (analog items) |    ✓    |           ✓           |
| `value`       | The current value                                                                       |    ✓    |                       |

A field the server doesn't expose for a node is simply left out. The current value is never read by a
synchronisation: it changes on every run, which would make every node look changed. In a synchronisation, these
fields can be used in the eligibility filter and in item field mapping expressions (e.g. `{{unit}}`). The
[discovery defaults](./common-settings.md#discovery-defaults) name each item after its `path`, which stays unique
across folders, unlike the display name alone.

Selected nodes can be added as items, or kept in sync, straight from the Explore modal — see
[Selecting Nodes](./common-settings.md#selecting-nodes).

Requests are batched per browsed level and split to respect the server's advertised operation limits
(`MaxNodesPerRead` / `MaxNodesPerBrowse`), or batches of 1000 nodes when the server doesn't advertise any. If a
metadata request fails, Explore still shows the nodes without these fields, while a synchronisation run fails rather
than record incomplete metadata.

## Security Configuration {#security-configuration}

### Communication Certificate {#communication-certificate}

When **Security Mode** is set to `Sign` or `Sign and Encrypt`, OIBus authenticates itself to the OPC UA server
using a certificate. This certificate is:

- **Auto-generated** by OIBus on first startup (4096-bit RSA, self-signed)
- **Location**: `<OIBusData>/certs/cert.pem` — private key: `<OIBusData>/certs/private.pem`

Before a secured connection can be established, **the OPC UA server must trust this certificate**. If it is
not in the server's trusted store, OIBus will log:

```
The connection may have been rejected by the server
```

To authorise it, import or copy `<OIBusData>/certs/cert.pem` into the server's trusted certificate store.

![Prosys Certificate Example](@site/static/img/guide/south/opcua/prosys-opcua-simulation-server-certificates.png)

:::info Prosys simulation server — trusted store paths

- **Trusted**: `.prosysopc\prosys-opc-ua-simulation-server\PKI\CA\trusted\certs\`
- **Rejected** (move from here to trusted): `.prosysopc\prosys-opc-ua-simulation-server\PKI\CA\rejected\`
  :::

### Authentication Certificate {#authentication-certificate}

When **Authentication** is set to `Certificate`, you must supply a separate identity certificate and its
private key in the connector settings (**Cert file path** and **Key file path** fields). This certificate
identifies the _user_, independently of the transport security certificate above.

The server must also trust this identity certificate. For Prosys, import it into:

```
.prosysopc\prosys-opc-ua-simulation-server\USERS_PKI\CA\certs\
```

If the server rejects it, OIBus logs `BadIdentityTokenRejected (0x80210000)`. In Prosys, rejected identity
certificates land in `.prosysopc\prosys-opc-ua-simulation-server\USERS_PKI\CA\rejected\` — move them to
the `certs\` folder next to it.

:::tip Reuse OIBus's generated certificate for authentication
You can point the **Cert file path** and **Key file path** connector fields to OIBus's own certificate
(`<OIBusData>/certs/cert.pem` and `<OIBusData>/certs/private.pem`) to use a single certificate for
both transport-level security and user authentication.
:::

## Creating a Custom Authentication Certificate for Prosys {#creating-a-custom-authentication-certificate-for-prosys}

If you need a dedicated identity certificate, used to authenticate OIBus, not only signing the communication,
generate one with OpenSSL:

1. Create `cert.conf`:

```ini
[ req ]
default_bits = 2048
default_md = sha256
distinguished_name = subject
req_extensions = req_ext
x509_extensions = req_ext
string_mask = utf8only
prompt = no

[ req_ext ]
basicConstraints = CA:FALSE
nsCertType = client, server
keyUsage = nonRepudiation, digitalSignature, keyEncipherment, dataEncipherment, keyCertSign
extendedKeyUsage= serverAuth, clientAuth
nsComment = "OIBus User Cert"
subjectKeyIdentifier=hash
authorityKeyIdentifier=keyid,issuer
subjectAltName = URI:urn:opcua:user:oibus,IP: 127.0.0.1

[ subject ]
countryName = FR
stateOrProvinceName = FR
localityName = Chambéry
organizationName = OI
commonName = oibus
```

2. Generate the certificate and strip the passphrase:

```bash
# Create key and certificate
openssl req -new -x509 -keyout oibus.key -out oibus.pem -config cert.conf

# Remove passphrase from key
openssl rsa -in oibus.key -out oibus.key

# Convert to DER format (required by some servers)
openssl x509 -inform PEM -outform DER -in oibus.pem -out oibus.der
```

3. Install in Prosys's user PKI store:

```bash
cp oibus.der ".prosysopc/prosys-opc-ua-simulation-server/USERS_PKI/CA/certs/"
```

Then, in the OIBus connector settings, set **Cert file path** to `oibus.pem` and **Key file path** to `oibus.key`.
