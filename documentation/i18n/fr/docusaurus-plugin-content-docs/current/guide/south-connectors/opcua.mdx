# OPC UA™

Protocole OPC Unified Architecture (OPC UA) pour un accès sécurisé aux données industrielles en mode lecture seule, prenant en charge à la fois les modes Historical Access (HA) et Data Access (DA).

:::info Présentation technologique

- Successeur moderne d'OPC Classic™ (voir le [connecteur OPC Classic™](./opc.mdx))
- Basé sur TCP/IP avec un espace d'adressage arborescent
- Utilise des ID de nœud pour référencer les données
- Implémenté à l'aide de la [bibliothèque node-opcua](https://github.com/node-opcua/node-opcua)
- Nativement embarqué dans de nombreux automates industriels
  :::

## OPC Classic vs OPC UA {#opc-classic-vs-opc-ua}

|                            | OPC Classic™                                                                                                                | OPC UA                                                                                       |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| **Standard**               | Trois spécifications distinctes : **DA** (valeurs en direct), **HDA** (données historiques), **AE** (alarmes &amp; événements) | Norme unifiée unique : **DA** (valeurs en direct) + **HA** (accès historique) + alarmes         |
| **Nom du mode historique** | **HDA** — Historical Data Access                                                                                          | **HA** — Historical Access (OPC UA Part 11). Même concept, nom différent — voir la note ci-dessous |
| **Transport**               | COM/DCOM — communication inter-processus Windows uniquement                                                              | TCP/IP ou HTTPS — fonctionne sur tout réseau IP                                                |
| **Plateforme**              | Windows uniquement                                                                                                        | Multi-plateforme : Windows, Linux, macOS, embarqué                                             |
| **Sécurité**                | Repose sur la sécurité du domaine/DCOM Windows                                                                            | Intégrée : signature des messages, chiffrement, authentification par certificat                |
| **Introduit en**            | 1996                                                                                                                       | 2006                                                                                            |
| **Exigence OIBus**          | Nécessite un [agent OIBus](../oibus-agent/installation.mdx) s'exécutant sur la machine Windows hébergeant le serveur OPC | Se connecte directement depuis OIBus — aucun agent requis                                      |

:::note HDA vs HA — la confusion des noms
Les utilisateurs venant d'un environnement OPC Classic cherchent souvent **HDA** dans OPC UA et ne le trouvent pas.
OPC UA renomme la fonctionnalité équivalente **HA** (Historical Access, défini dans OPC UA Part 11).
Le concept est identique — interroger un serveur pour des valeurs enregistrées dans le passé — mais l'acronyme
a changé. Dans OIBus, le connecteur OPC Classic appelle le mode `HDA`, et le connecteur OPC UA l'appelle
`HA`. Ne confondez pas OPC UA HA avec OPC Classic HDA : ce sont des protocoles distincts et ils ne sont **pas
interopérables**.
:::

**Choisissez OPC Classic** lorsque votre infrastructure exploite déjà des serveurs OPC DA ou OPC HDA qui ne peuvent pas être migrés. Un agent OIBus doit être déployé sur la machine Windows qui héberge ces serveurs.

**Choisissez OPC UA** pour tout nouveau déploiement. OPC UA est la norme actuelle de l'industrie : indépendante de la plateforme, adaptée aux réseaux, et avec une sécurité native intégrée.

### Configuration de la connexion {#connection-configuration}

| Paramètre                                     | Description                                                                                                               | Exemple de valeur              |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- | -------------------------- |
| **URL du point d'accès**                            | URL du serveur OPC UA.                                                                                                 | `opc.tcp://localhost:4840` |
| **Maintenir la session active**                      | Maintenir la session active entre les messages.                                                                                  | Activé/Désactivé           |
| **Intervalle de nouvelle tentative**                          | Délai en millisecondes entre les nouvelles tentatives.                                                                                    | `5000`                     |
| **Délai d'expiration de lecture**                            | Durée d'exécution maximale en millisecondes pour les requêtes.                                                                      | `15000`                    |
| **Requêtes parallèles maximum** (`maxParallelRun`) | Nombre maximal de requêtes d'éléments/groupes qu'OIBus peut exécuter simultanément contre ce serveur. De `1` (entièrement séquentiel) à `32`. | `1`                         |

### Requêtes parallèles {#parallel-queries}

Par défaut (**Requêtes parallèles maximum** = `1`), OIBus interroge les éléments et groupes de ce connecteur un à
la fois, même si plusieurs d'entre eux sont dus en même temps. Augmenter ce paramètre permet à OIBus de traiter en pipeline jusqu'à
ce nombre de requêtes simultanément, ce qui aide lorsque de nombreux éléments/groupes ont des modes de scan courts et attendre
leur tour prendrait autrement du retard.

Toutes les requêtes simultanées partagent la **même session OPC UA** — OIBus n'ouvre pas de session séparée par
requête. Une session unique prend déjà en charge en toute sécurité des requêtes en cours de traitement qui se chevauchent, et de nombreux
serveurs OPC UA (en particulier ceux embarqués dans des automates) limitent le nombre de sessions simultanées par client à un nombre
faible, parfois exactement un, donc partager une seule session évite d'atteindre cette limite. **Requêtes parallèles maximum**
limite uniquement le nombre de requêtes traitées en pipeline sur cette session partagée à la fois — cela n'ouvre pas de
sessions supplémentaires.

:::tip Augmentez progressivement
Chaque requête simultanée ajoute quand même de la charge sur la même connexion sous-jacente et sur le serveur lui-même.
Augmentez **Requêtes parallèles maximum** progressivement et surveillez les temps de réponse du serveur et les
journaux du connecteur — un serveur avec une capacité de traitement limitée peut mieux répondre à une valeur plus basse même si
davantage de requêtes simultanées seraient techniquement autorisées.
:::

## Paramètres du groupe {#group-settings}

Les éléments sont organisés en **groupes**. Chaque groupe définit une planification partagée et, pour le mode HA, les
paramètres de régulation par défaut pour tous les éléments qu'il contient.

| Paramètre         | Description                                                | Exemple de valeur |
| ------------------ | ------------------------------------------------------------ | ------------- |
| **Nom**            | Libellé unique du groupe au sein de ce connecteur.            | `Group A`     |
| **Mode de scan** | Planification de collecte appliquée à chaque élément du groupe. | `Every 1 min` |

## Configuration de sécurité {#security-configuration}

### Certificat de communication {#communication-certificate}

Lorsque le **Mode de sécurité** est défini sur `Sign` ou `Sign and Encrypt`, OIBus s'authentifie auprès du serveur OPC UA
à l'aide d'un certificat. Ce certificat est :

- **Généré automatiquement** par OIBus au premier démarrage (RSA 4096 bits, auto-signé)
- **Emplacement** : `<OIBusData>/certs/cert.pem` — clé privée : `<OIBusData>/certs/private.pem`

Avant qu'une connexion sécurisée puisse être établie, **le serveur OPC UA doit faire confiance à ce certificat**. S'il n'est
pas dans le magasin de confiance du serveur, OIBus enregistrera dans les journaux :

```
The connection may have been rejected by the server
```

Pour l'autoriser, importez ou copiez `<OIBusData>/certs/cert.pem` dans le magasin de certificats de confiance du serveur.

![Exemple de certificat Prosys](../../../static/img/guide/south/opcua/prosys-opcua-simulation-server-certificates.png)

:::info Serveur de simulation Prosys — chemins du magasin de confiance

- **Approuvés** : `.prosysopc\prosys-opc-ua-simulation-server\PKI\CA\trusted\certs\`
- **Rejetés** (déplacer d'ici vers approuvés) : `.prosysopc\prosys-opc-ua-simulation-server\PKI\CA\rejected\`
  :::

### Certificat d'authentification {#authentication-certificate}

Lorsque l'**Authentification** est définie sur `Certificate`, vous devez fournir un certificat d'identité distinct et sa
clé privée dans les paramètres du connecteur (champs **Chemin du fichier de certificat** et **Chemin du fichier de clé**). Ce certificat
identifie l'_utilisateur_, indépendamment du certificat de sécurité de transport ci-dessus.

Le serveur doit également faire confiance à ce certificat d'identité. Pour Prosys, importez-le dans :

```
.prosysopc\prosys-opc-ua-simulation-server\USERS_PKI\CA\certs\
```

Si le serveur le rejette, OIBus enregistre `BadIdentityTokenRejected (0x80210000)`. Dans Prosys, les certificats d'identité
rejetés atterrissent dans `.prosysopc\prosys-opc-ua-simulation-server\USERS_PKI\CA\rejected\` — déplacez-les vers
le dossier `certs\` situé à côté.

:::tip Réutiliser le certificat généré par OIBus pour l'authentification
Vous pouvez pointer les champs de connecteur **Chemin du fichier de certificat** et **Chemin du fichier de clé** vers le certificat propre à OIBus
(`<OIBusData>/certs/cert.pem` et `<OIBusData>/certs/private.pem`) pour utiliser un seul certificat pour
à la fois la sécurité au niveau du transport et l'authentification de l'utilisateur.
:::

## Créer un certificat d'authentification personnalisé pour Prosys {#creating-a-custom-authentication-certificate-for-prosys}

Si vous avez besoin d'un certificat d'identité dédié, utilisé pour authentifier OIBus, et pas seulement pour signer la communication,
générez-en un avec OpenSSL :

1. Créez `cert.conf` :

```ini
[ req ]
default_bits = 2048
default_md = sha256
distinguished_name = subject
req_extensions = req_ext
x509_extensions = req_ext
string_mask = utf8only
prompt = no

[ req_ext ]
basicConstraints = CA:FALSE
nsCertType = client, server
keyUsage = nonRepudiation, digitalSignature, keyEncipherment, dataEncipherment, keyCertSign
extendedKeyUsage= serverAuth, clientAuth
nsComment = "OIBus User Cert"
subjectKeyIdentifier=hash
authorityKeyIdentifier=keyid,issuer
subjectAltName = URI:urn:opcua:user:oibus,IP: 127.0.0.1

[ subject ]
countryName = FR
stateOrProvinceName = FR
localityName = Chambéry
organizationName = OI
commonName = oibus
```

2. Générez le certificat et retirez la phrase secrète :

```bash
# Create key and certificate
openssl req -new -x509 -keyout oibus.key -out oibus.pem -config cert.conf

# Remove passphrase from key
openssl rsa -in oibus.key -out oibus.key

# Convert to DER format (required by some servers)
openssl x509 -inform PEM -outform DER -in oibus.pem -out oibus.der
```

3. Installez-le dans le magasin PKI utilisateur de Prosys :

```bash
cp oibus.der ".prosysopc/prosys-opc-ua-simulation-server/USERS_PKI/CA/certs/"
```

Ensuite, dans les paramètres du connecteur OIBus, définissez **Chemin du fichier de certificat** sur `oibus.pem` et **Chemin du fichier de clé** sur `oibus.key`.
