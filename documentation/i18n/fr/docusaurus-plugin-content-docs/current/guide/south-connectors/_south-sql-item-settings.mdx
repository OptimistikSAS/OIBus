## Paramètres du groupe {#group-settings}

Les éléments peuvent être organisés en groupes. Chaque groupe définit une planification de collecte partagée et des
paramètres de limitation par défaut. Les éléments d'un même groupe sont toujours récupérés **un par un** en séquence
— le groupe fournit simplement des valeurs par défaut communes que les éléments individuels peuvent surcharger.

| Setting        | Description                                                                                                                                       | Example Value             |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------- |
| **Name**       | Libellé unique du groupe au sein de ce connecteur.                                                                                                 | `Group A`                 |
| **Scan mode**  | Planification utilisée pour collecter tous les éléments du groupe.                                                                                 | `Every 1 min`             |
| **Throttling** | Valeurs de limitation par défaut (Max read interval, Read delay, Start time offset, End time offset, Recovery strategy) héritées par les éléments du groupe. | `3600, 200, 0, 0, oldest` |

## Paramètres des éléments {#item-settings}

Chaque élément peut être configuré individuellement avec ses propres paramètres de requête et sa propre gestion des
dates/heures. Les éléments héritent des valeurs par défaut de planification et de limitation de leur groupe, mais
chaque paramètre peut être surchargé au niveau de l'élément en désactivant **Sync with group**.

### Configuration de la requête {#query-configuration}

Le champ de requête accepte la syntaxe SQL standard avec la prise en charge de variables internes qui améliorent la
résilience et l'optimisation des performances de la récupération des données.

#### Variables de requête {#query-variables}

| Setting      | Description                                                                                         | Example Value              |
| ------------ | --------------------------------------------------------------------------------------------------- | -------------------------- |
| `@StartTime` | Initialisée à l'heure de la première exécution, puis mise à jour avec l'horodatage le plus récent du champ de référence | `2024-01-15T10:00:00.000Z` |
| `@EndTime`   | Défini sur l'heure actuelle (`now()`) ou sur la fin du sous-intervalle lorsque les requêtes sont découpées | `2024-01-15T11:00:00.000Z` |

Exemple de requête :

```sql
SELECT device_id, value, reading_time
FROM sensor_data
WHERE reading_time > @StartTime
AND reading_time < @EndTime
ORDER BY reading_time
```

:::info Query Splitting
Pour traiter de grands ensembles de données, les requêtes peuvent être automatiquement divisées en plus petits blocs
basés sur le temps, selon le paramètre de limitation **Max read interval**.
:::

### Configuration du champ date/heure {#datetime-field-configuration}

| Setting             | Description                                                                                                    | Example Value               |
| ------------------- | -------------------------------------------------------------------------------------------------------------- | --------------------------- |
| **Field name**      | Nom du champ date/heure dans votre instruction SELECT                                                          | `timestamp`, `reading_time` |
| **Reference field** | Désigne le champ qui détermine le `@StartTime` pour les requêtes suivantes                                     | `reading_time`              |
| **Type**            | Type de données du champ date/heure. Les valeurs disponibles diffèrent selon le connecteur — voir la note spécifique au connecteur ci-dessous. | `iso-string`, `unix-epoch`  |
| **Timezone**        | Fuseau horaire de la date/heure stockée (pour les types chaîne/date)                                            | `UTC`, `Europe/Paris`       |
| **Format**          | Modèle de format pour les dates/heures basées sur des chaînes                                                   | `yyyy-MM-dd HH:mm:ss`       |
| **Locale**          | Locale pour les éléments de format (par exemple, les noms de mois)                                              | `en_US`, `fr_FR`            |

:::warning Type Consistency Requirement
Lors de l'utilisation de conversions de date/heure dans les requêtes, veillez à garder le type cohérent à la fois
dans la liste SELECT et dans la clause WHERE :

Approche problématique (peut entraîner un comportement inattendu) :

```sql
SELECT value, CONVERT(datetime, string_field) AS timestamp
FROM table
WHERE string_field > @StartTime
```

Approche recommandée :

```sql
SELECT value, CONVERT(datetime, string_field) AS timestamp
FROM table
WHERE CONVERT(datetime, string_field) > @StartTime
```

:::

### Processus de flux de données {#data-flow-process}

1. OIBus exécute chaque requête configurée de manière séquentielle.
2. Les résultats sont consolidés en une sortie structurée.
3. L'instant maximal est extrait du champ date/heure de référence, converti en UTC, et stocké comme prochain
   `@StartTime`.
4. La sortie finale est formatée selon les [paramètres de sérialisation](#csv-serialization).
5. Les données traitées sont envoyées aux connecteurs North configurés.

:::tip Best Practices

1. Choisissez des champs de référence avec des valeurs cohérentes et croissantes.
2. Pour les dates/heures sous forme de chaînes, assurez-vous que le format correspond entre le stockage en base de
   données et les variables de requête.
3. Ajoutez des index sur les champs date/heure pour de meilleures performances de requête.
4. Utilisez le Max read interval pour découper les grandes plages temporelles en blocs gérables.

:::
