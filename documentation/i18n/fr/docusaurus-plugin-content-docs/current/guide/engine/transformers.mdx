# Transformateurs

Un **transformateur** se situe entre une source de données et un connecteur North. Il convertit les données entrantes
dans le format attendu par le connecteur North avant qu'elles ne soient placées dans le cache du connecteur. Au-delà de
la conversion de format, les transformateurs sont également le mécanisme de **filtrage** des données qu'un connecteur
North reçoit — voir [Filtrage des données](../north-connectors/common-settings.md#data-filtering) pour plus de
détails.

Les transformateurs sont configurés **sur le connecteur North**, dans la section **Transformateurs** de sa page de
paramètres.

## Les sources d'un connecteur North {#the-sources-of-a-north-connector}

La section Transformateurs liste chaque source de données — chaque connecteur South, l'API OIBus et les consignes
OIAnalytics — avec le transformateur par lequel passent ses données, dans une étiquette verte lorsque toutes ses
données sont envoyées ; dans une étiquette verte à contour (**Partiellement envoyée**) lorsque seuls certains de ses
éléments, ou certaines sources de données de l'API OIBus, le sont ; dans une étiquette grise (**Ignorée**) lorsqu'aucune
ne l'est. Un connecteur South dont tous les éléments ont un transformateur, par leur groupe ou par le leur, est
**Envoyée**. Une source qu'aucun transformateur standard ne peut envoyer à ce connecteur North est ignorée elle aussi :
un transformateur personnalisé peut tout de même l'envoyer. Filtrez la liste selon ce qui atteint le connecteur North,
selon le statut ou le type des connecteurs South, ou recherchez une source par son nom.

L'API OIBus n'est listée que lorsque les [points d'accès de contenu](./engine-settings.mdx#content-endpoints) du
serveur web sont activés, et les consignes OIAnalytics uniquement lorsque OIBus est
[enregistré](../installation/oianalytics.mdx) et qu'OIAnalytics est autorisé à envoyer des consignes.

- **Ajoutez un transformateur à une source** depuis sa ligne : le bouton portant le nom d'un transformateur l'ajoute en
  un clic (le transformateur évident pour ses données, lorsque ses options par défaut sont valides), et **Autre…**
  ouvre la fenêtre de configuration pour cette source.
- **Dépliez un connecteur South** pour voir ses groupes, puis leurs éléments, chacun avec le transformateur par lequel
  passent ses données : le sien, celui de son groupe (**de son groupe**), celui de tous les éléments (**de tous les
  items**), ou **Ignorée**. De là :
  - **Ajouter** un transformateur à un groupe, ou à un élément qui n'en a pas ;
  - **Remplacer** le transformateur dont un élément hérite : lorsque le transformateur et les options choisis sont ceux
    d'un autre élément, l'élément est ajouté à ce transformateur plutôt que de recevoir sa propre copie ;
  - **Exclure** un élément du transformateur dont il hérite (voir **Sauf certains items** ci-dessous) ;
  - retirer un élément de son propre transformateur (en supprimant le transformateur lorsqu'il s'agissait de son
    dernier élément).

Un transformateur qui n'est jamais utilisé, parce qu'un autre placé avant lui dans la liste s'applique aux mêmes
données, est barré.

## Configurer un transformateur {#configuring-a-transformer}

Cliquez sur **Ajouter un transformateur** dans la section Transformateurs (ou sur un bouton d'une source) pour ouvrir
la fenêtre de configuration. La fenêtre comporte trois étapes, comme les fenêtres des éléments : **Source et
transformateur** (d'où proviennent les données, les éléments d'un connecteur South auxquels il s'applique, et le
transformateur, nouveau ou copié), **Options** (celles du transformateur choisi, essayées immédiatement avec le panneau
de test situé en dessous), puis **Vérification et enregistrement** (le transformateur tel qu'il sera enregistré, ce qui
a changé depuis son enregistrement, et les étapes à corriger d'abord). Un nouveau transformateur peut être enregistré
depuis l'étape Options, un transformateur modifié depuis n'importe quelle étape. Ouverte depuis la ligne d'une source
(ou de l'un de ses groupes ou éléments), la fenêtre affiche cette source, et la portée, déjà renseignées.

### 1 — Source {#1--source}

Choisissez d'où proviennent les données.

| Source                    | Description                                                                                                                                        |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Connecteur South**      | Données collectées par l'un des connecteurs South configurés                                                                                       |
| **API OIBus**             | Données envoyées à OIBus via l'API REST, depuis l'**identifiant de source de données** indiqué, ou depuis toute source de données sans identifiant |
| **Consignes OIAnalytics** | Commandes d'écriture (write-back) envoyées depuis OIAnalytics                                                                                      |

### 2 — Portée des éléments (connecteurs South uniquement) {#2--item-scope-south-connectors-only}

Lorsque la source est un connecteur South, vous pouvez restreindre les éléments auxquels le transformateur s'applique.

| Portée                   | Description                                                                |
| ------------------------ | -------------------------------------------------------------------------- |
| **Tous les éléments**    | Chaque élément du connecteur South sélectionné passe par ce transformateur |
| **Par groupe**           | Seuls les éléments appartenant à un groupe spécifique sont traités         |
| **Éléments spécifiques** | Sélectionnez individuellement des éléments dans la liste de recherche      |

Les éléments à sélectionner (ou à écarter) se recherchent par nom et se filtrent par groupe, mode d'acquisition et
statut, comme dans la liste des éléments du connecteur South.

Avec **Tous les éléments** ou **Par groupe**, cochez **Sauf certains items** pour écarter quelques éléments : le
transformateur s'applique à tous les autres éléments du connecteur South (ou du groupe), y compris les éléments ajoutés
ultérieurement. **Éléments spécifiques** nécessite au moins un élément : un transformateur sans élément s'appliquerait
à tous.

Sous la portée, la fenêtre indique combien d'éléments le transformateur enverrait, compte tenu des autres
transformateurs du connecteur North et de leur ordre : combien sont actuellement ignorés, combien il reprend à un autre
transformateur, et combien conservent un transformateur qui s'applique avant lui. Elle avertit lorsqu'un transformateur
qui s'applique avant lui envoie déjà tous les éléments sélectionnés.

:::tip
Un même connecteur North peut avoir **plusieurs transformateurs** avec des sources et des portées différentes. Cela
vous permet d'appliquer des conversions différentes à différentes parties du même connecteur South — par exemple, un
transformateur pour un groupe de capteurs de température et un autre pour des débitmètres. Lorsqu'un lot entrant
mélange des éléments couverts par différents transformateurs, OIBus le divise automatiquement pour que chaque partie
soit traitée par le transformateur qui la cible réellement.
:::

Si plusieurs transformateurs peuvent correspondre au même élément (par exemple, l'un ciblant un groupe et l'autre
« Tous les éléments » du même connecteur South), OIBus résout cela avec cette priorité, du plus spécifique au moins
spécifique :

1. Un transformateur ciblant cet **élément spécifique**.
2. Un transformateur ciblant le **groupe** de l'élément.
3. Un transformateur ciblant **tous les éléments** du connecteur South (aucun groupe, aucun élément spécifique
   sélectionné) — le repli par défaut.

Le premier transformateur configuré qui correspond, dans cet ordre, est utilisé ; les égalités au sein d'un même
niveau sont départagées par la position du transformateur dans la liste. Un transformateur qui écarte un élément
(**Sauf certains items**) est ignoré pour cet élément, qui se rabat sur le niveau suivant.

### 3 — Transformateur {#3--transformer}

Une fois une source sélectionnée, la liste est automatiquement filtrée pour n'afficher que les transformateurs
compatibles, et le transformateur évident est présélectionné : **Fichier (tel quel, renommé ou converti)**, qui les
envoie tels quels, pour des fichiers envoyés à un connecteur North acceptant des fichiers, sinon le seul transformateur
standard produisant le format propre au connecteur North (par exemple des valeurs OIAnalytics, des charges utiles MQTT),
sinon le passage direct des données (**Fichier** : les enregistrements dans un fichier CSV). Les choix disponibles
dépendent du type de connecteur South choisi :

| Type de connecteur South                                                                                                                                         | Transformateurs standard compatibles                                                                                                   |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| **OPC UA®, OPC Classic, Modbus, ADS, S7, BACnet, OSIsoft PI, MySQL, PostgreSQL, MSSQL, Oracle, SQLite, MongoDB, ODBC, OLEDB, InfluxDB** (liste d'enregistrements) | Fichier, Charges utiles MQTT, Valeurs Modbus, Charge utile OIAnalytics, Valeurs OPCUA                                                  |
| **MQTT, REST, SFTP, FTP, Folder Scanner, OIAnalytics** (fichier)                                                                                                 | Fichier (tel quel, renommé ou converti), Enregistrements, Charges utiles MQTT, Valeurs Modbus, Charge utile OIAnalytics, Valeurs OPCUA |
| **API OIBus**                                                                                                                                                    | Fichier (tel quel, renommé ou converti), Enregistrements, Charges utiles MQTT, Valeurs Modbus, Charge utile OIAnalytics, Valeurs OPCUA |
| **Consignes OIAnalytics** (liste d'enregistrements)                                                                                                              | Fichier, Charges utiles MQTT, Valeurs Modbus, Charge utile OIAnalytics, Valeurs OPCUA                                                  |

Les transformateurs personnalisés apparaissent également dans cette liste et sont toujours nommés par l'utilisateur.

:::info Données sans transformateur
Un connecteur North ignore les données pour lesquelles aucun transformateur n'est configuré : ces sources (et
éléments) sont affichées comme **Ignorée** dans la section Transformateurs (voir
[Les sources d'un connecteur North](#the-sources-of-a-north-connector)).
:::

Après avoir choisi un transformateur, son formulaire de paramètres apparaît directement dans la fenêtre.

## Transformateurs standard {#standard-transformers}

Les transformateurs standard sont intégrés et nécessitent seulement une configuration — aucun code.

:::info Listes d'enregistrements envoyées à OIAnalytics
Le North OIAnalytics n'accepte que des fichiers et des valeurs OIAnalytics : les listes d'enregistrements sont envoyées
via le transformateur [Charge utile OIAnalytics](#oianalytics-payload). Lors de la mise à jour vers la 3.10, ce
transformateur est ajouté à chaque North OIAnalytics pour les connecteurs South à points (OPC UA, OPC Classic, Modbus,
ADS, S7, BACnet, OSIsoft PI) et les requêtes d'historique, dont il recevait auparavant les valeurs sans transformateur.
:::

### Pour les listes d'enregistrements {#for-record-list-south-connectors}

La plupart des connecteurs South envoient des **listes d'enregistrements** : des tableaux d'enregistrements plats.

- Les **connecteurs à points** (OPC UA, OPC Classic, Modbus, TwinCAT ADS, Siemens S7, BACnet, OSIsoft PI) envoient des
  **enregistrements de points** : le point, l'horodatage et la valeur de chaque lecture, éventuellement avec des champs
  supplémentaires selon le protocole (par exemple la `quality` d'OPC UA).

  ```json
  { "pointId": "plant/temp1", "timestamp": "2024-01-15T10:00:00.000Z", "value": 23.5, "quality": "Good" }
  ```

- Les **connecteurs à requêtes** (MySQL, PostgreSQL, MSSQL, Oracle, SQLite, MongoDB, ODBC, OLEDB, InfluxDB) envoient
  chaque ligne (ou document) exactement telle que la base de données l'a retournée.

  ```json
  { "deviceId": "sensor-1", "readingTime": "2024-01-15T10:00:00.000Z", "reading": 23.5 }
  ```

- Les **consignes OIAnalytics** sont aussi des enregistrements : la référence et la valeur de chaque consigne (voir
  [Consignes OIAnalytics](#for-oianalytics-setpoints)).

  ```json
  { "reference": "pump1/setSpeed", "value": 1200 }
  ```

Les transformateurs ci-dessous restituent une liste d'enregistrements dans la forme attendue par un connecteur North.
Ceux qui ont besoin d'un point, d'un horodatage ou d'une valeur les lisent dans des colonnes configurables, qui valent
par défaut `pointId`, `timestamp` et `value` : les enregistrements de points fonctionnent sans les modifier, tandis que
pour des lignes de requête vous indiquez les colonnes de votre requête.

#### Fichier {#file-from-records}

Écrit les enregistrements dans un fichier **CSV** ou **JSON**, pour les connecteurs North attendant des fichiers (Azure
Blob, Amazon S3, SFTP, REST, File Writer...). Avec ses paramètres par défaut, les enregistrements sont écrits dans un
fichier CSV : c'est le transformateur présélectionné pour les listes d'enregistrements envoyées à un connecteur North
attendant des fichiers.

Chaque champ d'un enregistrement est écrit automatiquement — il n'est pas nécessaire de déclarer un champ simplement
pour qu'il apparaisse dans la sortie. Déclarer un champ (via **Champs**) n'est nécessaire que lorsqu'il doit être
renommé, converti vers un type spécifique, reformaté (dates) ou traité. Lorsque
**Conserver les autres champs** est désactivé, seuls les champs configurés sont écrits, dans leur ordre de
configuration.

Avant la 3.10, les fichiers CSV et JSON avaient leurs propres transformateurs (CSV et JSON) : la mise à jour les
remplace par celui-ci, en conservant leurs paramètres.

##### Paramètres {#settings}

Le groupe **Fichier écrit** :

| Paramètre                        | Description                                                                                                        |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| **Type de fichier**              | `CSV` (par défaut) ou `JSON`                                                                                       |
| **Encodage**                     | Encodage des caractères en sortie (`UTF_8`, `UTF_8_BOM`, `LATIN_1`, `UTF_16_LE`)                                   |
| **Compresser le fichier**        | Compresser le fichier de sortie en Gzip, en ajoutant `.gz` à son nom                                               |
| **Première ligne comme en-tête** | Écrire ou non une ligne d'en-tête avec les noms de colonnes (CSV)                                                  |
| **Délimiteur**                   | Séparateur de colonnes (`COMMA`, `SEMI_COLON`, `TAB`, etc.) (CSV)                                                  |
| **Saut de ligne**                | Séparateur de lignes (`CRLF`, `LF`, `CR`) (CSV)                                                                    |
| **Caractère de citation**        | Caractère utilisé pour encadrer les champs (`DOUBLE_QUOTE`, `SINGLE_QUOTE`, `NONE`) (CSV)                          |
| **Caractère d'échappement**      | Caractère utilisé pour échapper un caractère de citation dans un champ encadré (`BACKSLASH`, `DOUBLE_QUOTE`) (CSV) |
| **Valeur nulle**                 | Valeur écrite lorsqu'un champ configuré vaut `null` ou est absent (CSV ; un fichier JSON écrit `null`)             |

Puis :

| Paramètre                       | Description                                                                                                                                                                                                                                                                                                                                 |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Nom du fichier**              | Nom du fichier de sortie (par défaut `@ConnectorName-@ItemName-@QueryStartTime-@CurrentDate.csv`) ; prend en charge `@CurrentDate` (horodatage UTC courant), `@ConnectorName`, `@ItemName` et, pour un contenu provenant d'une requête d'historique South, `@QueryStartTime`/`@QueryEndTime` (la fenêtre temporelle interrogée, vide sinon) |
| **Conserver les autres champs** | Écrire inchangés les champs qui ne sont pas configurés dans **Champs** (activé par défaut)                                                                                                                                                                                                                                                  |
| **Champs**                      | Une liste de surcharges par champ (renommage, conversion ou traitement) — voir ci-dessous                                                                                                                                                                                                                                                   |

Chaque entrée de **Champs** cible un champ, par son nom dans les enregistrements :

| Paramètre               | Description                                                                                                                                               |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Champ**               | Nom du champ à configurer, correspondant à une clé dans les enregistrements                                                                               |
| **Nom écrit**           | Nom de la colonne (CSV) ou de la propriété (JSON) dans la sortie. Laisser vide pour conserver le nom du champ.                                            |
| **Traitement du champ** | Opérations facultatives (par exemple Convertir en nombre, Conversion de date, Majuscules), voir [Traitements des champs et des valeurs](#field-processes) |

##### Traitements des champs et des valeurs {#field-processes}

Le **Traitement du champ** des champs de fichier et des charges utiles MQTT, ainsi que le **Traitement de la
référence**, le **Traitement de l'horodatage** et le **Traitement de la valeur** de la charge utile OIAnalytics, sont
des listes d'opérations appliquées dans l'ordre, chacune au résultat de la précédente : conversion (en texte, en
nombre, en booléen, ou en l'objet ou le tableau d'un texte JSON), majuscules ou minuscules, suppression des espaces,
sous-chaîne, ajout de texte, remplacement de texte, opération numérique, arrondi, conversion de date (éventuellement
arrondie à la valeur inférieure selon une **Précision** : seconde, minute, heure ou jour) — les mêmes opérations que le
[traitement des champs des synchronisations d'éléments](../south-connectors/common-settings.md#field-processing). Les
paramètres affichent les opérations dans l'ordre ; **Configurer…** les ouvre dans une fenêtre, pour les ajouter, les
modifier, les réordonner ou les supprimer.

La fenêtre teste les opérations sur des valeurs du champ : les premières du contenu sur lequel le dernier test du
transformateur a été exécuté (lancez d'abord le panneau de test du transformateur), qui peuvent être modifiées,
ajoutées ou supprimées pour tester d'autres cas. Chaque valeur est affichée avec son résultat, ou la raison pour
laquelle une opération échoue sur elle.

Les opérations ne s'appliquent qu'à une valeur pouvant être traitée :

- une valeur absente (`null`) est laissée telle quelle : elle n'est pas traitée. Dans un fichier CSV, elle est écrite
  avec la **Valeur nulle** ; dans une charge utile OIAnalytics, l'enregistrement est ignoré ;
- une valeur sur laquelle une opération échoue (par exemple un texte dans une opération numérique) est ignorée avec un avertissement dans les journaux, une fois par
  champ. Le champ est écrit vide dans un fichier, l'enregistrement est ignoré dans une charge utile OIAnalytics, et une
  référence est conservée telle quelle. Convertissez d'abord le champ (par exemple **Convertir** en nombre avant une
  opération numérique) ;
- un objet ou un tableau (d'un fichier JSON) peut uniquement être converti ;
- un champ sans opération est écrit tel qu'il est lu : un texte d'un fichier CSV reste un texte dans un fichier JSON,
  sauf s'il est converti.

Avant la 3.10, les traitements étaient des expressions JavaScript, et les champs avaient un type de données et des
paramètres de date/heure : la mise à jour les transforme en opérations équivalentes — une **Conversion** pour le type
de données, une **Conversion de date** pour les paramètres de date/heure, puis les opérations de l'expression :
`value.trim().toUpperCase()` devient **Supprimer les espaces** puis **Majuscules**, `Math.round(value * 100) / 100` un
**Arrondi** à 2 décimales, `'plant.' + value` un **Ajout de texte**... Une expression faisant ce qu'aucune opération ne
fait (par exemple `value.split('/').pop()`) est supprimée, avec un avertissement dans les journaux : vérifiez le
traitement du champ après la mise à jour.

##### Exemple — Enregistrements de points dans un fichier CSV {#example}

**Entrée (éléments OPC UA : temp1, pressure1)**

```json
[
  { "pointId": "plant/temp1", "timestamp": "2024-01-15T10:00:00.000Z", "value": 23.5, "quality": "Good" },
  { "pointId": "plant/pressure1", "timestamp": "2024-01-15T10:00:00.000Z", "value": 102.1, "quality": "Good" }
]
```

Avec le type de fichier `CSV`, le délimiteur `SEMI_COLON`, **Conserver les autres champs** désactivé, et trois champs :
`pointId` (nom écrit `Reference`, traitement du champ : un remplacement de `plant/` par rien), `timestamp` (nom écrit
`Timestamp`, traitement du champ : une conversion de date de `iso-string` vers `string` avec le format
`yyyy-MM-dd HH:mm:ss` et le fuseau horaire `Europe/Paris`) et `value` (nom écrit `Value`) :

**CSV en sortie** — `quality` n'est pas écrit

```csv
Reference;Timestamp;Value
temp1;2024-01-15 11:00:00;23.5
pressure1;2024-01-15 11:00:00;102.1
```

##### Exemple — Lignes de requête dans un fichier CSV {#example-7}

**Entrée** (liste d'enregistrements provenant d'un élément MySQL)

```json
[
  { "deviceId": "sensor-1", "readingTime": "2024-01-15T10:00:00.000Z", "value": 23.5 },
  { "deviceId": "sensor-1", "readingTime": "2024-01-15T10:01:00.000Z", "value": 23.8 }
]
```

Avec le type de fichier `CSV` et un seul champ configuré (`readingTime`, traitement du champ : une conversion de date de
`iso-string` vers `string` avec le format `yyyy-MM-dd HH:mm:ss` et le fuseau horaire `Europe/Paris`) — `deviceId` et
`value` ne sont pas configurés, ils passent donc inchangés :

**CSV en sortie**

```csv
deviceId,value,readingTime
sensor-1,23.5,2024-01-15 11:00:00
sensor-1,23.8,2024-01-15 11:01:00
```

##### Exemple — Enregistrements tels quels {#example-1}

Avec les paramètres par défaut, les enregistrements (enregistrements de points d'un connecteur South OPC UA ou Modbus,
ou lignes d'une requête SQL) sont enregistrés inchangés sous forme de fichier `.json`.

#### Charges utiles MQTT {#mqtt-payloads}

Associe chaque enregistrement à un message MQTT via une table de correspondance **identifiant de point → topic**. Les
enregistrements dont l'identifiant de point n'a pas de correspondance sont silencieusement rejetés. La charge utile est
l'enregistrement sans sa colonne de point, sous forme de chaîne JSON, ou la valeur seule.

##### Paramètres {#settings-1}

| Paramètre               | Description                                                                                                                                                                  |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Colonne ID du point** | Champ des enregistrements contenant l'identifiant de point (par défaut `pointId`)                                                                                            |
| **Contenu**             | **Enregistrement** : l'enregistrement sans sa colonne de point, en JSON (par défaut). **Valeur** : la colonne de valeur seule, le texte tel quel, les autres valeurs en JSON |
| **Colonne de valeur**   | Champ des enregistrements contenant la valeur, avec le contenu **Valeur** (par défaut `value`)                                                                               |
| **Table de mappage**    | Liste de paires `{ pointId, topic }`                                                                                                                                         |

##### Exemple {#example-2}

Table de mappage : `plant/temp1 → sensors/temperature`, `plant/pressure1 → sensors/pressure`

**Entrée**

```json
[
  { "pointId": "plant/temp1", "timestamp": "2024-01-15T10:00:00.000Z", "value": "23.5" },
  { "pointId": "plant/pressure1", "timestamp": "2024-01-15T10:00:00.000Z", "value": "102.1" },
  { "pointId": "plant/unknown", "timestamp": "2024-01-15T10:00:00.000Z", "value": "0" }
]
```

**Sortie** — `plant/unknown` est rejeté (pas de correspondance)

```json
[
  { "topic": "sensors/temperature", "payload": "{\"timestamp\":\"2024-01-15T10:00:00.000Z\",\"value\":\"23.5\"}" },
  { "topic": "sensors/pressure", "payload": "{\"timestamp\":\"2024-01-15T10:00:00.000Z\",\"value\":\"102.1\"}" }
]
```

#### Valeurs Modbus {#modbus-values}

Associe chaque enregistrement à une commande d'écriture Modbus via une table de correspondance **identifiant de point →
adresse**. La valeur est convertie vers le type approprié (voir
[Conversion des valeurs Modbus](#modbus-value-conversion)). Les enregistrements sans correspondance sont rejetés.

##### Conversion des valeurs Modbus {#modbus-value-conversion}

Les booléens, les nombres et leurs formes textuelles (`true`, `false`, `1`, `0`, `12.5`...) sont acceptés. Une bobine
(coil) est activée pour `true` ou tout nombre non nul, et désactivée pour `false` ou `0`. Un registre reçoit la partie
entière du nombre (`12.7` → `12`), et `1` / `0` pour `true` / `false`. Toute autre valeur (par exemple `on`, un texte
vide) est ignorée avec un avertissement.

##### Paramètres {#settings-2}

| Paramètre               | Description                                                                                |
| ----------------------- | ------------------------------------------------------------------------------------------ |
| **Colonne ID du point** | Champ des enregistrements contenant l'identifiant de point (par défaut `pointId`)          |
| **Colonne de valeur**   | Champ des enregistrements contenant la valeur à écrire (par défaut `value`)                |
| **Table de mappage**    | Liste de triplets `{ pointId, address, modbusType }` (`modbusType` : `coil` ou `register`) |

##### Exemple {#example-3}

Table de mappage : `plant/valve1 → 0x0010 (coil)`, `plant/speed → 0x0020 (register)`

**Entrée**

```json
[
  { "pointId": "plant/valve1", "timestamp": "2024-01-15T10:00:00.000Z", "value": "true" },
  { "pointId": "plant/speed", "timestamp": "2024-01-15T10:00:00.000Z", "value": "1450" }
]
```

**Sortie**

```json
[
  { "address": "0x0010", "value": true, "modbusType": "coil" },
  { "address": "0x0020", "value": 1450, "modbusType": "register" }
]
```

#### Charge utile OIAnalytics {#oianalytics-payload}

Prépare les enregistrements pour le connecteur North OIAnalytics, qui en a besoin pour recevoir des listes
d'enregistrements. Seuls l'identifiant de point, l'horodatage et la valeur de chaque enregistrement sont transmis — les
champs supplémentaires comme la qualité sont supprimés — et les horodatages peuvent être arrondis à une précision
inférieure par une conversion de date, pour réduire l'empreinte de stockage. Pour économiser de la bande passante, les
valeurs sont écrites au **format compact** d'OIAnalytics : trois tableaux parallèles de même taille (`timestamps`,
`values`, `references`), la i-ème valeur étant constituée du i-ème élément de chaque tableau.

Les enregistrements sans identifiant de point, sans valeur ou sans horodatage valide sont ignorés, avec un seul
avertissement par lot. Une colonne de date retournée par un pilote de base de données sous forme d'objet date est un
instant, quel que soit le type d'entrée d'une conversion de date ; les autres horodatages doivent être des dates/heures
ISO une fois traités.

##### Paramètres {#settings-3}

Les paramètres sont regroupés par partie de la charge utile OIAnalytics.

| Groupe         | Paramètre                      | Description                                                                                                                                                                                                                                                                                              |
| -------------- | ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Référence**  | **Champ de la référence**      | Champ des enregistrements contenant la référence (par défaut `pointId`)                                                                                                                                                                                                                                  |
|                | **Traitement de la référence** | Opérations facultatives appliquées à chaque référence (par exemple Remplacer du texte `plant/` par rien, puis Majuscules), voir [Traitements des champs et des valeurs](#field-processes)                                                                                                                |
| **Horodatage** | **Champ de l'horodatage**      | Champ des enregistrements contenant l'horodatage (par défaut `timestamp`)                                                                                                                                                                                                                                |
|                | **Traitement de l'horodatage** | Opérations facultatives appliquées à chaque horodatage, qui doivent donner une date/heure ISO (par exemple une Conversion de date de `unix-epoch-ms` vers `iso-string`, arrondie à la seconde inférieure par sa **Précision**) — aucune pour un horodatage ISO, comme dans les enregistrements de points |
| **Valeur**     | **Champ de la valeur**         | Champ des enregistrements contenant la valeur (par défaut `value`)                                                                                                                                                                                                                                       |
|                | **Traitement de la valeur**    | Opérations facultatives appliquées à chaque valeur (par exemple Arrondir à 2 décimales), voir [Traitements des champs et des valeurs](#field-processes)                                                                                                                                                  |

Avant la 3.10, les paramètres n'étaient pas regroupés : la mise à jour les déplace dans leur groupe, sans traitement de
la valeur. Un type de source de l'horodatage autre que `iso-string` (avec son fuseau horaire, son format et ses
paramètres régionaux) devient une conversion de date vers `iso-string` dans le traitement de l'horodatage, et une
précision autre que `ms` devient la **Précision** de cette conversion (d'une conversion de `iso-string` vers
`iso-string` ajoutée à cet effet, pour un horodatage ISO).

##### Exemple — Précision `s` {#example--precision-s}

Traitement de l'horodatage : une conversion de date de `iso-string` vers `iso-string`, avec la précision **Seconde**.

**Entrée**

```json
[{ "pointId": "tag/temp1", "timestamp": "2024-01-15T10:00:00.523Z", "value": "23.5", "quality": "good" }]
```

**Sortie** — les millisecondes sont mises à zéro, `quality` est supprimé

```json
{ "timestamps": ["2024-01-15T10:00:00.000Z"], "values": ["23.5"], "references": ["tag/temp1"] }
```

##### Exemple — Lignes de requête {#example--query-rows}

**Entrée** (liste d'enregistrements provenant d'un élément PostgreSQL), avec le champ de la référence `deviceId`, le
champ de l'horodatage `readingTime` (traitement de l'horodatage : une conversion de date de `string` — format
`yyyy-MM-dd HH:mm:ss`, fuseau horaire `Europe/Paris` — vers `iso-string`) et le champ de la valeur `reading` :

```json
[{ "deviceId": "sensor-1", "readingTime": "2024-01-15 11:00:00", "reading": 23.5 }]
```

**Sortie**

```json
{ "timestamps": ["2024-01-15T10:00:00.000Z"], "values": [23.5], "references": ["sensor-1"] }
```

#### Valeurs OPCUA {#opcua-values}

Associe chaque enregistrement à une commande d'écriture OPC UA via une table de correspondance **identifiant de point →
node ID**. La valeur est transmise telle quelle. Les enregistrements sans correspondance, ou sans valeur, sont rejetés.

##### Paramètres {#settings-4}

| Paramètre               | Description                                                                       |
| ----------------------- | --------------------------------------------------------------------------------- |
| **Colonne ID du point** | Champ des enregistrements contenant l'identifiant de point (par défaut `pointId`) |
| **Colonne de valeur**   | Champ des enregistrements contenant la valeur à écrire (par défaut `value`)       |
| **Table de mappage**    | Liste de paires `{ pointId, nodeId }`                                             |

##### Exemple {#example-4}

Table de mappage : `plant/temp1 → ns=1;s=Temperature`, `plant/valve1 → ns=1;s=Valve1`

**Entrée**

```json
[
  { "pointId": "plant/temp1", "timestamp": "2024-01-15T10:00:00.000Z", "value": "23.5" },
  { "pointId": "plant/valve1", "timestamp": "2024-01-15T10:00:00.000Z", "value": "true" }
]
```

**Sortie**

```json
[
  { "nodeId": "ns=1;s=Temperature", "value": "23.5" },
  { "nodeId": "ns=1;s=Valve1", "value": "true" }
]
```

### Pour les connecteurs South fichier {#for-file-and-query-based-south-connectors}

Ces transformateurs traitent des fichiers ou des charges utiles JSON produits par des connecteurs tels que MQTT, REST,
SFTP, FTP, Folder Scanner et OIAnalytics, ainsi que des données injectées via l'**API OIBus**.

#### Lecture du fichier {#reading-the-file}

Les transformateurs de fichiers lisent d'abord les lignes du fichier (sauf les fichiers de type **Tout fichier** de
[Fichier (tel quel, renommé ou converti)](#file-as-is-renamed-or-converted)), avec les paramètres de leur groupe
**Fichier** :

| Paramètre                            | Description                                                                                                                     |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| **Type de fichier**                  | `CSV` ou `JSON`                                                                                                                 |
| **Délimiteur CSV**                   | Séparateur de colonnes (`COMMA`, `SEMI_COLON`, `TAB`, etc.), pour un fichier CSV                                                |
| **Comporte un en-tête**              | Indique si la première ligne d'un fichier CSV est un en-tête                                                                    |
| **JSONPath de l'itérateur de ligne** | JSONPath correspondant aux lignes d'un fichier JSON (par défaut `$[*]`, chaque élément du tableau racine), pour un fichier JSON |

Les autres paramètres lisent ensuite des **champs** de chaque ligne :

- dans un fichier **CSV**, un champ est une colonne : son nom dans l'en-tête, ou son index à partir de `0` sans
  en-tête. Les nombres et les booléens sont typés.
- dans un fichier **JSON**, un champ est une propriété de la ligne (par exemple `value`), ou un **JSONPath** de
  l'ensemble du fichier commençant par `$`, dont les jokers (`[*]`) sont résolus selon la ligne (par exemple
  `$.metrics[*].value` pour la ligne `$.metrics[2]`). Un JSONPath lit aussi une valeur partagée par toutes les lignes
  (par exemple `$.site`). Un objet ou un tableau est lu sous forme de son texte JSON.

:::info Chaînes JSON imbriquées
Un JSONPath (y compris l'itérateur de ligne) analyse automatiquement des nœuds intermédiaires sérialisés en JSON — par
exemple un connecteur South MQTT dont les messages transportent une charge utile JSON sous forme de chaîne brute. Si un
segment de chemin résout vers une chaîne contenant elle-même du JSON, le reste du chemin est résolu par rapport à la
valeur analysée. L'itérateur de ligne peut traverser cette frontière de chaîne et produire quand même une ligne par
correspondance imbriquée, de sorte qu'un seul message contenant plusieurs lectures se divise en plusieurs lignes. Voir
l'exemple [Charge utile OIAnalytics](#oianalytics-payload-from-file) ci-dessous pour un cas détaillé.
:::

Avant la 3.10, les fichiers CSV et JSON avaient leurs propres transformateurs (Valeurs temporelles et Charges utiles
MQTT depuis CSV, OIAnalytics depuis JSON) : la mise à jour les remplace par les transformateurs de fichiers ci-dessous,
en conservant leurs paramètres.

#### Enregistrements {#records-from-file}

Envoie les lignes du fichier sous forme d'enregistrements, avec tous leurs champs, aux connecteurs North qui acceptent
des listes d'enregistrements (Console). Ses seuls paramètres sont ceux du [groupe Fichier](#reading-the-file).

##### Exemple {#example-5}

**CSV en entrée** (récupéré par un élément REST), lu avec un délimiteur `COMMA` et un en-tête

```csv
SensorID,Timestamp,Reading
tag/temp1,2024-01-15T10:00:00.000Z,23.5
tag/pressure1,2024-01-15T10:00:00.000Z,102.1
```

**Sortie (enregistrements)**

```json
[
  { "SensorID": "tag/temp1", "Timestamp": "2024-01-15T10:00:00.000Z", "Reading": 23.5 },
  { "SensorID": "tag/pressure1", "Timestamp": "2024-01-15T10:00:00.000Z", "Reading": 102.1 }
]
```

#### Charges utiles MQTT {#mqtt-payloads-from-file}

Convertit chaque ligne du fichier en un message MQTT avec un topic et une charge utile. Deux modes de charge utile sont
pris en charge :

- **Simple** — un seul champ devient la charge utile, convertie vers le type configuré.
- **Objet** — plusieurs champs sont assemblés en une charge utile objet JSON.

Les lignes sans topic ou sans charge utile sont ignorées.

##### Paramètres {#settings-6}

Après le [groupe Fichier](#reading-the-file) :

| Paramètre                   | Description                                                                                                                                                                 |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Champ du sujet**          | Champ contenant le topic MQTT                                                                                                                                               |
| **Type de charge utile**    | `value` (un champ) ou `object` (plusieurs champs)                                                                                                                           |
| **Champ de valeur**         | Champ contenant la charge utile (charge utile `value`)                                                                                                                      |
| **Traitement de la valeur** | Opérations facultatives appliquées à la valeur, voir [Traitements des champs et des valeurs](#field-processes) — la charge utile est la valeur traitée, sous forme de texte |
| **Champs objet**            | Liste de correspondances `{ key, field }` (charge utile `object`), chacune avec son propre **Traitement du champ** (par exemple Convertir en nombre)                        |

Avant la 3.10, le type de charge utile typait aussi une charge utile simple (`string`, `number`, `boolean` ou
`datetime`, avec des paramètres de date/heure), et les champs objet avaient un type de données : la mise à jour les
transforme en une charge utile `value` et des champs objet avec les opérations équivalentes.

##### Exemple — Charge utile simple {#example--simple-payload}

**CSV en entrée**

```csv
topic,value
plant/pump1/speed,1450
plant/pump1/running,true
```

**Sortie (messages MQTT)**

```json
[
  { "topic": "plant/pump1/speed", "payload": "1450" },
  { "topic": "plant/pump1/running", "payload": "true" }
]
```

##### Exemple — Charge utile objet depuis du JSON {#example--object-payload}

**JSON en entrée**

```json
{
  "site": "plant",
  "sensors": [
    { "topic": "plant/sensor1", "value": 23.5, "quality": "good" },
    { "topic": "plant/sensor2", "value": 48.0, "quality": "good" }
  ]
}
```

Configuration : itérateur de ligne `$.sensors[*]`, champ du sujet `topic`, champs objet `value → value` (converti en
nombre), `quality → quality` et `site → $.site`

**Sortie (messages MQTT)**

```json
[
  { "topic": "plant/sensor1", "payload": "{\"value\":23.5,\"quality\":\"good\",\"site\":\"plant\"}" },
  { "topic": "plant/sensor2", "payload": "{\"value\":48,\"quality\":\"good\",\"site\":\"plant\"}" }
]
```

#### Valeurs Modbus {#modbus-values-from-file}

Écrit les valeurs des lignes du fichier vers un connecteur North Modbus, comme le transformateur
[Valeurs Modbus](#modbus-values) des listes d'enregistrements : après le [groupe Fichier](#reading-the-file), ses
paramètres sont les mêmes (colonnes d'identifiant de point et de valeur, et la table de correspondance **identifiant de
point → adresse**), les colonnes étant des champs des lignes du fichier.

##### Exemple {#example--modbus-values-from-a-csv-file}

**CSV en entrée**, lu avec un délimiteur `SEMI_COLON` et un en-tête

```csv
tag;setpoint
pump1/speed;1450
valve1/open;true
```

Avec la colonne ID du point `tag`, la colonne de valeur `setpoint`, et la table de mappage
`pump1/speed → 0x0010 (register)`, `valve1/open → 0x0001 (coil)` :

**Sortie**

```json
[
  { "address": "0x0010", "value": 1450, "modbusType": "register" },
  { "address": "0x0001", "value": true, "modbusType": "coil" }
]
```

#### Valeurs OPCUA {#opcua-values-from-file}

Écrit les valeurs des lignes du fichier vers un connecteur North OPC UA, comme le transformateur
[Valeurs OPCUA](#opcua-values) des listes d'enregistrements : après le [groupe Fichier](#reading-the-file), ses
paramètres sont les mêmes (colonnes d'identifiant de point et de valeur, et la table de correspondance **identifiant de
point → node ID**), les colonnes étant des champs des lignes du fichier.

##### Exemple {#example--opcua-values-from-a-json-file}

**JSON en entrée**

```json
{ "setpoints": [{ "tag": "valve1", "data": { "value": true } }] }
```

Avec l'itérateur de ligne `$.setpoints[*]`, la colonne ID du point `tag`, la colonne de valeur
`$.setpoints[*].data.value`, et la table de mappage `valve1 → ns=1;s=Valve1` :

**Sortie**

```json
[{ "nodeId": "ns=1;s=Valve1", "value": true }]
```

#### Fichier (tel quel, renommé ou converti) {#file-as-is-renamed-or-converted}

Par défaut (type de fichier **Tout fichier**, nom de fichier `@SourceFilename@SourceExtension`), envoie les fichiers tels
quels, en conservant leur nom, à un connecteur North attendant des fichiers (Azure Blob, Amazon S3, SFTP, REST, File
Writer, OIAnalytics...) : le connecteur North les copie dans son cache sans les lire. Un fichier d'un sous-dossier du
Folder Scanner conserve son dossier, et les charges utiles JSON du connecteur South MQTT et de l'API OIBus, qui n'ont
pas de nom, sont enregistrées sous forme de fichiers `.json` avec un nom aléatoire.

Avec le type de fichier **Tout fichier**, le fichier est seulement **renommé**, et éventuellement **compressé** (**Compresser
le fichier**, gzip, en ajoutant `.gz` à son nom) : son contenu est sinon envoyé tel quel. Modifier le contenu d'un tel
fichier nécessite un [transformateur personnalisé](#custom-transformers).

Avec le type de fichier **CSV** ou **JSON**, il convertit le fichier en un fichier CSV ou JSON — CSV vers JSON, JSON
vers CSV, ou vers un autre format CSV ou JSON — en renommant, en convertissant et en traitant les champs de ses lignes.
Après le [groupe Fichier](#reading-the-file), ses paramètres sont le
[groupe Fichier écrit, le Nom du fichier, Conserver les autres champs et les Champs](#settings) du transformateur
[Fichier](#file-from-records) des listes d'enregistrements, les champs étant lus dans les lignes du fichier (un
JSONPath pour un fichier JSON, voir [Lecture du fichier](#reading-the-file)).

En plus des variables des listes d'enregistrements, le **Nom du fichier** prend en charge `@SourceFilename` et
`@SourceExtension` : le nom (sans extension) et l'extension (avec son point) du fichier transformé, par exemple
`@SourceFilename_copy@SourceExtension`.

Avant la 3.10, les fichiers JSON avaient leur propre transformateur vers CSV (CSV depuis JSON), et les fichiers étaient
envoyés tels quels par le transformateur **Fichier (tel quel)** : la mise à jour les remplace par celui-ci, en
conservant les paramètres du premier, le second envoyant les fichiers tels quels.

##### Exemple — JSON vers CSV {#example-6}

Un connecteur South REST récupère un rapport JSON depuis une API, reformaté pour un connecteur North File Writer.

**JSON en entrée** (retourné par l'élément REST)

```json
{
  "data": [
    { "ts": "2024-01-15T10:00:00.000Z", "tag": "temp1", "val": 23.5, "ok": true },
    { "ts": "2024-01-15T10:01:00.000Z", "tag": "temp1", "val": 23.8, "ok": true },
    { "ts": "2024-01-15T10:00:00.000Z", "tag": "pressure1", "val": 102.1, "ok": false }
  ]
}
```

Configuration :

- Type de fichier `JSON`, JSONPath de l'itérateur de ligne `$.data[*]`
- Type du fichier écrit `CSV`, nom du fichier `@SourceFilename.csv`, **Conserver les autres champs** désactivé
- Champs : `ts` (nom écrit `Timestamp`, une conversion de date), `tag` (`Tag`), `val` (`Value`, converti en nombre),
  `ok` (`OK`, converti en booléen)

**CSV en sortie**

```csv
Timestamp,Tag,Value,OK
2024-01-15T10:00:00.000Z,temp1,23.5,true
2024-01-15T10:01:00.000Z,temp1,23.8,true
2024-01-15T10:00:00.000Z,pressure1,102.1,false
```

##### Exemple — Renommer un fichier {#example--renaming-a-file}

Avec le type de fichier `Tout fichier` et le nom de fichier `@SourceFilename_@CurrentDate@SourceExtension`, un fichier
`report.pdf` est envoyé inchangé sous le nom `report_2024_01_15_10_00_00_000.pdf`.

#### Charge utile OIAnalytics {#oianalytics-payload-from-file}

Envoie les lignes du fichier à un connecteur North OIAnalytics, au format compact d'OIAnalytics (tableaux parallèles
`timestamps`, `values` et `references`), comme le transformateur [Charge utile OIAnalytics](#oianalytics-payload) des
listes d'enregistrements. Après le [groupe Fichier](#reading-the-file), ses paramètres sont les mêmes : les
[groupes Référence, Horodatage et Valeur](#settings-3), dont les champs sont lus dans les lignes du fichier.

C'est le transformateur à privilégier lorsqu'un connecteur South (typiquement MQTT, REST ou Folder Scanner) fournit un
fichier CSV ou JSON et que vous souhaitez l'envoyer directement à un connecteur North OIAnalytics sans écrire de
transformateur personnalisé. Les lignes sans référence, sans valeur ou sans horodatage valide sont ignorées, avec un
seul avertissement par fichier.

##### Exemple — Messages MQTT avec une charge utile sérialisée en JSON {#example--mqtt-messages-with-a-json-stringified-payload}

Un connecteur South MQTT fournit chaque message sous la forme `{ message, timestamp, item }`, où `message` est la
**chaîne de charge utile MQTT brute**. Un seul message peut transporter plusieurs métriques ; l'itérateur de ligne
utilise donc **deux** jokers — l'un pour le tableau externe de messages, l'autre pour les métriques à l'intérieur de la
charge utile (sérialisée en JSON) de chaque message — et produit une ligne par métrique, qu'un message donné contienne
une seule lecture ou plusieurs.

**Entrée** — le premier message transporte deux métriques, le second en transporte une

```json
[
  {
    "message": "{\"metrics\":[{\"name\":\"PLANT.UNIT1.TANK3.LEVEL\",\"value\":52.2936,\"timestamp\":\"2026-07-16T08:50:18.808Z\"},{\"name\":\"PLANT.UNIT1.TANK3.TEMP\",\"value\":18.4,\"timestamp\":\"2026-07-16T08:50:19.001Z\"}]}"
  },
  { "message": "{\"metrics\":[{\"name\":\"PLANT.UNIT2.PUMP1.SPEED\",\"value\":1450,\"timestamp\":\"2026-07-16T08:50:20.500Z\"}]}" }
]
```

Configuration :

- Type de fichier : `JSON`, JSONPath de l'itérateur de ligne : `$[*].message.metrics[*]`
- Champ de la référence : `name`
- Champ de l'horodatage : `timestamp`, aucun traitement de l'horodatage (horodatages ISO, inchangés)
- Champ de la valeur : `value`

Le premier `[*]` parcourt le tableau externe de messages ; le second traverse la frontière de la chaîne `message`
(analysée automatiquement) pour parcourir les métriques qu'elle contient, chaque métrique étant une ligne dont les
propriétés sont ses champs. La même configuration gère aussi bien un message à métrique unique qu'un message à
métriques multiples.

**Sortie** — trois lignes : deux issues du premier message, une du second

```json
{
  "timestamps": ["2026-07-16T08:50:18.808Z", "2026-07-16T08:50:19.001Z", "2026-07-16T08:50:20.500Z"],
  "values": [52.2936, 18.4, 1450],
  "references": ["PLANT.UNIT1.TANK3.LEVEL", "PLANT.UNIT1.TANK3.TEMP", "PLANT.UNIT2.PUMP1.SPEED"]
}
```

### Pour les consignes OIAnalytics {#for-oianalytics-setpoints}

Les commandes d'écriture (write-back) envoyées par OIAnalytics sont des listes d'enregistrements : chaque consigne est
un enregistrement avec sa référence et sa valeur.

```json
[
  { "reference": "pump1/setSpeed", "value": 1200 },
  { "reference": "valve2/open", "value": true }
]
```

Elles passent par les [transformateurs des listes d'enregistrements](#for-record-list-south-connectors), en lisant
l'identifiant de point dans la colonne `reference` et la valeur dans la colonne `value` : [Fichier](#file-from-records)
les écrit dans un fichier JSON (par exemple pour la Console), [Charges utiles MQTT](#mqtt-payloads) avec le contenu
**Valeur** publie chaque valeur seule, [Valeurs Modbus](#modbus-values) et [Valeurs OPCUA](#opcua-values) les écrivent
dans les bobines, registres ou nœuds correspondants.

Par exemple, [Charges utiles MQTT](#mqtt-payloads) avec la colonne ID du point `reference`, le contenu **Valeur**, la
colonne de valeur `value` et la table de mappage `pump1/setSpeed → control/pump1/speed` publie les consignes ci-dessus
ainsi (`valve2/open` n'ayant pas de correspondance) :

```json
[{ "topic": "control/pump1/speed", "payload": "1200" }]
```

:::info Transformateurs de consignes depuis OIBus 3.9
Le type de données `setpoint` n'existe plus. Lors de la mise à jour, les transformateurs de consignes JSON, Charges
utiles MQTT, Valeurs Modbus et Valeurs OPCUA sont remplacés par leurs équivalents pour les listes d'enregistrements,
leur table de mappage conservant ses références comme identifiants de point (celui des charges utiles MQTT publiant la
valeur seule, comme auparavant). Les transformateurs personnalisés prenant ou produisant des consignes ont été basculés
vers `record-list` : les enregistrements qu'ils lisent ou écrivent conservent la forme `{ reference, value }`.
:::

## Tester un transformateur sur un élément South réel {#testing-a-transformer-against-a-real-south-item}

Au-delà du test isolé du code d'un transformateur personnalisé (voir ci-dessous), vous pouvez prévisualiser
n'importe quel transformateur — standard ou personnalisé — de bout en bout sur des données réelles, fraîchement
collectées, depuis le panneau de test de l'étape **Paramètres** de la fenêtre de l'élément (décrit dans
[Tester un élément](../south-connectors/common-settings.md#testing-an-item)) :

1. Choisissez l'un des connecteurs North associés à l'élément (ou, pour un élément de requête d'historique,
   directement l'un des transformateurs propres à la requête).
2. Choisissez l'un des transformateurs configurés de ce North et ajustez ses options pour cette exécution de test
   uniquement — la configuration enregistrée n'est pas modifiée.
3. Lancez le test. La fenêtre affiche le pipeline complet : **Résultat brut → Transformateur (+ options) → Sortie du
   transformateur**, ce qui vous permet de valider un transformateur sur les données réelles de l'élément avant
   qu'elles n'atteignent le cache du North.

Le transformateur est exécuté avec l'élément testé comme source : les variables `@ConnectorName` (le connecteur South,
ou la requête d'historique) et `@ItemName` de son **Nom du fichier** sont remplacées comme elles le seront à
l'exécution, et l'élément doit être sélectionné pour lancer le test.

La sortie transformée est affichée avec le nom de son fichier, et peut être présentée sous forme de **Tableau** (un
fichier CSV, ou un tableau JSON d'objets), de **JSON** ou de contenu **Brut**. La première vue disponible dans cet ordre
est affichée par défaut.

Seuls les transformateurs de ce North appliqués à l'élément testé sont listés : ceux du connecteur South de l'élément,
ciblant tous ses éléments ou une sélection qui le contient. Pour les connecteurs fichier (Folder Scanner, FTP, SFTP),
le résultat brut liste les fichiers correspondants ; lorsqu'un transformateur est sélectionné, il s'exécute sur le
contenu du fichier correspondant le plus récent, comme il le ferait à l'exécution.

## Transformateurs personnalisés {#custom-transformers}

Lorsqu'aucun transformateur standard ne convient à votre cas d'usage, vous pouvez écrire un **transformateur
personnalisé** en JavaScript ou TypeScript. Le code personnalisé s'exécute dans un bac à sable (sandbox) isolé et
sécurisé, sans accès au système de fichiers de l'hôte, aux modules Node.js, ni au réseau.

Les transformateurs personnalisés sont créés dans la page **Moteur → Transformateurs** et sont ensuite disponibles dans
la liste de sélection des transformateurs de tout connecteur North. Leur **type d'entrée** est `file` (fichiers et
charges utiles) ou `record-list` (enregistrements, et consignes OIAnalytics) ; leur **type de sortie** est `file`,
`record-list`, `mqtt`, `opcua`, `modbus` ou `oianalytics`.

:::info Transformateurs personnalisés depuis OIBus 3.9
Le type de données `time-values` n'existe plus : les transformateurs personnalisés prenant ou produisant des
time-values ont été basculés vers `record-list` lors de la mise à jour. Leur code doit désormais lire et écrire des
enregistrements de points plats (`{ pointId, timestamp, value }`, par exemple `record.value`) au lieu de
`{ pointId, timestamp, data: { value } }`.
:::

### Fonction Transform {#transform-function}

Votre code doit exporter une fonction `transform` (ou un export par défaut). Elle reçoit quatre arguments et doit
retourner un objet résultat.

```typescript
/**
 * @param content  - The raw input data as a UTF-8 string (JSON, CSV, XML…)
 * @param source   - Metadata about the data source ({ type, dataSourceId, … })
 * @param filename - The original filename (or a generated ID if no file was involved)
 * @param options  - The transformer options as configured in the UI
 */
export function transform(
  content: string,
  source: object,
  filename: string,
  options: object
): { data: unknown; filename: string; numberOfElement?: number } {
  // …
}
```

| Champ de retour   | Description                                                                                                     |
| ----------------- | --------------------------------------------------------------------------------------------------------------- |
| `data`            | Le contenu écrit dans le fichier de cache (voir ci-dessous) : une chaîne, du binaire brut ou toute autre valeur |
| `filename`        | Le nom de fichier utilisé lorsque la sortie est stockée dans le cache du North                                  |
| `numberOfElement` | Nombre facultatif d'enregistrements traités, affiché dans les journaux et les métriques                         |

La sortie du transformateur est **écrite telle quelle dans le fichier de cache**, puis relue par le North selon son
type de contenu. `data` est traité selon sa nature :

| `data` retourné                                  | Stocké sous forme de            | À utiliser avec                                                  |
| ------------------------------------------------ | ------------------------------- | ---------------------------------------------------------------- |
| une **chaîne**                                   | la chaîne telle quelle (UTF-8)  | tout type de sortie — vous contrôlez le texte exact              |
| un **`Uint8Array` / `ArrayBuffer`** (binaire)    | les octets bruts, à l'identique | le type de sortie **`file`** uniquement (North fichier)          |
| toute **autre valeur** (objet, tableau, nombre…) | `JSON.stringify(data)`          | les sorties typées (`record-list`, `mqtt`, …) qui lisent du JSON |

:::caution Faire correspondre `data` au type de sortie ; garder `filename` sous forme de chaîne

- Pour les types de sortie **typés** (`record-list`, `mqtt`, `oianalytics`, `modbus`, `opcua`), le North lit le
  fichier de cache comme du **JSON** — retournez une chaîne ou un objet/tableau (qu'OIBus sérialise en JSON). Un
  retour binaire ne pourra pas être analysé.
- La sortie **binaire** (`Uint8Array`/`ArrayBuffer`) est destinée au type de sortie **`file`**, où les North fichier
  (File Writer, S3, Azure, envoi de fichiers OIAnalytics) écrivent/téléversent les octets sans modification.
- Une valeur ni chaîne ni binaire que `JSON.stringify` rejette (une structure circulaire, un `BigInt`) ou ignore (une
  fonction) fait échouer la transformation avec une erreur explicite au lieu d'être mise en cache.

`filename` **doit être une chaîne** — il devient le nom du fichier de cache et est enregistré dans les métriques du
connecteur ; retourner un objet ou un tableau à cet endroit peut donc casser la persistance des métriques. Lorsque
vous le dérivez des données d'entrée (un topic MQTT, un champ de la charge utile…), convertissez-le en chaîne et
retirez les séparateurs de chemin, ex. `` `mqtt_${String(topic).replace(/[\\/]/g, '_')}.json` ``.
:::

### Bibliothèques disponibles {#available-libraries}

Les bibliothèques suivantes sont préchargées dans le bac à sable et disponibles via `require` :

| Bibliothèque                                                           | Nom `require`   | Description                                           |
| ---------------------------------------------------------------------- | --------------- | ----------------------------------------------------- |
| **[Luxon](https://moment.github.io/luxon/)**                           | `luxon`         | Analyse, formatage et calculs sur les dates/heures    |
| **[JSONPath Plus](https://jsonpath-plus.github.io/JSONPath/docs/ts/)** | `jsonpath-plus` | Requêtes JSONPath sur des structures JSON arbitraires |
| **[PapaParse](https://www.papaparse.com/docs)**                        | `papaparse`     | Analyse et sérialisation CSV                          |

Tout autre appel à `require` lève une erreur — `fs`, `http`, `process` et tous les modules natifs Node.js sont
bloqués.

### Journalisation {#logging}

À l'intérieur du bac à sable, `console.log`, `console.info`, `console.warn` et `console.error` sont relayés vers le
journal (logger) d'OIBus. Tous les messages apparaissent préfixés par `CUSTOM TRANSFORMER:`.

### Limites {#limits}

| Limite             | Valeur                                                                   |
| ------------------ | ------------------------------------------------------------------------ |
| Mémoire            | 256 Mo par exécution                                                     |
| Délai d'expiration | Configurable dans les paramètres du transformateur                       |
| Accès aux modules  | Uniquement `luxon`, `jsonpath-plus`, `papaparse`                         |
| Accès à l'hôte     | Aucun (système de fichiers, réseau et variables d'environnement bloqués) |

### Exemples {#examples}

#### Exemple 1 — Reformater un tableau JSON en CSV (JavaScript) {#example-1--reformat-a-json-array-to-csv-javascript}

Un connecteur South REST retourne un tableau JSON. Ce transformateur le convertit en fichier CSV délimité par des
points-virgules pour un connecteur North File Writer.

**Entrée (`content`)**

```json
[
  { "ts": "2024-01-15T10:00:00.000Z", "id": "temp1", "val": 23.5 },
  { "ts": "2024-01-15T10:01:00.000Z", "id": "temp1", "val": 23.8 },
  { "ts": "2024-01-15T10:00:00.000Z", "id": "pressure1", "val": 102.1 }
]
```

**Sortie**

```csv
Timestamp;Tag;Value
2024-01-15T10:00:00.000Z;temp1;23.5
2024-01-15T10:01:00.000Z;temp1;23.8
2024-01-15T10:00:00.000Z;pressure1;102.1
```

**Code**

```javascript
export function transform(content, source, filename, options) {
  const Papa = require('papaparse');
  const rows = JSON.parse(content);

  const csv = Papa.unparse(
    rows.map(r => ({
      Timestamp: r.ts,
      Tag: r.id,
      Value: r.val
    })),
    { delimiter: ';', header: true }
  );

  return {
    data: csv,
    filename: `export_${filename.replace('.json', '.csv')}`,
    numberOfElement: rows.length
  };
}
```

#### Exemple 2 — Filtrer et enrichir des enregistrements de points (TypeScript) {#example-2--filter-and-enrich-point-records-typescript}

Ne conserver que les lectures au-dessus d'un seuil configuré, et annoter chacune avec un champ `status` dérivé.

**Entrée (`content`)** — les enregistrements de points d'un connecteur South à points, `options.threshold = 20`

```json
[
  { "pointId": "plant/temp1", "timestamp": "2024-01-15T10:00:00.000Z", "value": "23.5" },
  { "pointId": "plant/temp2", "timestamp": "2024-01-15T10:00:00.000Z", "value": "18.0" },
  { "pointId": "plant/pressure1", "timestamp": "2024-01-15T10:00:00.000Z", "value": "102.1" }
]
```

**Sortie** — `temp2` est rejeté (18.0 ≤ 20), les autres sont annotés

```json
[
  { "pointId": "plant/temp1", "timestamp": "2024-01-15T10:00:00.000Z", "value": "23.5", "status": "NORMAL" },
  { "pointId": "plant/pressure1", "timestamp": "2024-01-15T10:00:00.000Z", "value": "102.1", "status": "HIGH" }
]
```

**Code**

```typescript
type PointRecord = { pointId: string; timestamp: string; value: string };

export function transform(
  content: string,
  _source: object,
  _filename: string,
  options: { threshold: number }
): { data: string; filename: string; numberOfElement: number } {
  const records: Array<PointRecord> = JSON.parse(content);
  const threshold = options.threshold ?? 0;

  const filtered = records
    .filter(record => parseFloat(record.value) > threshold)
    .map(record => ({
      ...record,
      status: parseFloat(record.value) > threshold * 2 ? 'HIGH' : 'NORMAL'
    }));

  console.info(`Kept ${filtered.length} / ${records.length} records above threshold ${threshold}`);

  return {
    data: JSON.stringify(filtered),
    filename: `filtered_${Date.now()}.json`,
    numberOfElement: filtered.length
  };
}
```

#### Exemple 3 — Extraire des champs d'un JSON imbriqué avec JSONPath (JavaScript) {#example-3--extract-fields-from-a-nested-json-with-jsonpath-javascript}

**Entrée (`content`)**

```json
{
  "records": [
    { "header": { "ts": "2024-01-15T10:00:00.000Z" }, "tag": "plant/temp1", "measurements": { "val": 23.5 } },
    { "header": { "ts": "2024-01-15T10:01:00.000Z" }, "tag": "plant/temp1", "measurements": { "val": 23.8 } },
    { "header": { "ts": "2024-01-15T10:00:00.000Z" }, "tag": "plant/pressure1", "measurements": { "val": 102.1 } }
  ]
}
```

**Sortie**

```json
[
  { "pointId": "plant/temp1", "timestamp": "2024-01-15T10:00:00.000Z", "value": 23.5 },
  { "pointId": "plant/temp1", "timestamp": "2024-01-15T10:01:00.000Z", "value": 23.8 },
  { "pointId": "plant/pressure1", "timestamp": "2024-01-15T10:00:00.000Z", "value": 102.1 }
]
```

**Code**

```javascript
export function transform(content, _source, _filename, _options) {
  const { JSONPath } = require('jsonpath-plus');
  const data = JSON.parse(content);

  const timestamps = JSONPath({ path: '$.records[*].header.ts', json: data });
  const tags = JSONPath({ path: '$.records[*].tag', json: data });
  const values = JSONPath({ path: '$.records[*].measurements.val', json: data });

  const records = timestamps.map((ts, i) => ({
    pointId: tags[i],
    timestamp: ts,
    value: values[i]
  }));

  return {
    data: JSON.stringify(records),
    filename: `extracted_${Date.now()}.json`,
    numberOfElement: records.length
  };
}
```

#### Exemple 4 — Conversion d'horodatage avec Luxon (JavaScript) {#example-4--timestamp-conversion-with-luxon-javascript}

Analyser des horodatages Unix epoch en millisecondes provenant d'une réponse d'API REST et les convertir en ISO-8601
dans un fuseau horaire spécifique.

**Entrée (`content`)**

```json
[
  { "id": "plant/temp1", "epoch_ms": 1705312800000, "val": 23.5 },
  { "id": "plant/pressure1", "epoch_ms": 1705312800000, "val": 102.1 }
]
```

**Sortie** — `epoch_ms` converti en ISO-8601, fuseau horaire `Europe/Paris` (UTC+1 en janvier)

```json
[
  { "id": "plant/temp1", "epoch_ms": 1705312800000, "val": 23.5, "timestamp": "2024-01-15T11:00:00.000+01:00" },
  { "id": "plant/pressure1", "epoch_ms": 1705312800000, "val": 102.1, "timestamp": "2024-01-15T11:00:00.000+01:00" }
]
```

**Code**

```javascript
export function transform(content, _source, _filename, _options) {
  const { DateTime } = require('luxon');
  const rows = JSON.parse(content);

  const converted = rows.map(row => ({
    ...row,
    timestamp: DateTime.fromMillis(row.epoch_ms, { zone: 'Europe/Paris' }).toISO()
  }));

  return {
    data: JSON.stringify(converted),
    filename: `converted_${Date.now()}.json`,
    numberOfElement: converted.length
  };
}
```

#### Exemple 5 — Normaliser des messages JSON MQTT en enregistrements (JavaScript) {#example-5--normalize-mqtt-json-messages-to-records-javascript}

Un connecteur **South MQTT** fournit chaque lot de messages reçus sous la forme d'un unique fichier JSON, conservé en
mémoire : un tableau JSON de `{ message, timestamp, item: { id, name, topic } }`, où `message` est la **chaîne de
charge utile MQTT brute**. Cette charge utile brute peut avoir n'importe quelle forme — un simple nombre, une chaîne
JSON, un objet plat ou un tableau de lectures (voir les [topics JSON](../../developer/local-test-stack.md#json-topics)
publiés par la pile de test locale). Ce transformateur normalise tous ces cas en enregistrements de points (sortie
`record-list`), en utilisant le topic comme identifiant de point.

**Entrée (`content`)** — trois messages provenant de topics différents

```json
[
  {
    "message": "{\"value\":35.17,\"unit\":\"celsius\",\"timestamp\":\"2026-06-04T08:15:06.673+00:00\",\"quality\":\"good\"}",
    "timestamp": "2026-06-04T08:15:06.700Z",
    "item": { "id": "i1", "name": "flat", "topic": "workshop1/json/flat" }
  },
  {
    "message": "44.53",
    "timestamp": "2026-06-04T08:15:06.700Z",
    "item": { "id": "i2", "name": "number", "topic": "workshop2/json/number" }
  },
  {
    "message": "[{\"timestamp\":\"2026-06-04T08:15:06.673+00:00\",\"value\":34.95},{\"timestamp\":\"2026-06-04T08:15:08.673+00:00\",\"value\":35.48}]",
    "timestamp": "2026-06-04T08:15:06.700Z",
    "item": { "id": "i3", "name": "array", "topic": "workshop1/json/array" }
  }
]
```

**Sortie** — un enregistrement de point par lecture ; le message tableau en produit deux

```json
[
  { "pointId": "workshop1/json/flat", "timestamp": "2026-06-04T08:15:06.673+00:00", "value": "35.17" },
  { "pointId": "workshop2/json/number", "timestamp": "2026-06-04T08:15:06.700Z", "value": "44.53" },
  { "pointId": "workshop1/json/array", "timestamp": "2026-06-04T08:15:06.673+00:00", "value": "34.95" },
  { "pointId": "workshop1/json/array", "timestamp": "2026-06-04T08:15:08.673+00:00", "value": "35.48" }
]
```

**Code**

```javascript
export function transform(content, _source, _filename, _options) {
  const messages = JSON.parse(content); // [{ message, timestamp, item: { topic } }, …]
  const records = [];

  // Extract a scalar value from one reading, whatever its shape.
  const toValue = reading => {
    if (reading !== null && typeof reading === 'object') {
      // Flat reading ({ value, … }); fall back to the whole object for nested shapes.
      return reading.value ?? JSON.stringify(reading);
    }
    return reading; // number, string or boolean
  };

  for (const { message, timestamp, item } of messages) {
    // The raw MQTT payload may be JSON (object/array/number/string) or plain text.
    let parsed;
    try {
      parsed = JSON.parse(message);
    } catch {
      parsed = message; // non-JSON payload: keep the raw string
    }

    const readings = Array.isArray(parsed) ? parsed : [parsed];
    for (const reading of readings) {
      records.push({
        pointId: item.topic,
        timestamp: (reading && reading.timestamp) || timestamp,
        value: String(toValue(reading))
      });
    }
  }

  return {
    data: JSON.stringify(records),
    // Always a plain string filename — never a payload object (see the caution above).
    filename: `mqtt_${Date.now()}.json`,
    numberOfElement: records.length
  };
}
```

(`flat`, `nested`, `array`, `mixed`, `string`, `number`), afin que vous puissiez y connecter un connecteur South MQTT
et éprouver un transformateur personnalisé sur chaque cas.
