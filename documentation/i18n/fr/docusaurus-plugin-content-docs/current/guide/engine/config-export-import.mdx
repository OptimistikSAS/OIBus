# Exporter / importer la configuration

OIBus peut exporter l'intégralité de sa configuration sous la forme d'un unique fichier JSON portable, puis importer
ce fichier — sur la même instance ou sur une autre — pour recréer la configuration à partir de zéro. Cela est utile
pour les sauvegardes, la reprise après sinistre, ou le clonage d'une configuration vers une nouvelle instance.

Les deux actions sont disponibles depuis **Engine > Settings**, via les boutons **Export configuration** et
**Import configuration**.

## Ce qui est exporté {#what-gets-exported}

Le fichier d'export (`oibus-config-export.json`) comporte trois champs de premier niveau :

- `oibusVersion` : la version de l'OIBus dont provient la configuration.
- `exportedAt` : la date de production du fichier, à titre informatif uniquement.
- `config` : la configuration elle-même, composée des mêmes sections que celles qu'OIBus envoie à OIAnalytics :
  - Les modes de scan
  - Les filtres IP
  - Les certificats
  - Les transformateurs
  - Les connecteurs South (y compris les éléments, les groupes et les workflows de configuration)
  - Les connecteurs North
  - Les requêtes d'historique
  - Les utilisateurs
  - Les paramètres du moteur et les paramètres d'enregistrement OIAnalytics, à titre informatif uniquement : ils ne
    sont jamais importés (voir [Enregistrement](#registration-is-not-imported) ci-dessous)

Comme `config` utilise le même format que la configuration qu'OIBus envoie à OIAnalytics, un fichier produit par
OIAnalytics à partir de la configuration qu'il détient pour un OIBus s'importe de la même manière qu'un fichier
exporté par OIBus. Son `oibusVersion` est alors la version de cet OIBus, et non celle d'OIAnalytics.

### Les secrets sont toujours retirés {#secrets-are-always-stripped}

Aucun secret n'est jamais écrit dans le fichier d'export — ni en clair, ni chiffré. Cela s'applique à tout champ de
type secret dans la configuration : identifiants des connecteurs (mots de passe, clés API, jetons), mots de passe
proxy, mot de passe de journalisation Loki, clés privées de certificats, et mots de passe utilisateurs. Un fichier
exporté peut donc être partagé ou stocké sans exposer aucun identifiant, mais cela signifie aussi que ces champs
doivent être ressaisis manuellement après un import — voir [Étapes manuelles après import](#manual-steps-after-import).

## L'import est un remplacement complet, pas une fusion {#import-is-a-full-replace-not-a-merge}

Importer un fichier de configuration **efface toutes les sections concernées de la configuration locale de
l'instance cible et les recrée à partir du fichier**, en conservant l'ID interne d'origine de chaque entité. Cette
opération est destructrice et ne peut pas être annulée : chaque connecteur South, connecteur North, requête
d'historique, workflow de configuration, mode de scan, filtre IP, transformateur, certificat et utilisateur actuellement présent sur
l'instance est supprimé avant que les éléments importés ne soient créés. L'interface exige une confirmation
explicite, rappelant ce point, avant qu'un import ne soit soumis.

Les paramètres propres au moteur et l'enregistrement OIAnalytics ne sont jamais effacés ni écrasés par un import —
voir [Enregistrement](#registration-is-not-imported).

Si le fichier téléversé est mal formé, ou est rejeté pour l'une des raisons ci-dessous, **rien n'est écrit** : l'import
est tout-ou-rien.

## Versions prises en charge {#supported-versions}

L'export de configuration est disponible à partir d'OIBus 3.10.0, mais un fichier peut contenir la configuration d'un
OIBus aussi ancien que 3.9.0 (par exemple un fichier produit par OIAnalytics). Un fichier peut être importé dans tout
OIBus au moins aussi récent que celui que désigne son `oibusVersion` :

- **Les fichiers plus récents sont rejetés** : un import est rejeté d'emblée si l'`oibusVersion` du fichier est plus
  récente que l'instance OIBus qui l'importe, car il peut contenir des paramètres que cette version ne connaît pas.
  Une pré-version est considérée comme antérieure à sa version finale (`3.10.0-beta-2` est antérieure à `3.10.0`).
- **Les fichiers antérieurs à 3.9.0 sont rejetés**, y compris ceux issus des pré-versions de 3.9.0.
- **Les fichiers plus anciens sont mis à niveau** : avant de valider le fichier, OIBus amène sa configuration de son
  `oibusVersion` au format attendu par la version qui l'importe, en appliquant dans l'ordre chaque étape de mise à
  niveau de configuration des versions intermédiaires. Ces étapes font subir à la configuration ce que les migrations
  de base de données de ces versions font subir à une installation existante. Le résultat de l'import liste chaque
  mise à niveau appliquée.

Après les mises à niveau, l'ensemble de la configuration est validé : sa structure (chaque section, entité et champ),
puis les paramètres de chaque connecteur et élément par rapport aux manifestes de connecteurs actuels. Si une
validation échoue, l'import complet est rejeté avec une liste d'erreurs par entité et, là encore, rien n'est écrit.

## Étapes manuelles après import {#manual-steps-after-import}

Comme les secrets ne sont jamais exportés, une configuration importée n'est pas immédiatement utilisable telle
quelle :

- **Les connecteurs South et North sont importés avec `enabled: false`**, quelle que soit leur valeur exportée. Leurs
  paramètres sont importés tels qu'exportés par ailleurs, mais avec chaque champ de type secret vide, de sorte que
  les laisser activés échouerait soit à se connecter avec des identifiants vides, soit — pour un protocole
  d'écriture — se connecterait avec des paramètres dépourvus de sens. Les identifiants doivent être ressaisis et
  chaque connecteur réactivé manuellement avant de pouvoir fonctionner à nouveau.
- **Les certificats sont importés sans leur clé privée.** L'entrée de certificat elle-même (nom, clé publique,
  certificat, chaîne de certificats, expiration) est recréée sous son ID d'origine afin que tout ce qui y fait
  référence continue de fonctionner, mais la clé privée doit être réimportée manuellement avant que le certificat
  puisse être utilisé pour TLS.
- **Les utilisateurs sont recréés avec un mot de passe aléatoire**, puisque les mots de passe ne sont jamais
  exportés. Chaque utilisateur importé doit réinitialiser son mot de passe avant de pouvoir se reconnecter.
- **Les workflows de configuration sont importés désactivés**, avec les éléments qu'ils ont créés toujours rattachés.
  Leur historique d'exécution n'est pas exporté. Réactivez chacun d'eux une fois son connecteur South configuré.
- **Les transformateurs standards sont mis en correspondance par nom de fonction**, et non recréés — ils sont
  initialisés une fois au démarrage d'OIBus et associés à la configuration importée via leur `functionName`. Si
  l'instance cible ne dispose pas d'un transformateur standard avec un nom de fonction correspondant (par exemple une
  version d'OIBus plus ancienne ou plus récente), les liens vers celui-ci sont ignorés et signalés sous forme
  d'avertissement. Les transformateurs personnalisés sont toujours recréés sous leur ID d'origine.

La réponse d'import (et le panneau correspondant de l'interface) liste chaque mise à niveau appliquée et chaque
avertissement soulevé pendant l'import — y compris ceux ci-dessus — de sorte que cela reste visible après la fin de
l'import plutôt que dans une notification éphémère.

### L'enregistrement n'est pas importé {#registration-is-not-imported}

Les paramètres d'enregistrement OIAnalytics sont inclus dans l'export à titre informatif/de référence uniquement.
Importer un fichier n'écrit jamais l'état d'enregistrement — enregistrer l'instance cible auprès d'OIAnalytics (ou la
réenregistrer) doit être fait manuellement, de la même façon que sur une instance neuve.
