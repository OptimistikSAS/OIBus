# 转换器

**转换器**位于数据源和北向连接器之间。它会在数据放入连接器缓存之前，将传入的数据转换为北向连接器所期望的格式。除了格式转换之外，转换器也是**过滤**北向连接器接收哪些数据的机制——详情参见[数据过滤](../north-connectors/common-settings.md#data-filtering)。

转换器是**在北向连接器上**配置的，位于其设置页面的**转换器**部分。

## 北向连接器的数据源 {#the-sources-of-a-north-connector}

转换器部分列出了每一个数据源——每个南向连接器、OIBus API 和 OIAnalytics 设定点——以及其数据所经过的转换器：当其全部数据都被发送时显示为绿色标签；当只有部分项目（或部分 OIBus API 数据源）被发送时显示为绿色描边标签（**部分发送**）；当没有任何数据被发送时显示为灰色标签（**已丢弃**）。如果一个南向连接器的所有项目都有转换器（通过其分组或其自身的转换器），则为**已发送**。没有任何标准转换器能够发送到该北向连接器的数据源同样会被丢弃：自定义转换器仍然可以发送它。您可以按到达北向连接器的内容、按南向连接器的状态或类型过滤列表，或按名称搜索数据源。

只有当 Web 服务器的[内容端点](./engine-settings.mdx#content-endpoints)已启用时才会列出 OIBus API；只有当 OIBus 已[注册](../installation/oianalytics.mdx)且允许 OIAnalytics 发送设定点时才会列出 OIAnalytics 设定点。

- 从数据源所在行**为其添加转换器**：以转换器命名的按钮可一键添加该转换器（当其默认选项有效时，即适合其数据的那个显而易见的转换器），**其他…** 则会为该数据源打开配置弹窗。
- **展开南向连接器**可查看其分组及分组中的项目，每个项目都显示其数据所经过的转换器：其自身的转换器、其分组的转换器（**来自其分组**）、所有项目的转换器（**来自所有数据项**），或**已丢弃**。在此处可以：
  - 为分组或尚无转换器的项目**添加**转换器；
  - **覆盖**项目继承的转换器：当所选的转换器和选项与另一个项目的相同时，该项目会被加入那个转换器，而不是获得自己的副本；
  - 将项目从其继承的转换器中**排除**（参见下文的**排除部分数据项**）；
  - 将项目从其自身的转换器中移除（当它是该转换器的最后一个项目时，会删除该转换器）。

从未被使用的转换器（因为列表中排在它前面的另一个转换器作用于相同的数据）会以删除线显示。

## 配置转换器 {#configuring-a-transformer}

点击转换器部分中的**添加转换器**（或数据源的某个按钮）以打开配置弹窗。与项目弹窗一样，该弹窗包含三个步骤：**数据源和转换器**（数据来自何处、转换器所应用的南向连接器项目，以及新建或复制的转换器）、**选项**（所选转换器的选项，可通过其下方的测试面板立即试用），然后是**检查并保存**（转换器将被保存的样子、自上次保存以来的更改，以及需要先修正的步骤）。新转换器可以从选项步骤保存，已编辑的转换器可以从任意步骤保存。从某个数据源（或其某个分组或项目）所在行打开时，弹窗中已设置好该数据源和范围。

### 1 — 来源 {#1--source}

选择数据的来源。

| 来源                   | 描述                                                                                     |
| ---------------------- | ---------------------------------------------------------------------------------------- |
| **南向连接器**         | 由某个已配置的南向连接器采集的数据                                                       |
| **OIBus API**          | 通过 REST API 推送到 OIBus 的数据，来自指定的**数据源 ID**，或来自所有未指定 ID 的数据源 |
| **OIAnalytics 设定点** | 从 OIAnalytics 发送的写回命令                                                            |

### 2 — 项目范围（仅限南向连接器） {#2--item-scope-south-connectors-only}

当来源为南向连接器时，您可以限制转换器所应用的项目。

| 范围       | 描述                                     |
| ---------- | ---------------------------------------- |
| **全部项** | 所选南向连接器的每个项目都会经过此转换器 |
| **按组**   | 只处理属于特定分组的项目                 |
| **特定项** | 从搜索列表中手动挑选单个项目             |

要挑选（或排除）的项目可按名称搜索，并按分组、扫描模式和状态过滤，与南向连接器的项目列表中一样。

选择**全部项**或**按组**时，勾选**排除部分数据项**即可排除少数项目：转换器会应用于南向连接器（或该分组）的所有其他项目，包括之后添加的项目。**特定项**至少需要一个项目：没有项目的转换器将应用于所有项目。

在范围下方，弹窗会根据北向连接器的其他转换器及其顺序，告知该转换器将发送多少个项目：当前有多少个被丢弃、它从其他转换器接管了多少个，以及有多少个保留了优先生效的转换器。当某个优先生效的转换器已经发送了所有选定项目时，弹窗会发出警告。

:::tip
单个北向连接器可以配置**多个转换器**，各自具有不同的来源和范围。这样您就可以对同一个南向连接器的不同部分应用不同的转换——例如，为一组温度传感器配置一个转换器，为流量计配置另一个转换器。当传入的一批数据混合了由不同转换器覆盖的项目时，OIBus 会自动将其拆分，使每一部分都由实际针对它的转换器处理。
:::

如果同一个项目可能匹配多个转换器（例如一个针对某个分组，另一个针对同一南向连接器的“全部项”），OIBus 会按照以下优先级解析，最具体的优先：

1. 针对该**特定项目**的转换器。
2. 针对该项目所属**分组**的转换器。
3. 针对该南向连接器**所有项目**（未选择分组，也未选择特定项目）的转换器——即兜底转换器。

按此顺序匹配到的第一个已配置转换器将被使用；同一层级内的并列情况按转换器在列表中的位置决定。排除了某个项目的转换器（**排除部分数据项**）对该项目会被跳过，该项目将回退到下一层级。

### 3 — 转换器 {#3--transformer}

选定来源后，列表会自动过滤，仅显示兼容的转换器，并预先选中最显而易见的那个：对于发送到接受文件的北向连接器的文件，选中**文件（原样、重命名或转换）**，按原样发送；否则选中唯一能生成该北向连接器自身格式的标准转换器（例如 OIAnalytics 值、MQTT 有效载荷）；否则选中数据的直通转换器（**文件**：CSV 文件中的记录）。可选项取决于所选南向连接器的类型：

| 南向连接器类型                                                                                                                                     | 兼容的标准转换器                                                                           |
| -------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| **OPC UA、OPC Classic、Modbus、ADS、S7、BACnet、OSIsoft PI、MySQL、PostgreSQL、MSSQL、Oracle、SQLite、MongoDB、ODBC、OLEDB、InfluxDB**（记录列表） | 文件、MQTT 有效载荷、Modbus 值、OIAnalytics 有效载荷、OPCUA 值                             |
| **MQTT、REST、SFTP、FTP、Folder Scanner、OIAnalytics**（基于文件）                                                                                 | 文件（原样、重命名或转换）、记录、MQTT 有效载荷、Modbus 值、OIAnalytics 有效载荷、OPCUA 值 |
| **OIBus API**                                                                                                                                      | 文件（原样、重命名或转换）、记录、MQTT 有效载荷、Modbus 值、OIAnalytics 有效载荷、OPCUA 值 |
| **OIAnalytics 设定点**（记录列表）                                                                                                                 | 文件、MQTT 有效载荷、Modbus 值、OIAnalytics 有效载荷、OPCUA 值                             |

此列表中还会显示自定义转换器，它们始终由用户命名。

:::info 没有转换器的数据
北向连接器会忽略未配置转换器的数据：此类数据源（及项目）在转换器部分中显示为**已丢弃**（参见[北向连接器的数据源](#the-sources-of-a-north-connector)）。
:::

选择转换器后，其设置表单会直接显示在弹窗中。

## 标准转换器 {#standard-transformers}

标准转换器是内置的，只需配置即可使用——无需编写代码。

:::info 发送到 OIAnalytics 的记录列表
OIAnalytics 北向连接器只接受文件和 OIAnalytics 值：记录列表通过 [OIAnalytics 有效载荷](#oianalytics-payload)转换器发送。升级到 3.10 时，会为每个 OIAnalytics 北向连接器针对基于点位的南向连接器（OPC UA、OPC Classic、Modbus、ADS、S7、BACnet、OSIsoft PI）和历史查询添加此转换器——此前它们的值无需转换器即可被接收。
:::

### 适用于记录列表 {#for-record-list-south-connectors}

大多数南向连接器发送**记录列表**：由扁平记录组成的数组。

- **基于点位的连接器**（OPC UA、OPC Classic、Modbus、TwinCAT ADS、Siemens S7、BACnet、OSIsoft PI）发送**点位记录**：每次读数的点位、时间戳和值，并可能根据协议带有额外字段（例如 OPC UA 的 `quality`）。

  ```json
  { "pointId": "plant/temp1", "timestamp": "2024-01-15T10:00:00.000Z", "value": 23.5, "quality": "Good" }
  ```

- **基于查询的连接器**（MySQL、PostgreSQL、MSSQL、Oracle、SQLite、MongoDB、ODBC、OLEDB、InfluxDB）按数据库返回的原样发送每一行（或每一个文档）。

  ```json
  { "deviceId": "sensor-1", "readingTime": "2024-01-15T10:00:00.000Z", "reading": 23.5 }
  ```

- **OIAnalytics 设定点**也是记录：每个设定点的引用和值（参见 [OIAnalytics 设定点](#for-oianalytics-setpoints)）。

  ```json
  { "reference": "pump1/setSpeed", "value": 1200 }
  ```

下面的转换器将记录列表渲染为北向连接器所期望的形式。需要点位、时间戳或值的转换器会从可配置的列中读取它们，这些列默认为 `pointId`、`timestamp` 和 `value`：点位记录无需修改即可使用，而对于查询行，您需要指定查询中的列名。

---

#### 文件 {#file-from-records}

将记录写入 **CSV** 或 **JSON** 文件，供需要文件的北向连接器使用（Azure Blob、Amazon S3、SFTP、REST、File Writer……）。使用默认设置时，记录会被写入 CSV 文件：这是发送到需要文件的北向连接器的记录列表所预先选中的转换器。

记录的每个字段都会被自动写入——无需仅为了让某个字段出现在输出中而声明它。只有当某个字段需要重命名、转换为特定类型、重新格式化（日期）或通过 JavaScript 表达式处理时，才需要声明字段（通过**字段**）。关闭**保留其他字段**时，只写入已配置的字段，并按其配置顺序排列。

在 3.10 之前，CSV 和 JSON 文件各有自己的转换器（CSV 和 JSON）：升级时会用此转换器替换它们，并保留其设置。

##### 设置 {#settings}

**写入的文件**分组：

| 设置               | 描述                                                                     |
| ------------------ | ------------------------------------------------------------------------ |
| **文件类型**       | `CSV`（默认）或 `JSON`                                                   |
| **编码**           | 输出字符编码（`UTF_8`、`UTF_8_BOM`、`LATIN_1`、`UTF_16_LE`）             |
| **压缩文件**       | 对输出文件进行 Gzip 压缩，并在文件名后添加 `.gz`                         |
| **第一行作为表头** | 是否写入包含列名的表头行（CSV）                                          |
| **分隔符**         | 列分隔符（`COMMA`、`SEMI_COLON`、`TAB` 等）（CSV）                       |
| **换行符**         | 行分隔符（`CRLF`、`LF`、`CR`）（CSV）                                    |
| **引号字符**       | 用于给字段加引号的字符（`DOUBLE_QUOTE`、`SINGLE_QUOTE`、`NONE`）（CSV）  |
| **转义字符**       | 用于转义带引号字段内引号字符的字符（`BACKSLASH`、`DOUBLE_QUOTE`）（CSV） |
| **空值**           | 当已配置字段为 `null` 或缺失时写出的值（CSV；JSON 文件写入 `null`）      |

然后：

| 设置             | 描述                                                                                                                                                                                                                                                  |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **文件名**       | 输出文件名（默认 `@ConnectorName-@ItemName-@QueryStartTime-@CurrentDate.csv`）；支持 `@CurrentDate`（当前 UTC 时间戳）、`@ConnectorName`、`@ItemName`，以及在内容来自南向历史查询时支持 `@QueryStartTime`/`@QueryEndTime`（查询的时间窗口，否则为空） |
| **保留其他字段** | 原样写入未在**字段**中配置的字段（默认启用）                                                                                                                                                                                                          |
| **字段**         | 按字段覆盖的列表（重命名、类型转换或处理）——见下文                                                                                                                                                                                                    |

**字段**中的每个条目通过其在记录中的名称定位一个字段：

| 设置         | 描述                                                                                     |
| ------------ | ---------------------------------------------------------------------------------------- |
| **字段**     | 要配置的字段名，与记录中的某个键相匹配                                                   |
| **写入名称** | 输出中的列名（CSV）或属性名（JSON）。留空则保留字段名。                                  |
| **字段处理** | 可选的操作（例如转换为数字、日期时间转换、大写），参见[字段和值的处理](#field-processes) |

##### 字段和值的处理 {#field-processes}

文件字段和 MQTT 有效载荷的**字段处理**，以及 OIAnalytics 有效载荷的**引用处理**、**时间戳处理**和**值处理**，都是按顺序执行的操作列表，每个操作作用于前一个操作的结果：转换（为文本、数字、布尔值，或 JSON 文本所含的对象或数组）、大写或小写、去除空格、子字符串、添加文本、替换文本、数值运算、四舍五入、日期时间转换（可按**精度**向下取整：秒、分钟、小时或天），或者对于其他任何处理，使用作用于 `value` 的 JavaScript **表达式**——与[项目同步的字段处理](../south-connectors/common-settings.md#field-processing)的操作相同。设置中按顺序显示这些操作；**设置…** 会在弹窗中打开它们，以便添加、修改、重新排序或删除。

该弹窗会在字段的值上测试这些操作：使用上一次转换器测试所运行内容中的前几个值（请先运行转换器的测试面板），这些值可以修改、添加或删除，以测试其他情况。每个值都会显示其结果，或某个操作在该值上失败的原因。

这些操作只应用于可以处理的值：

- 缺失的值（`null`）保持不变：不会被处理。在 CSV 文件中，它以**空值**写入；在 OIAnalytics 有效载荷中，该记录会被跳过；
- 操作失败的值（例如数值运算中的文本，或调用了该值所没有的方法的表达式）会被跳过，并在日志中记录一条警告，每个字段一次。在文件中该字段写为空，在 OIAnalytics 有效载荷中该记录会被跳过，而引用则保持原样。请先转换该字段（例如在数值运算之前先**转换**为数字）；
- 对象或数组（来自 JSON 文件）只能被转换，或由表达式处理；
- 没有操作的字段按读取时的原样写入：CSV 文件中的文本在 JSON 文件中仍然是文本，除非进行了转换。

在 3.10 之前，处理是 JavaScript 表达式，字段具有数据类型和日期时间设置：升级时会将它们转换为效果相同的操作——数据类型对应一个**转换**，日期时间设置对应一个**日期时间转换**，表达式则对应一个单独的**表达式**操作。

##### 示例 — CSV 文件中的点位记录 {#example}

**输入（OPC UA 项目：temp1、pressure1）**

```json
[
  { "pointId": "plant/temp1", "timestamp": "2024-01-15T10:00:00.000Z", "value": 23.5, "quality": "Good" },
  { "pointId": "plant/pressure1", "timestamp": "2024-01-15T10:00:00.000Z", "value": 102.1, "quality": "Good" }
]
```

使用文件类型 `CSV`、分隔符 `SEMI_COLON`，关闭**保留其他字段**，并配置三个字段：`pointId`（写入名称 `Reference`，字段处理：表达式 `value.split('/').pop()`）、`timestamp`（写入名称 `Timestamp`，字段处理：从 `iso-string` 到 `string` 的日期时间转换，格式为 `yyyy-MM-dd HH:mm:ss`，时区为 `Europe/Paris`）和 `value`（写入名称 `Value`）：

**输出 CSV** — 不写入 `quality`

```csv
Reference;Timestamp;Value
temp1;2024-01-15 11:00:00;23.5
pressure1;2024-01-15 11:00:00;102.1
```

##### 示例 — CSV 文件中的查询行 {#example-7}

**输入**（来自某个 MySQL 项目的记录列表）

```json
[
  { "deviceId": "sensor-1", "readingTime": "2024-01-15T10:00:00.000Z", "value": 23.5 },
  { "deviceId": "sensor-1", "readingTime": "2024-01-15T10:01:00.000Z", "value": 23.8 }
]
```

使用文件类型 `CSV`，且仅配置一个字段（`readingTime`，字段处理：从 `iso-string` 到 `string` 的日期时间转换，格式为 `yyyy-MM-dd HH:mm:ss`，时区为 `Europe/Paris`）——`deviceId` 和 `value` 未配置，因此原样透传：

**输出 CSV**

```csv
deviceId,value,readingTime
sensor-1,23.5,2024-01-15 11:00:00
sensor-1,23.8,2024-01-15 11:01:00
```

##### 示例 — 原样输出记录 {#example-1}

使用默认设置时，记录（OPC UA 或 Modbus 南向连接器的点位记录，或 SQL 查询的行）会原样保存为 `.json` 文件。

#### MQTT 有效载荷 {#mqtt-payloads}

使用**点位 ID → 主题**映射表将每条记录映射为一条 MQTT 消息。点位 ID 没有匹配项的记录会被静默丢弃。有效载荷是去掉点位列后的记录（JSON 字符串），或者仅为值。

##### 设置 {#settings-1}

| 设置           | 描述                                                                                     |
| -------------- | ---------------------------------------------------------------------------------------- |
| **点位 ID 列** | 记录中包含点位 ID 的字段（默认 `pointId`）                                               |
| **负载**       | **记录**：去掉点位列后的记录，JSON 格式（默认）。**值**：仅值列，文本原样，其他值为 JSON |
| **值列**       | 使用**值**负载时，记录中包含值的字段（默认 `value`）                                     |
| **映射表**     | `{ pointId, topic }` 对的列表                                                            |

##### 示例 {#example-2}

映射表：`plant/temp1 → sensors/temperature`，`plant/pressure1 → sensors/pressure`

**输入**

```json
[
  { "pointId": "plant/temp1", "timestamp": "2024-01-15T10:00:00.000Z", "value": "23.5" },
  { "pointId": "plant/pressure1", "timestamp": "2024-01-15T10:00:00.000Z", "value": "102.1" },
  { "pointId": "plant/unknown", "timestamp": "2024-01-15T10:00:00.000Z", "value": "0" }
]
```

**输出** — `plant/unknown` 被丢弃（无映射）

```json
[
  { "topic": "sensors/temperature", "payload": "{\"timestamp\":\"2024-01-15T10:00:00.000Z\",\"value\":\"23.5\"}" },
  { "topic": "sensors/pressure", "payload": "{\"timestamp\":\"2024-01-15T10:00:00.000Z\",\"value\":\"102.1\"}" }
]
```

#### Modbus 值 {#modbus-values}

使用**点位 ID → 地址**映射表将每条记录映射为一条 Modbus 写命令。值会被转换为相应的类型（参见 [Modbus 值转换](#modbus-value-conversion)）。没有匹配项的记录会被丢弃。

##### Modbus 值转换 {#modbus-value-conversion}

接受布尔值、数字及其文本形式（`true`、`false`、`1`、`0`、`12.5`……）。对于 `true` 或任何非零数字，线圈被置位；对于 `false` 或 `0`，线圈被清除。寄存器接收数字的整数部分（`12.7` → `12`），`true` / `false` 则对应 `1` / `0`。任何其他值（例如 `on`、空文本）都会被跳过并发出警告。

##### 设置 {#settings-2}

| 设置           | 描述                                                                            |
| -------------- | ------------------------------------------------------------------------------- |
| **点位 ID 列** | 记录中包含点位 ID 的字段（默认 `pointId`）                                      |
| **值列**       | 记录中包含要写入的值的字段（默认 `value`）                                      |
| **映射表**     | `{ pointId, address, modbusType }` 的列表（`modbusType`：`coil` 或 `register`） |

##### 示例 {#example-3}

映射表：`plant/valve1 → 0x0010 (coil)`，`plant/speed → 0x0020 (register)`

**输入**

```json
[
  { "pointId": "plant/valve1", "timestamp": "2024-01-15T10:00:00.000Z", "value": "true" },
  { "pointId": "plant/speed", "timestamp": "2024-01-15T10:00:00.000Z", "value": "1450" }
]
```

**输出**

```json
[
  { "address": "0x0010", "value": true, "modbusType": "coil" },
  { "address": "0x0020", "value": 1450, "modbusType": "register" }
]
```

#### OIAnalytics 有效载荷 {#oianalytics-payload}

为 OIAnalytics 北向连接器准备记录——该连接器需要它才能接收记录列表。只有每条记录的点位 ID、时间戳和值会被转发——质量等额外字段会被剥离——并且时间戳可以通过日期时间转换向下取整到某个精度，以减少存储占用。为了节省带宽，值以 OIAnalytics **紧凑格式**写入：三个大小相同的并行数组（`timestamps`、`values`、`references`），第 i 个值由每个数组的第 i 个元素组成。

没有点位 ID、值或有效时间戳的记录会被跳过，每批只发出一条警告。由数据库驱动以日期对象形式返回的日期列是一个时间点，与日期时间转换的输入类型无关；其他时间戳在处理后必须是 ISO 日期时间。

##### 设置 {#settings-3}

设置按 OIAnalytics 有效载荷的组成部分分组。

| 分组       | 设置           | 描述                                                                                                                                                                                      |
| ---------- | -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **引用**   | **引用字段**   | 记录中包含引用的字段（默认 `pointId`）                                                                                                                                                    |
|            | **引用处理**   | 应用于每个引用的可选操作（例如将文本 `plant/` 替换为空，然后转为大写），参见[字段和值的处理](#field-processes)                                                                            |
| **时间戳** | **时间戳字段** | 记录中包含时间戳的字段（默认 `timestamp`）                                                                                                                                                |
|            | **时间戳处理** | 应用于每个时间戳的可选操作，结果必须是 ISO 日期时间（例如从 `unix-epoch-ms` 到 `iso-string` 的日期时间转换，并通过其**精度**向下取整到秒）——对于 ISO 时间戳（如点位记录中）则无需任何操作 |
| **值**     | **值字段**     | 记录中包含值的字段（默认 `value`）                                                                                                                                                        |
|            | **值处理**     | 应用于每个值的可选操作（例如四舍五入到 2 位小数），参见[字段和值的处理](#field-processes)                                                                                                 |

在 3.10 之前，这些设置没有分组：升级时会将它们移入各自的分组，且不带值处理。除 `iso-string` 之外的时间戳源类型（及其时区、格式和区域设置）会变为时间戳处理中转换到 `iso-string` 的日期时间转换，除 `ms` 之外的精度则变为该转换的**精度**（对于 ISO 时间戳，则为此专门添加的从 `iso-string` 到 `iso-string` 的转换的精度）。

##### 示例 — 精度 `s` {#example--precision-s}

时间戳处理：从 `iso-string` 到 `iso-string` 的日期时间转换，精度为**秒**。

**输入**

```json
[{ "pointId": "tag/temp1", "timestamp": "2024-01-15T10:00:00.523Z", "value": "23.5", "quality": "good" }]
```

**输出** — 毫秒被清零，`quality` 被剥离

```json
{ "timestamps": ["2024-01-15T10:00:00.000Z"], "values": ["23.5"], "references": ["tag/temp1"] }
```

##### 示例 — 查询行 {#example--query-rows}

**输入**（来自某个 PostgreSQL 项目的记录列表），引用字段为 `deviceId`，时间戳字段为 `readingTime`（时间戳处理：从 `string`——格式 `yyyy-MM-dd HH:mm:ss`，时区 `Europe/Paris`——到 `iso-string` 的日期时间转换），值字段为 `reading`：

```json
[{ "deviceId": "sensor-1", "readingTime": "2024-01-15 11:00:00", "reading": 23.5 }]
```

**输出**

```json
{ "timestamps": ["2024-01-15T10:00:00.000Z"], "values": [23.5], "references": ["sensor-1"] }
```

### 适用于基于文件的南向连接器 {#for-file-and-query-based-south-connectors}

这些转换器处理由 MQTT、REST、SFTP、FTP、Folder Scanner 和 OIAnalytics 等连接器产生的文件或 JSON 有效载荷，以及通过 **OIBus API** 注入的数据。

#### 读取文件 {#reading-the-file}

文件转换器首先使用其**文件**分组的设置读取文件中的行（[文件（原样、重命名或转换）](#file-as-is-renamed-or-converted)的**任意文件**类型文件除外）：

| 设置                  | 描述                                                                                 |
| --------------------- | ------------------------------------------------------------------------------------ |
| **文件类型**          | `CSV` 或 `JSON`                                                                      |
| **CSV 分隔符**        | 列分隔符（`COMMA`、`SEMI_COLON`、`TAB` 等），适用于 CSV 文件                         |
| **包含表头**          | CSV 文件的第一行是否为表头                                                           |
| **行迭代器 JSONPath** | 匹配 JSON 文件中各行的 JSONPath（默认 `$[*]`，即根数组的每个元素），适用于 JSON 文件 |

其他设置随后读取每一行的**字段**：

- 在 **CSV** 文件中，字段是一列：其在表头中的名称，或在没有表头时从 `0` 开始的索引。数字和布尔值会被类型化。
- 在 **JSON** 文件中，字段是行的一个属性（例如 `value`），或以 `$` 开头、针对整个文件的 **JSONPath**，其通配符（`[*]`）会解析为当前行（例如对于行 `$.metrics[2]`，`$.metrics[*].value`）。JSONPath 也可以读取所有行共享的值（例如 `$.site`）。对象或数组会被读取为其 JSON 文本。

:::info 嵌套的 JSON 字符串
JSONPath（包括行迭代器）会自动解析被 JSON 字符串化的中间节点——例如某个 MQTT 南向连接器，其消息以原始字符串形式携带 JSON 有效载荷。如果某个路径片段解析到一个本身包含 JSON 的字符串，路径的其余部分会针对解析后的值继续解析。行迭代器可以跨越该字符串边界，并仍然为每个嵌套匹配产生一行，因此一条包含多个读数的消息会被拆分为多行。完整示例请参见下面的 [OIAnalytics 有效载荷](#oianalytics-payload-from-file)。
:::

在 3.10 之前，CSV 和 JSON 文件各有自己的转换器（来自 CSV 的时间值和 MQTT 有效载荷、来自 JSON 的 OIAnalytics）：升级时会用下面的文件转换器替换它们，并保留其设置。

#### 记录 {#records-from-file}

##### 示例 {#example-5}

**输入 CSV**（由 REST 项目获取），使用 `COMMA` 分隔符和表头读取

```csv
SensorID,Timestamp,Reading
tag/temp1,2024-01-15T10:00:00.000Z,23.5
tag/pressure1,2024-01-15T10:00:00.000Z,102.1
```

**输出（记录）**

```json
[
  { "SensorID": "tag/temp1", "Timestamp": "2024-01-15T10:00:00.000Z", "Reading": 23.5 },
  { "SensorID": "tag/pressure1", "Timestamp": "2024-01-15T10:00:00.000Z", "Reading": 102.1 }
```

#### MQTT 有效载荷 {#mqtt-payloads-from-file}

将文件中的每一行转换为一条带有主题和有效载荷的 MQTT 消息。支持两种有效载荷模式：

- **简单** — 单个字段成为有效载荷，并转换为配置的类型。
- **对象** — 多个字段被组装成一个 JSON 对象有效载荷。

没有主题或有效载荷的行会被跳过。

##### 设置 {#settings-6}

在[文件分组](#reading-the-file)之后：

| 设置             | 描述                                                                                               |
| ---------------- | -------------------------------------------------------------------------------------------------- |
| **主题字段**     | 包含 MQTT 主题的字段                                                                               |
| **有效载荷类型** | `value`（一个字段）或 `object`（多个字段）                                                         |
| **值字段**       | 包含有效载荷的字段（`value` 有效载荷）                                                             |
| **值处理**       | 应用于值的可选操作，参见[字段和值的处理](#field-processes)——有效载荷为处理后的值的文本形式         |
| **对象字段**     | `{ key, field }` 映射的列表（`object` 有效载荷），每个映射都有自己的**字段处理**（例如转换为数字） |

在 3.10 之前，有效载荷类型还会对简单有效载荷进行类型化（`string`、`number`、`boolean` 或 `datetime`，带日期时间设置），对象字段也具有数据类型：升级时会将它们转换为 `value` 有效载荷，以及带有效果相同操作的对象字段。

##### 示例 — 简单有效载荷 {#example--simple-payload}

**输入 CSV**

```csv
topic,value
plant/pump1/speed,1450
plant/pump1/running,true
```

**输出（MQTT 消息）**

```json
[
  { "topic": "plant/pump1/speed", "payload": "1450" },
  { "topic": "plant/pump1/running", "payload": "true" }
]
```

##### 示例 — 来自 JSON 的对象有效载荷 {#example--object-payload}

**输入 JSON**

```json
{
  "site": "plant",
  "sensors": [
    { "topic": "plant/sensor1", "value": 23.5, "quality": "good" },
    { "topic": "plant/sensor2", "value": 48.0, "quality": "good" }
  ]
}
```

配置：行迭代器 `$.sensors[*]`，主题字段 `topic`，对象字段 `value → value`（转换为数字）、`quality → quality` 和 `site → $.site`

**输出（MQTT 消息）**

```json
[
  { "topic": "plant/sensor1", "payload": "{\"value\":23.5,\"quality\":\"good\",\"site\":\"plant\"}" },
  { "topic": "plant/sensor2", "payload": "{\"value\":48,\"quality\":\"good\",\"site\":\"plant\"}" }
]
```

**输出**

```json
[
  { "address": "0x0010", "value": 1450, "modbusType": "register" },
  { "address": "0x0001", "value": true, "modbusType": "coil" }
]
```

#### OPCUA 值 {#opcua-values-from-file}

将文件中各行的值写入 OPC UA 北向连接器，与记录列表的 [OPCUA 值](#opcua-values)转换器相同：在[文件分组](#reading-the-file)之后，其设置相同（点位 ID 列和值列，以及**点位 ID → 节点 ID**映射表），只是这些列是文件中各行的字段。

#### 文件（原样、重命名或转换） {#file-as-is-renamed-or-converted}

默认情况下（文件类型为**任意文件**，文件名为 `@SourceFilename@SourceExtension`），按原样发送文件并保留其名称，发送到需要文件的北向连接器（Azure Blob、Amazon S3、SFTP、REST、File Writer、OIAnalytics……）：北向连接器会将文件复制到其缓存中而不读取它们。Folder Scanner 子文件夹中的文件会保留其文件夹，而 MQTT 南向连接器和 OIBus API 的 JSON 有效载荷由于没有名称，会以随机名称保存为 `.json` 文件。

当文件类型为**任意文件**时，文件只会被**重命名**，并可选择**压缩**（**压缩文件**，gzip，在文件名后添加 `.gz`）：除此之外，其内容按原样发送。要更改此类文件的内容，需要使用[自定义转换器](#custom-transformers)。

当文件类型为 **CSV** 或 **JSON** 时，它会将文件转换为 CSV 或 JSON 文件——CSV 转 JSON、JSON 转 CSV，或转换为另一种 CSV 或 JSON 格式——同时对其各行的字段进行重命名、类型转换和处理。在[文件分组](#reading-the-file)之后，其设置为记录列表的[文件](#file-from-records)转换器的[写入的文件分组、文件名、保留其他字段和字段](#settings)，字段从文件的各行中读取（对于 JSON 文件为 JSONPath，参见[读取文件](#reading-the-file)）。

除了记录列表的变量之外，**文件名**还支持 `@SourceFilename` 和 `@SourceExtension`：被转换文件的名称（不含扩展名）和扩展名（含点号），例如 `@SourceFilename_copy@SourceExtension`。

在 3.10 之前，JSON 文件有自己的转 CSV 转换器（CSV（来自 JSON）），而文件由**文件（原样）**转换器按原样发送：升级时会用此转换器替换它们，保留前者的设置，后者则按原样发送文件。

##### 示例 — JSON 转 CSV {#example-6}

REST 南向连接器从 API 获取一份 JSON 报告，并为 File Writer 北向连接器重新格式化。

**输入 JSON**（由 REST 项目返回）

```json
{
  "data": [
    { "ts": "2024-01-15T10:00:00.000Z", "tag": "temp1", "val": 23.5, "ok": true },
    { "ts": "2024-01-15T10:01:00.000Z", "tag": "temp1", "val": 23.8, "ok": true },
    { "ts": "2024-01-15T10:00:00.000Z", "tag": "pressure1", "val": 102.1, "ok": false }
  ]
}
```

配置：

- 文件类型 `JSON`，行迭代器 JSONPath `$.data[*]`
- 写入的文件类型 `CSV`，文件名 `@SourceFilename.csv`，关闭**保留其他字段**
- 字段：`ts`（写入名称 `Timestamp`，日期时间转换）、`tag`（`Tag`）、`val`（`Value`，转换为数字）、`ok`（`OK`，转换为布尔值）

**输出 CSV**

```csv
Timestamp,Tag,Value,OK
2024-01-15T10:00:00.000Z,temp1,23.5,true
2024-01-15T10:01:00.000Z,temp1,23.8,true
2024-01-15T10:00:00.000Z,pressure1,102.1,false
```

##### 示例 — 重命名文件 {#example--renaming-a-file}

使用文件类型 `任意文件` 和文件名 `@SourceFilename_@CurrentDate@SourceExtension`，文件 `report.pdf` 会以 `report_2024_01_15_10_00_00_000.pdf` 的名称原样发送。

#### OIAnalytics 有效载荷 {#oianalytics-payload-from-file}

以 OIAnalytics 紧凑格式（`timestamps`、`values` 和 `references` 三个并行数组）将文件中的行发送到 OIAnalytics 北向连接器，与记录列表的 [OIAnalytics 有效载荷](#oianalytics-payload)转换器相同。在[文件分组](#reading-the-file)之后，其设置相同：[引用、时间戳和值分组](#settings-3)，其字段从文件的各行中读取。

当南向连接器（通常是 MQTT、REST 或 Folder Scanner）提供 CSV 或 JSON 文件，而您又希望不编写自定义转换器就直接将其发送给 OIAnalytics 北向连接器时，就应该使用此转换器。没有引用、值或有效时间戳的行会被跳过，每个文件只发出一条警告。

##### 示例 — 带有 JSON 字符串化有效载荷的 MQTT 消息 {#example--mqtt-messages-with-a-json-stringified-payload}

某个 MQTT 南向连接器将每条消息交付为 `{ message, timestamp, item }`，其中 `message` 是**原始 MQTT 有效载荷字符串**。单条消息可以携带多个指标，因此行迭代器使用了**两个**通配符——一个用于外层消息数组，另一个用于每条消息（被 JSON 字符串化的）有效载荷内部的指标——并为每个指标展开一行，无论某条消息携带的是一个读数还是多个读数。

**输入** — 第一条消息携带两个指标，第二条携带一个

```json
[
  {
    "message": "{\"metrics\":[{\"name\":\"PLANT.UNIT1.TANK3.LEVEL\",\"value\":52.2936,\"timestamp\":\"2026-07-16T08:50:18.808Z\"},{\"name\":\"PLANT.UNIT1.TANK3.TEMP\",\"value\":18.4,\"timestamp\":\"2026-07-16T08:50:19.001Z\"}]}"
  },
  { "message": "{\"metrics\":[{\"name\":\"PLANT.UNIT2.PUMP1.SPEED\",\"value\":1450,\"timestamp\":\"2026-07-16T08:50:20.500Z\"}]}" }
]
```

配置：

- 文件类型：`JSON`，行迭代器 JSONPath：`$[*].message.metrics[*]`
- 引用字段：`name`
- 时间戳字段：`timestamp`，无时间戳处理（ISO 时间戳，保持不变）
- 值字段：`value`

第一个 `[*]` 遍历外层消息数组；第二个跨越 `message` 字符串边界（自动解析）以遍历其中的指标，每个指标都是一行，其属性即为该行的字段。同一份配置既能处理单指标消息，也能处理多指标消息。

**输出** — 三行：两行来自第一条消息，一行来自第二条消息

```json
{
  "timestamps": ["2026-07-16T08:50:18.808Z", "2026-07-16T08:50:19.001Z", "2026-07-16T08:50:20.500Z"],
  "values": [52.2936, 18.4, 1450],
  "references": ["PLANT.UNIT1.TANK3.LEVEL", "PLANT.UNIT1.TANK3.TEMP", "PLANT.UNIT2.PUMP1.SPEED"]
}
```

---

### 适用于 OIAnalytics 设定点 {#for-oianalytics-setpoints}

OIAnalytics 发送的写回命令是记录列表：每个设定点是一条带有其引用和值的记录。

```json
[
  { "reference": "pump1/setSpeed", "value": 1200 },
  { "reference": "valve2/open", "value": true }
]
```

它们会经过[记录列表转换器](#for-record-list-south-connectors)，从 `reference` 列读取点位 ID，从 `value` 列读取值：[文件](#file-from-records)将它们写入 JSON 文件（例如用于 Console），使用**值**负载的 [MQTT 有效载荷](#mqtt-payloads)单独发布每个值，[Modbus 值](#modbus-values)和 [OPCUA 值](#opcua-values)将它们写入映射的线圈、寄存器或节点。

例如，[MQTT 有效载荷](#mqtt-payloads)在点位 ID 列为 `reference`、使用**值**负载、值列为 `value`、映射表为 `pump1/setSpeed → control/pump1/speed` 时，会将上述设定点发布为（`valve2/open` 没有映射）：

```json
[{ "topic": "control/pump1/speed", "payload": "1200" }]
```

:::info 自 OIBus 3.9 起的设定点转换器
`setpoint` 数据类型已不复存在。升级时，JSON、MQTT 有效载荷、Modbus 值和 OPCUA 值这几个设定点转换器会被替换为对应的记录列表转换器，其映射表将原有的引用保留为点位 ID（MQTT 有效载荷转换器与以前一样仅发布值）。接收或生成设定点的自定义转换器已切换为 `record-list`：它们读取或写入的记录保持 `{ reference, value }` 结构。
:::

## 针对真实南向项目测试转换器 {#testing-a-transformer-against-a-real-south-item}

除了在隔离环境中测试自定义转换器的代码（见下文）之外，您还可以在项目弹窗**设置**步骤的测试面板（参见[测试项目](../south-connectors/common-settings.md#testing-an-item)）中，使用真实的、刚采集的数据端到端地预览任意转换器（标准或自定义）：

1. 选择该项目关联的某个北向连接器（或者，对于历史查询项目，直接选择该查询自身的某个转换器）。
2. 选择该北向连接器已配置的某个转换器，并仅针对本次测试运行调整其选项——已保存的配置不受影响。
3. 运行测试。弹窗会显示完整的处理流程：**原始结果 → 转换器（+ 选项） → 转换器输出**，这样您就可以在数据到达北向连接器缓存之前，使用该项目的实际数据验证转换器。

转换器以被测试的项目作为其数据源运行：其**文件名**中的 `@ConnectorName`（南向连接器或历史查询）和 `@ItemName` 变量会像运行时一样被替换，并且必须选择项目才能运行测试。

转换后的输出会连同其文件名一起显示，并可以显示为**表格**（CSV 文件或由对象组成的 JSON 数组）、**JSON** 或**原始**内容。默认显示按此顺序第一个可用的视图。

只会列出该北向连接器中应用于被测试项目的转换器：即该项目所属南向连接器的、针对其所有项目或针对包含该项目的选择的转换器。对于基于文件的连接器（Folder Scanner、FTP、SFTP），原始结果会列出匹配的文件；选择转换器后，它会像运行时一样，在最新的匹配文件内容上运行。

## 自定义转换器 {#custom-transformers}

当没有标准转换器适合您的用例时，您可以使用 JavaScript 或 TypeScript 编写**自定义转换器**。自定义代码运行在一个安全的隔离沙箱中，无法访问主机文件系统、Node.js 模块或网络。

自定义转换器在**引擎 → 转换器**页面中创建，随后可在任何北向连接器的转换器选择列表中使用。其**输入类型**为 `file`（文件和有效载荷）或 `record-list`（记录，以及 OIAnalytics 设定点）；其**输出类型**为 `file`、`record-list`、`mqtt`、`opcua`、`modbus` 或 `oianalytics`。

:::info 自 OIBus 3.9 起的自定义转换器
`time-values` 数据类型已不复存在：接收或生成时间值的自定义转换器在升级时已切换为 `record-list`。其代码现在必须读取和写入扁平的点位记录（`{ pointId, timestamp, value }`，例如 `record.value`），而不是 `{ pointId, timestamp, data: { value } }`。
:::

### 转换函数 {#transform-function}

您的代码必须导出一个 `transform` 函数（或一个默认导出）。它接收四个参数，并且必须返回一个结果对象。

```typescript
/**
 * @param content  - The raw input data as a UTF-8 string (JSON, CSV, XML…)
 * @param source   - Metadata about the data source ({ type, dataSourceId, … })
 * @param filename - The original filename (or a generated ID if no file was involved)
 * @param options  - The transformer options as configured in the UI
 */
export function transform(
  content: string,
  source: object,
  filename: string,
  options: object
): { data: unknown; filename: string; numberOfElement?: number } {
  // …
}
```

| 返回字段          | 描述                                                             |
| ----------------- | ---------------------------------------------------------------- |
| `data`            | 写入缓存文件的内容（见下文）：字符串、原始二进制数据或任何其他值 |
| `filename`        | 输出存储在北向连接器缓存中时使用的文件名                         |
| `numberOfElement` | 可选的已处理记录数，会显示在日志和指标中                         |

转换器的输出会**原样写入缓存文件**，然后由北向连接器根据其内容类型读回。`data` 按其类型处理：

| 返回的 `data`                              | 存储为                    | 适用于                                             |
| ------------------------------------------ | ------------------------- | -------------------------------------------------- |
| **字符串**                                 | 原样存储该字符串（UTF-8） | 任意输出类型——由您控制确切的文本                   |
| **`Uint8Array` / `ArrayBuffer`**（二进制） | 原始字节，逐字节保留      | 仅限 **`file`** 输出类型（文件类北向连接器）       |
| 任何**其他值**（对象、数组、数字……）       | `JSON.stringify(data)`    | 读取 JSON 的类型化输出（`record-list`、`mqtt` 等） |

:::caution 使 `data` 与输出类型匹配；确保 `filename` 是字符串

- 对于**类型化**输出类型（`record-list`、`mqtt`、`oianalytics`、`modbus`、`opcua`），北向连接器会将缓存文件作为 **JSON** 读取——请返回字符串或对象/数组（OIBus 会将其序列化为 JSON）。在这里返回二进制数据将无法解析。
- **二进制**输出（`Uint8Array`/`ArrayBuffer`）用于 **`file`** 输出类型，此时文件类北向连接器（File Writer、S3、Azure、OIAnalytics 文件上传）会原样写入/上传这些字节。
- 非字符串、非二进制的值如果被 `JSON.stringify` 拒绝（循环结构、`BigInt`）或丢弃（函数），转换会以明确的错误失败，而不会被缓存。

`filename` **必须是字符串**——它会成为缓存文件名并被记录到连接器指标中，因此在此处返回对象或数组可能会破坏指标持久化。当您从输入数据（MQTT 主题、有效载荷字段等）推导文件名时，请将其转换为字符串并去除路径分隔符，例如 `` `mqtt_${String(topic).replace(/[\\/]/g, '_')}.json` ``。
:::

### 可用的库 {#available-libraries}

以下库已预先加载到沙箱中，可通过 `require` 使用：

#### 示例 1 — 将 JSON 数组重新格式化为 CSV（JavaScript） {#example-1--reformat-a-json-array-to-csv-javascript}

某个 REST 南向连接器返回一个 JSON 数组。此转换器将其转换为以分号分隔的 CSV 文件，供 File Writer 北向连接器使用。

**输入（`content`）**

```json
[
  { "ts": "2024-01-15T10:00:00.000Z", "id": "temp1", "val": 23.5 },
  { "ts": "2024-01-15T10:01:00.000Z", "id": "temp1", "val": 23.8 },
  { "ts": "2024-01-15T10:00:00.000Z", "id": "pressure1", "val": 102.1 }
]
```

**输出**

```csv
Timestamp;Tag;Value
2024-01-15T10:00:00.000Z;temp1;23.5
2024-01-15T10:01:00.000Z;temp1;23.8
2024-01-15T10:00:00.000Z;pressure1;102.1
```

**代码**

```javascript
export function transform(content, source, filename, options) {
  const Papa = require('papaparse');
  const rows = JSON.parse(content);

  const csv = Papa.unparse(
    rows.map(r => ({
      Timestamp: r.ts,
      Tag: r.id,
      Value: r.val
    })),
    { delimiter: ';', header: true }
  );

  return {
    data: csv,
    filename: `export_${filename.replace('.json', '.csv')}`,
    numberOfElement: rows.length
  };
}
```

#### 示例 2 — 过滤并丰富点位记录（TypeScript） {#example-2--filter-and-enrich-point-records-typescript}

只保留高于配置阈值的读数，并为每条读数添加一个派生的 `status` 字段。

**输入（`content`）** — 某个基于点位的南向连接器的点位记录，`options.threshold = 20`

```json
[
  { "pointId": "plant/temp1", "timestamp": "2024-01-15T10:00:00.000Z", "value": "23.5" },
  { "pointId": "plant/temp2", "timestamp": "2024-01-15T10:00:00.000Z", "value": "18.0" },
  { "pointId": "plant/pressure1", "timestamp": "2024-01-15T10:00:00.000Z", "value": "102.1" }
]
```

**输出** — `temp2` 被丢弃（18.0 ≤ 20），其余记录被标注

```json
[
  { "pointId": "plant/temp1", "timestamp": "2024-01-15T10:00:00.000Z", "value": "23.5", "status": "NORMAL" },
  { "pointId": "plant/pressure1", "timestamp": "2024-01-15T10:00:00.000Z", "value": "102.1", "status": "HIGH" }
]
```

**代码**

```typescript
type PointRecord = { pointId: string; timestamp: string; value: string };

export function transform(
  content: string,
  _source: object,
  _filename: string,
  options: { threshold: number }
): { data: string; filename: string; numberOfElement: number } {
  const records: Array<PointRecord> = JSON.parse(content);
  const threshold = options.threshold ?? 0;

  const filtered = records
    .filter(record => parseFloat(record.value) > threshold)
    .map(record => ({
      ...record,
      status: parseFloat(record.value) > threshold * 2 ? 'HIGH' : 'NORMAL'
    }));

  console.info(`Kept ${filtered.length} / ${records.length} records above threshold ${threshold}`);

  return {
    data: JSON.stringify(filtered),
    filename: `filtered_${Date.now()}.json`,
    numberOfElement: filtered.length
  };
}
```

#### 示例 3 — 使用 JSONPath 从嵌套 JSON 中提取字段（JavaScript） {#example-3--extract-fields-from-a-nested-json-with-jsonpath-javascript}

**输入（`content`）**

```json
{
  "records": [
    { "header": { "ts": "2024-01-15T10:00:00.000Z" }, "tag": "plant/temp1", "measurements": { "val": 23.5 } },
    { "header": { "ts": "2024-01-15T10:01:00.000Z" }, "tag": "plant/temp1", "measurements": { "val": 23.8 } },
    { "header": { "ts": "2024-01-15T10:00:00.000Z" }, "tag": "plant/pressure1", "measurements": { "val": 102.1 } }
  ]
}
```

**输出**

```json
[
  { "pointId": "plant/temp1", "timestamp": "2024-01-15T10:00:00.000Z", "value": 23.5 },
  { "pointId": "plant/temp1", "timestamp": "2024-01-15T10:01:00.000Z", "value": 23.8 },
  { "pointId": "plant/pressure1", "timestamp": "2024-01-15T10:00:00.000Z", "value": 102.1 }
]
```

**代码**

```javascript
export function transform(content, _source, _filename, _options) {
  const { JSONPath } = require('jsonpath-plus');
  const data = JSON.parse(content);

  const timestamps = JSONPath({ path: '$.records[*].header.ts', json: data });
  const tags = JSONPath({ path: '$.records[*].tag', json: data });
  const values = JSONPath({ path: '$.records[*].measurements.val', json: data });

  const records = timestamps.map((ts, i) => ({
    pointId: tags[i],
    timestamp: ts,
    value: values[i]
  }));

  return {
    data: JSON.stringify(records),
    filename: `extracted_${Date.now()}.json`,
    numberOfElement: records.length
  };
}
```

#### 示例 4 — 使用 Luxon 进行时间戳转换（JavaScript） {#example-4--timestamp-conversion-with-luxon-javascript}

解析 REST API 响应中的 Unix 纪元毫秒时间戳，并将其转换为特定时区的 ISO-8601 格式。

#### 示例 5 — 将 MQTT JSON 消息规范化为记录（JavaScript） {#example-5--normalize-mqtt-json-messages-to-records-javascript}

**MQTT 南向连接器**将每批接收到的消息作为单个 JSON 文件（保存在内存中）交付：一个由 `{ message, timestamp, item: { id, name, topic } }` 组成的 JSON 数组，其中 `message` 是**原始 MQTT 有效载荷字符串**。该原始有效载荷可以是任意形式——一个裸数字、一个 JSON 字符串、一个扁平对象，或一个读数数组（参见本地测试环境发布的 [JSON 主题](../../developer/local-test-stack.md#json-topics)）。此转换器将它们全部规范化为点位记录（`record-list` 输出），并使用主题作为点位 ID。

**输入（`content`）** — 来自不同主题的三条消息

```json
[
  {
    "message": "{\"value\":35.17,\"unit\":\"celsius\",\"timestamp\":\"2026-06-04T08:15:06.673+00:00\",\"quality\":\"good\"}",
    "timestamp": "2026-06-04T08:15:06.700Z",
    "item": { "id": "i1", "name": "flat", "topic": "workshop1/json/flat" }
  },
  {
    "message": "44.53",
    "timestamp": "2026-06-04T08:15:06.700Z",
    "item": { "id": "i2", "name": "number", "topic": "workshop2/json/number" }
  },
  {
    "message": "[{\"timestamp\":\"2026-06-04T08:15:06.673+00:00\",\"value\":34.95},{\"timestamp\":\"2026-06-04T08:15:08.673+00:00\",\"value\":35.48}]",
    "timestamp": "2026-06-04T08:15:06.700Z",
    "item": { "id": "i3", "name": "array", "topic": "workshop1/json/array" }
  }
]
```

**输出** — 每个读数一条点位记录；数组消息产生两条

```json
[
  { "pointId": "workshop1/json/flat", "timestamp": "2026-06-04T08:15:06.673+00:00", "value": "35.17" },
  { "pointId": "workshop2/json/number", "timestamp": "2026-06-04T08:15:06.700Z", "value": "44.53" },
  { "pointId": "workshop1/json/array", "timestamp": "2026-06-04T08:15:06.673+00:00", "value": "34.95" },
  { "pointId": "workshop1/json/array", "timestamp": "2026-06-04T08:15:08.673+00:00", "value": "35.48" }
]
```

**代码**

```javascript
export function transform(content, _source, _filename, _options) {
  const messages = JSON.parse(content); // [{ message, timestamp, item: { topic } }, …]
  const records = [];

  // Extract a scalar value from one reading, whatever its shape.
  const toValue = reading => {
    if (reading !== null && typeof reading === 'object') {
      // Flat reading ({ value, … }); fall back to the whole object for nested shapes.
      return reading.value ?? JSON.stringify(reading);
    }
    return reading; // number, string or boolean
  };

  for (const { message, timestamp, item } of messages) {
    // The raw MQTT payload may be JSON (object/array/number/string) or plain text.
    let parsed;
    try {
      parsed = JSON.parse(message);
    } catch {
      parsed = message; // non-JSON payload: keep the raw string
    }

    const readings = Array.isArray(parsed) ? parsed : [parsed];
    for (const reading of readings) {
      records.push({
        pointId: item.topic,
        timestamp: (reading && reading.timestamp) || timestamp,
        value: String(toValue(reading))
      });
    }
  }

  return {
    data: JSON.stringify(records),
    // Always a plain string filename — never a payload object (see the caution above).
    filename: `mqtt_${Date.now()}.json`,
    numberOfElement: records.length
  };
}
```

:::tip 在本地生成这些有效载荷
[本地测试环境](../../developer/local-test-stack.md#json-topics)会发布完全相同的 MQTT JSON 结构（`flat`、`nested`、`array`、`mixed`、`string`、`number`），因此您可以将 MQTT 南向连接器指向它，并针对每种情况测试自定义转换器。
:::
