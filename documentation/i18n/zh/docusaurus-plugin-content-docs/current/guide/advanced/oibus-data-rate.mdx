# 数据速率与缓存大小

OIBus 使用**存储转发**机制：当北向连接器无法访问其目标时，数据会被缓冲到磁盘上的本地缓存中。连接恢复后，缓存的数据会按顺序重新发送。要正确设定缓存大小——足够大以在预期的中断期间不填满磁盘——需要了解每种格式的持续数据速率。

本页说明如何按格式估算数据量，并提供一个交互式计算器，用于为你的具体部署方案确定缓存大小。

## 传输格式 {#transmission-formats}

OIBus 根据北向连接器的不同，以两种模式发送数据：

| 模式              | 描述                                               | 连接器                                       |
| ----------------- | --------------------------------------------------------- | ------------------------------------------------ |
| **文件端点** | 数据写入 CSV 文件并推送到远程位置 | SFTP、Amazon S3、Azure Blob Storage、File Writer |
| **JSON 载荷**  | 数据序列化为 JSON 数组并通过 HTTP POST 发送      | OIAnalytics、REST API                            |

格式的选择对吞吐量和缓存大小有很大影响，尤其是在高频或多信号的工作负载下。

:::note 本页适用范围
本页的字节大小计算公式所建模的是 CSV 文件以及上述连接器所使用的
`{timestamp, pointId, value}` JSON 结构。它们不适用于**Modbus**、**MQTT** 或 **OPC UA**
北向连接器，这些连接器直接写入其工业协议（寄存器写入、主题发布、节点写入），
使用的是不同的、协议特定的缓存格式——也不适用于 **Console** 北向连接器，
该连接器仅记录到标准输出，完全不会为中断传输或缓冲数据。
:::

## CSV 格式估算 {#csv-format-estimations}

以下字节大小基于以下具有代表性的字段宽度：

| 字段                        | 示例                    |  字节数 |
| ---------------------------- | -------------------------- | -----: |
| 时间戳                    | `2020-02-01T20:04:00.000Z` |     24 |
| 点名称                   | `Data001`                  |      7 |
| 数值                | `12.0`                     |      4 |
| 分隔符（逗号或换行符） | `,` / `\n`                 | 各 1 |

### 1. 行格式 {#1-row-format}

每行一个数据点。

```
Timestamp,Reference,Value
2020-02-01T20:04:00.000Z,Data001,12.0
```

**每行大小**（=每个数据点的大小）：

- 时间戳：24 字节
- 参考名：7 字节
- 数值：4 字节
- 2 个逗号 + 换行符：3 字节
- **总计：每个数据点 38 字节**

|              |                                                                                                               |
| ------------ | ------------------------------------------------------------------------------------------------------------- |
| **适用场景** | 数据点具有不同的时间戳，来自异构数据源，或以不规则间隔到达           |
| **优点**     | 结构最简单；每行都是自包含的；易于流式处理或追加；解析一行无需 schema |
| **缺点**     | 最冗长的 CSV 格式——时间戳会为每个数据点重复一次                          |

### 2. 列格式 {#2-column-format}

K 个数据点共享一个时间戳行，点名称出现在表头中。

```
Timestamp,Data001,Data002,Data003
2020-02-01T20:04:00.000Z,12.0,10.0,10.0
```

**每个数据行的大小**（每行 K 个数据点）：

- 时间戳：24 字节
- K 个数值：K × 4 字节
- K 个逗号 + 换行符：K + 1 字节
- **每行总计：(25 + 5K) 字节 → 每个数据点 (25 + 5K) / K 字节**

对于 K = 3：40 字节/行 → **约 13.3 字节/数据点**

|              |                                                                                                              |
| ------------ | ------------------------------------------------------------------------------------------------------------ |
| **适用场景** | 多个信号在同一扫描速率下被同时采样（例如一个 SCADA 扫描组）                  |
| **优点**     | 时间戳在 K 个数据点之间共享——随 K 增长空间效率显著提升；天然适合同步轮询      |
| **缺点**     | 一行中的所有数据点必须共享同一个时间戳；schema 存在于表头中——脱离表头更难处理 |

### 3. 列-行格式 {#3-column-row-format}

每行包含一个时间戳、一个共享的参考名以及 K 个数值。子 ID 出现在表头中。

```
Timestamp,Reference,001,002,003
2020-02-01T20:04:00.000Z,Data,12.0,10.0,10.0
```

**每个数据行的大小**（每行 K 个数据点，参考名 4 字节）：

- 时间戳：24 字节
- 参考名：4 字节
- K 个数值：K × 4 字节
- (K + 1) 个逗号 + 换行符：K + 2 字节
- **每行总计：(30 + 5K) 字节 → 每个数据点 (30 + 5K) / K 字节**

对于 K = 3：45 字节/行 → **15 字节/数据点**

|              |                                                                                                                                                                    |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **适用场景** | 数据具有天然的分组结构——例如跨多个设备实例的同一测量值，如历史数据连接器中使用组/参考数组的场景 |
| **优点**     | 结合了时间戳共享与额外的分组维度；当参考名有意义时可读性好                                                        |
| **缺点**     | 与列格式有相同的时间戳约束；由于额外的参考列，效率略低；下游工具的广泛支持较少                                |

## JSON 载荷估算 {#json-payload-estimation}

```json
[
  {
    "timestamp": "2020-02-01T20:04:00.000Z",
    "pointId": "Data001",
    "value": "12.0"
  }
]
```

**大小明细**（紧凑序列化，无空白字符）：

| 组成部分             | 内容                                  |  字节数 |
| --------------------- | ---------------------------------------- | -----: |
| `timestamp` 字段     | `"timestamp":"2020-02-01T20:04:00.000Z"` |     38 |
| `pointId` 字段       | `"pointId":"Data001"`                    |     19 |
| `value` 字段         | `"value":"12.0"`                         |     14 |
| 结构字符 | `[{`、2 个 `,`、`}]`                       |      6 |
| **总计**             |                                          | **77** |

|              |                                                                                                                               |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| **适用场景** | 将数据发送到原生消费 JSON 的 REST API 或现代平台                                                      |
| **优点**     | 自描述；接收方无需了解 schema；在大多数语言和平台上都易于消费                |
| **缺点**     | 最冗长的格式——在 K = 3 时大约是行 CSV 的 2 倍、列 CSV 的约 5.8 倍；序列化开销更高 |

## 格式效率总结 {#format-efficiency-summary}

各 K 值下每个数据点的字节数（列-行格式假设参考名为 4 字节）：

| 格式         | 公式       | K = 1 | K = 3 | K = 10 |
| -------------- | ------------- | ----: | ----: | -----: |
| 行 CSV        | 38            |    38 |  38.0 |   38.0 |
| 列 CSV     | (25 + 5K) / K |    30 |  13.3 |    7.5 |
| 列-行 CSV | (30 + 5K) / K |    35 |  15.0 |    8.0 |
| JSON           | 77            |    77 |  77.0 |   77.0 |

列格式将时间戳的开销分摊到 K 个数据点上，随着 K 增长空间效率显著提升。在 K = 10 时，列 CSV 使用的空间比行 CSV **少 5 倍**，比 JSON **少 10 倍**。

## 缓存大小计算器 {#cache-sizing-calculator}

使用下方的计算器来估算你的部署所需的吞吐量和最小缓存大小。

**输入指南：**

| 输入                       | 表示的内容                                                                                                                     |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| **每秒数据点数**    | 所有活跃南向连接器向该北向连接器提供数据的持续采集速率                                         |
| **每行数据点数（K）**      | 共享一个时间戳行的信号数量——仅影响列格式和列-行格式                                               |
| **安全缓冲（%）**       | 为 CSV 表头行、部分记录、测量突发以及舍入误差预留的额外余量。典型值为 20%–30%。                                                              |
| **网络开销（%）**    | 来自传输层的额外字节——TLS 摊销、HTTP 分块、SFTP 数据包封装。对于 HTTPS 或 SFTP，典型值为 20%–50%。 |
| **中断时长（小时）** | 预期最长的断连窗口。在连接恢复之前，缓存必须至少能容纳这么多的数据。              |

**中断期间所需缓存**列显示的是在北向连接器缓存设置中应配置的**最大存储大小**的最小值。

## 应用结果 {#applying-the-result}

在每个北向连接器的**缓存**选项卡中，将**最大存储大小**设置为至少为你所选格式对应的**中断期间所需缓存**列所示的值。在以下情况下应额外留出余量：

- 你所处环境中的中断往往持续时间超过估算值
- 多个北向连接器共享同一个磁盘卷
- 主机还运行后台导出、日志记录或其他磁盘密集型进程

:::tip 多个北向连接器
每个北向连接器都维护自己独立的缓存。如果多个连接器同时转发数据，请分别为每个连接器确定大小，并确认主机具有足够的总磁盘容量。
:::

## 压缩的影响 {#effect-of-compression}

某些传输配置支持载荷压缩——例如，OIBus 与反向代理之间的 HTTPS 上使用 gzip，或在客户端启用压缩的 SFTP。压缩通常能将载荷大小**减少 CSV 的 60%–80%**、**JSON 的 70%–85%**，因为这两种格式都包含高度重复的内容（时间戳、字段名、数值字符串）。

请注意，OIBus 缓存存储的是**压缩之前**的数据。因此缓存大小取决于计算器中显示的未压缩速率。压缩只会减少在传输线路上发送的字节数，而不会减少缓存所占用的磁盘空间。
