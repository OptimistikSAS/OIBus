# 调整南向历史调用设置

[通用设置](../south-connectors/common-settings.md)介绍了具有历史查询能力的连接器的四个时序字段——
**最大读取间隔**、**读取延迟**、**开始时间偏移**、**结束时间偏移**——以及**恢复策略**，
并展示了它们在条目或分组上的位置。本页将更深入一层：探讨每个设置对一次查询实际
产生的影响的思维模型，以及关于该使用_什么值_以及_为什么_的实际场景。

这些设置仅存在于具有历史数据能力的南向连接器上（SQL 连接器、HA 模式下的 OPC UA、
HDA 模式下的 OPC Classic、OSIsoft PI、OIAnalytics、REST、InfluxDB——完整列表参见
[历史查询](../history-queries.md#compatible-south-connectors)）。仅支持流式传输的连接器（MQTT、Modbus、
文件夹/FTP/SFTP 扫描器）没有需要切分的时间范围，因此本页内容对它们均不适用。

## 思维模型：一次运行，四个决策 {#the-mental-model-one-run-four-decisions}

每次具有历史查询能力的条目或分组运行时，OIBus 都会依次执行相同的四个步骤：

1. **计算有效窗口。** 从被跟踪的时刻（上一次成功查询的结束时间）开始，结合
   当前时间，然后将 `开始时间偏移` 和 `结束时间偏移` 应用到两端。如果得到的结束时间
   不晚于得到的开始时间，则本次运行会被完全跳过——不会执行任何查询，被跟踪
   的时刻也不会移动。
2. **拆分为子区间。** 有效窗口会被切分为若干连续的块，每块最多为
   `最大读取间隔` 秒（最后一块可能更短）。值为 `0`（或留空）会禁用
   拆分——整个窗口会在一次调用中被查询。
3. **依次查询每个子区间**，在一个子查询与下一个子查询之间暂停 `读取延迟` 毫秒
   （第一个子查询之前不暂停，最后一个之后也不暂停）。`恢复策略` 决定该
   顺序是从最旧到最新（默认）还是从最新到最旧。
4. **推进被跟踪的时刻。** 在 `oldest`（最旧）模式下，只要某个子区间返回的数据
   比已跟踪的数据更新，它就会在_每个_子区间之后向前推进——因此运行中途崩溃
   只会丢失正在处理中的那个区间。在
   `newest`（最新）模式下，只有在_每个_子区间都完成后才会推进一次，因此运行中途重启
   不会跳过一个更旧、尚未查询过的块。

偏移只被应用一次，作用于整个窗口的两端——而不会针对第 2 步产生的每个子区间
重新应用。

```
tracked instant                                                            now
|                                                                            |
Start time offset                                              End time offset
v                                                                            v
+----------------------------- effective window -----------------------------+

+---sub-interval 1---+---sub-interval 2---+---sub-interval 3---+----last-----+
                                          ^
                                Read delay pause here
```

`开始时间偏移` 和 `结束时间偏移` 各自决定有效窗口的一端——负值会使
该端更早，正值会使其更晚；上图并不假定任何一个方向，因为这完全取决
于你所配置的正负号。拆分只会在两端都确定_之后_发生：`子区间 1`
恰好从上图中的有效开始时间开始，最后一个子区间恰好在有效结束时间结束，无论
偏移如何移动这两端。上图所示的读取延迟暂停会在每一对
连续的子区间之间重复出现——第一个之前不会出现，最后一个之后也不会出现。

本页的其余部分将逐一说明为什么你可能需要将这些设置从默认值调离。

## 最大读取间隔：限制单次查询请求的数据量 {#max-read-interval-bounding-how-much-a-single-query-asks-for}

`最大读取间隔` 的存在是为了保护数据源和 OIBus，防止单次查询请求量过大——
这在数据源为所请求的窗口保存**大量数值**时就会发生。

### 示例：大量积压数据 {#example-a-wide-backlog}

假设某个连接器以每秒 1 次采样的速度采集 200 个标签：即每秒 200 行，约每小时
720,000 行。如果该连接器因维护而停止 24 小时，那么下一次运行的窗口将
覆盖整个停机期间——如果不进行拆分，这将是单次查询向数据源请求超过
1700 万行数据的一次往返。根据数据源的不同，这可能意味着一次锁表数分钟的
查询、一次超时、任一侧的内存不足错误，或者仅仅是连接器驱动无法
缓冲的过大负载。

将 `最大读取间隔` 设置为，例如 `3600`（1 小时），会将那一个巨大的查询转变为 24 个
连续的约 720,000 行的查询。每一个都足够小，可以快速且可预测地完成，并且——结合
`oldest` 恢复策略——每完成一小时都会被持久化地记录检查点，因此在补齐过程中重启
只会重复正在进行中的那一小时，而不是整整一天。

### 设定大小 {#sizing-it}

- **根据数据源（以及网络）在一次调用中能够舒适返回的数据量来设定** — 关于如何将
  行数换算为字节估算值，参见
  [数据速率与缓存大小](./oibus-data-rate.mdx)。
  查询超时严格或服务器端内存有限的数据源需要更小的间隔；能够高效处理宽范围扫描的
  数据源（例如有适当索引的时间序列数据库）可以使用更大的间隔。
- **不要仅因为稳态速率较低就缩小该值。** 该设置必须能应对最坏情况——
  即最长的现实积压量（周末停机、网络中断）——而不仅仅是窗口本来就很小的
  正常轮询周期。
- **对于低流量的数据源，`0`（不拆分）是可以的**，因为其窗口在实践中始终很小，但对于
  可能在停机后积累大量积压数据的场景则存在风险，因为下一次运行会变成一次
  无边界的查询。

:::warning 类 SQL 连接器必须在查询中引用两个时间变量
对于基于 SQL 的连接器（MSSQL、MySQL/MariaDB、ODBC、OLEDB、Oracle、PostgreSQL）以及 REST，OIBus 无
法自行限定查询范围——它只会替换你的查询文本所要求的变量。`最大读取
间隔` 只有在查询同时显式过滤 **`@StartTime`** 和 **`@EndTime`** 时才会生效：

```sql
SELECT * FROM sensor_data
WHERE timestamp > @StartTime
AND timestamp <= @EndTime
```

如果查询中缺少 `@EndTime`，每个子区间仍然会从 `@StartTime` 开始获取数据而没有
上限——拆分每次都会产生同样过大的、无边界的结果，而不是一系列更小的
结果。如果 `@StartTime` 也缺失，那么每次运行都只会简单地重新读取同一个固定的结果集。

内部自行管理历史读取的连接器——OPC UA（HA 模式）、OPC Classic（HDA 模式）以及
OSIsoft PI——不存在这个注意事项：OIBus 会将子区间的开始和结束时间直接传递给
连接器自身的历史读取调用，因此无论标签的配置如何，`最大读取间隔` 始终会限定
查询范围。
:::

## 读取延迟：调节连续子查询的节奏 {#read-delay-pacing-consecutive-sub-queries}

`读取延迟` 会在子查询之间插入一段暂停，以避免较大的 `最大读取间隔` 拆分变成一连串
背靠背的请求猛烈冲击数据源——这对于限速的 API（REST、OIAnalytics）、不应被
独占的生产数据库，或需要一点时间才能处理完上一个请求再接收下一个请求的
PLC/历史服务器都很有用。

### 与最大读取间隔的相互作用 {#the-interaction-with-max-read-interval}

这两个设置之间存在直接的权衡。一次运行的总节奏开销大约为：

```
overhead ≈ (number of sub-intervals − 1) × Read delay
```

将 24 小时的积压拆分为 24 个 1 小时的块，`读取延迟` 为 1 秒时，会增加约 23 秒的总
暂停时间——可以忽略不计。但如果同样 24 小时的积压被拆分为 1 分钟的块（1,440 个子区间），
在相同的 1 秒延迟下，会增加将近 **24 分钟**的纯节奏开销，这还是在 1,440 次往返本身
之上叠加的。如果你为了降低每次查询的负载而缩小 `最大读取间隔`，请检查这对
真实积压场景下的补齐时间造成的影响，不要想当然地认为小的 `读取延迟` 是无害的。

### 设定大小 {#sizing-it-1}

| 现象                                                                  | 调整方式                                                |
| ------------------------------------------------------------------------ | --------------------------------------------------------- |
| 数据源拒绝请求、限速，或在重复轮询下性能下降 | 增加 `读取延迟`                                     |
| 补齐大量积压所需的时间远超积压本身的时长     | 减少 `读取延迟` 和/或增加 `最大读取间隔` |
| 数据源完全没有速率方面的顾虑（如本地文件支持的数据库等）          | `0` 是可以的                                               |

## 开始/结束时间偏移：当数据源尚未写完时 {#startend-time-offset-when-the-source-isnt-done-writing-yet}

当**一起查询的多个条目并非在同一时刻被数据源全部处理完毕**时，这个设置最为
重要。

### 为什么会发生这种情况 {#why-this-happens}

许多历史数据类型的数据源不会在一个数值刚被打上时间戳的瞬间就使其可被持久地
查询到。SQL 表可能会定期批量提交插入；OPC UA HA 服务器通常会先在本地缓冲
新历史化的样本，然后再将其刷新到其底层存储中；PI 或 OPC Classic HDA 服务器会
在内部逐个标签地解析多标签读取。最后这种情况正是具体的“多个条目一起”的场景：
一次针对一组条目的批量查询可能看到标签 A 的值已经刷新并可被查询，而标签 B 在
同一时刻的值仍停留在内部缓冲区中，落后几百毫秒——因为该分组作为共享同一个
被跟踪时刻的一次调用被查询，这种不一致性在每个条目层面是不可见的。

如果 OIBus 查询 `[被跟踪的时刻, 现在]` 并立即将被跟踪的时刻推进到 `现在`，任何
在查询时尚未被数据源处理的数值就会永远丢失——下一次运行会严格从它之后开始，
将永远不会再请求那段时间。

### 开始时间偏移：重新请求一段安全缓冲区 {#start-time-offset-re-request-a-safety-cushion}

**负的** `开始时间偏移`（例如 `-2000`，表示 2 秒的缓冲区）会将窗口的开始
向后移动，从而使 OIBus 重新请求上一次运行已经覆盖过的一段时间。任何上一次尚未
被处理的数值都会有第二次出现的机会。这依赖于查询本身（或下游的
去重步骤）能够容忍已经出现过的行被再次返回——这对大多数基于时间戳键的 SQL
查询以及北向对重复时间戳的处理来说都是成立的。

将负偏移设置得比数据源已知或观察到的提交/刷新延迟略大一些。如果你不知道
该延迟，可以从保守值开始（例如 `-5000`），并在确认边界处不再出现缺口后再收紧。

### 结束时间偏移：完全不触碰模糊区域 {#end-time-offset-dont-touch-the-fuzzy-region-at-all}

**负的** `结束时间偏移` 采用相反的方式：它不是在下次重新查询一段缓冲区，而是
将_本次_窗口的结束向后拉，使那段尚不可靠的尾部区域从一开始就不会被查询。这
适用于最终一致的数据源，即重新查询既不安全也不方便——例如，由一个每隔几秒
才刷新一次的物化视图支撑的 API，此时“截至此刻”的请求可能返回一个部分或
即将变化的结果。

与 `开始时间偏移` 相比，其权衡实际上关乎响应速度，而不是数据丢失——两种方式都
不会真正丢失数值。`开始时间偏移` 会重复查询它已经查询过的数值，但作为交换，
一个迟到的数值会在它变得可用后的下一次运行中尽快被采集到，因为该次运行会重新
请求同样的尾部区间。`结束时间偏移` 永远不会重复某个数值，但它会将被缩短的
尾部区域中的每个数值都延迟至少一次运行：由于被跟踪的时刻只会推进到被缩短的
结束点，该区域只会成为_下一次_运行窗口的一部分，而不是现在被查询。

### 示例：2 秒提交延迟的可视化 {#example-a-2-second-commit-lag-visualized}

一个简单的示例：某数据源在数值打上时间戳后 2 秒才提交它，某扫描模式每 5
秒轮询一次——这是一个夸张的比例，纯粹是为了让规律更易于观察。每次运行的窗口
都会延伸到数据源尚未提交的数据的 2 秒之内：那段尾部区间（下方标为 `███`）就是
“风险区域”。三种方式的区别在于各自如何处理它。

```
No offset — the risky zone is dropped, every single run
  run @:15   [:10 ─────────── :13 ███ :15)        tracked instant → :15
  run @:20   [:15 ─────────── :18 ███ :20)        tracked instant → :20   (:13-:14 never revisited — LOST)
  run @:25   [:20 ─────────── :23 ███ :25)        tracked instant → :25   (:18-:19 never revisited — LOST)

Start time offset = -2s — the risky zone is re-asked and recovered, but duplicated
  run @:15   [:08 ▒▒▒ :10 ─────────── :13 ███ :15)   tracked instant → :15
  run @:20   [:13 ▒▒▒ :15 ─────────── :18 ███ :20)   :13-:14 now committed → RECOVERED (re-read, duplicate)
  run @:25   [:18 ▒▒▒ :20 ─────────── :23 ███ :25)   :18-:19 RECOVERED the same way — repeats every run

End time offset = -2s — the risky zone is never queried, just deferred
  run @:15   [:10 ─────────── :13)                   tracked instant → :13   (window never reaches :13-:14)
  run @:20               [:13 ─────────── :18)       :13-:14 collected here — one run later, never duplicated
  run @:25                           [:18 ─────────── :23)   :18-:19 collected here — same one-run delay, repeats
```

`███` = 窗口所请求但数据源尚未提交的部分，因此该查询会静默地对这部分不返回任何
数据。`▒▒▒` = 上一次运行中还是 `███`、而现在数据源已经赶上进度、被重新请求的部分。

在没有偏移的情况下，每次运行都会永久丢失自己的尾部 2 秒。`开始时间偏移`
用一次无害的重复读取，换来一次运行后恢复那同样的 2 秒。`结束时间偏移`
永远不会重复任何内容，但代价是“现在”最后 2 秒内的所有内容总是会晚一整轮
到达。

同样的情形也适用于批量的分组查询，只是沿着一个不同的轴向展开。设想的不是一个
数据源固定滞后一段时间，而是条目 A 和 B 在每个刻度（`:15`、`:20`、`:25`……）一起被
读取：条目 A 在 `:15` 的值可能在该分组被查询时已经存储完毕，而条目 B 在同一
`:15` 采样的值却是稍晚才写入的——因此风险区域是刻度边界本身，取决于哪个
条目尚未跟上进度，而不是一段固定的尾部时间。同样的三种结果依然成立：在
没有偏移的情况下，条目 B 的 `:15` 样本一旦被跟踪的时刻推进过去就会被永久静默丢弃；
负的 `开始时间偏移` 会在下一个刻度重新请求 `:15` 边界并恢复条目 B 的值（代价是
对条目 A（其值本已存在）进行一次无害的重复读取）；负的 `结束时间偏移` 则
干脆不请求某个刻度，直到下一轮运行，那时该分组中的每个条目都应该已经跟上进度。

### 如何选择 {#choosing-between-them}

| 情形                                                                                    | 使用                                     |
| --------------------------------------------------------------------------------------------- | ---------------------------------------- |
| 数据源偶尔会稍晚提交某个数值；重复读取无害              | 负的 `开始时间偏移`            |
| 数据源最新的数据在稳定之前不可靠/不完整；重新查询不受欢迎 | 负的 `结束时间偏移`              |
| 一次批量的多条目查询（OPC UA HA、PI、HDA），其中条目并非同时全部刷新          | 分组上的负的 `结束时间偏移` |
| OIBus 的时钟落后于数据源的时钟                                                            | 正的 `结束时间偏移`              |

正的 `结束时间偏移` 主要用于**时钟对齐**：如果 OIBus 自身的时钟比数据源的时钟
落后一个大致已知的量，数据源可能已经存在时间戳晚于 OIBus 所认为的“现在”的数据。
将查询的上限向前推进相同的偏差量，可以让 OIBus 检索到数据源的实际当前时间，
而不是止步于自身滞后的时钟。

## 恢复策略：补齐期间的顺序与持久性 {#recovery-strategy-order-and-durability-during-catch-up}

只有当需要处理的子区间不止一个时——即当积压数据（首次运行、停机、被放宽的
`开始时间偏移`）在一次轮询中产生了多个块时——`恢复策略` 才有意义。

- **`从最旧到最新`（默认）** 会按时间顺序处理积压数据，并在每个块之后为被跟踪的
  时刻设置检查点。补齐过程中崩溃或重启只会重新查询正在处理中的那一个块。
  仪表盘会落后于实际情况，直到整个积压被清空为止。
- **`从最新到最旧`** 会先查询最新的块，使当前数值立即可用，然后再回填
  更旧的块。被跟踪的时刻只会在该次运行的_整个_积压完成之后才推进——运行
  中途重启会重新查询整个积压，而不是从中断处继续，以此换取更快地看到“现在”，
  代价是牺牲了崩溃安全性。

当仪表盘或下游消费者需要尽快获得当前数值，即便一次长时间的回填仍在补齐历史数据时，
选择 `newest`（最新）。当增量的、崩溃安全的进度比“现在”出现的速度更重要时，保留
`oldest`（最旧，默认值）——这对大多数无人值守的部署来说是正确的选择。

## 综合示例 {#putting-it-together-a-worked-example}

一个南向 MSSQL 连接器从一张历史数据表中轮询 200 个标签。该数据库会批量提交插入，
通常在样本时间戳后的 1.5 秒内完成提交。团队希望仪表盘即使在维护窗口之后也能
快速显示当前数值，同时也希望在回填被中断时具备崩溃安全的进度。

| 设置               | 值                   | 理由                                                                                                                          |
| --------------------- | ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| **最大读取间隔** | `900`                   | 15 分钟的块能使每次查询的行数（在此速率下约 180,000 行）舒适地保持在数据源响应时间预算之内。    |
| **读取延迟**        | `500`                   | 足以避免与同一数据库上的生产流量竞争，同时又不会明显拖慢历时数小时的补齐过程。 |
| **开始时间偏移** | `-2000`                 | 一个 2 秒的缓冲区，明显大于观察到的 1.5 秒提交延迟。                                                                  |
| **恢复策略** | `从最旧到最新` | 对该连接器而言，崩溃安全性的优先级高于“现在”的即时可见性。                                                                |

如果同一个团队反而需要实时仪表盘在一次长时间的周末停机补齐期间立即反映
当前数值——并接受一次补齐中途的重启会重新运行整个积压——他们会将
`恢复策略` 切换为 `从最新到最旧`，并保持其他三个值不变。

## 常见陷阱 {#common-pitfalls}

- **`最大读取间隔` 相对数据源来说过大。** 任何真实积压之后的下一次运行都会变成一次
  过大的查询——这正是该设置本应防止的问题。
- **`最大读取间隔` 相对你实际看到的积压来说过小。** 会将一个数据量问题转变为
  一个区间数量问题：数千个微小的子查询，每一个都要付出完整的 `读取延迟` 暂停成本。请对照
  上方的开销公式，针对你的最坏情况积压进行检查，而不仅仅是稳态情况。
- **忘记偏移只作用于整个窗口一次，而不是按子区间应用。** 按 `最大读取间隔` 进行拆分
  是在偏移已应用到有效开始/结束之_后_发生的——拆分窗口中间的子区间边界不会被
  独立地偏移。
- **`结束时间偏移` 持续大于轮询间隔。** 如果扫描模式的触发频率高于该偏移缩小
  窗口的幅度，某些运行计算出的结束时间会不晚于开始时间，从而被完全跳过——
  表现为日志中记录了一次被跳过的查询，且没有采集到数据。
- **在已有既定被跟踪时刻的连接器上更改这些设置。** 下一次运行会从当前的
  被跟踪时刻开始应用新值；`最大读取间隔` 或任一偏移的大幅跳变可能在
  该边界处产生一个小缺口或一次重复。关于配置变更后被跟踪时刻行为的完整说明，
  参见[通用设置——最大时刻跟踪](../south-connectors/common-settings.md#max-instant-tracking)。

## 快速参考 {#quick-reference}

| 目标/现象                                                                       | 调整                                              |
| ------------------------------------------------------------------------------------ | ---------------------------------------------------- |
| 数据源在大范围查询下超时或耗尽内存                                               | 降低 `最大读取间隔`                           |
| 补齐大量积压的时间主要花在暂停上，而不是查询本身       | 提高 `最大读取间隔` 和/或降低 `读取延迟` |
| 数据源在重复轮询下限速、性能下降或报错                                       | 提高 `读取延迟`                                  |
| 需要尽快获取迟到的数值，可接受重复数据           | 负的 `开始时间偏移`                        |
| 必须避免重复读取，可以等到下一次运行再获取已可用的数值 | 负的 `结束时间偏移`                          |
| 仪表盘必须在长时间回填期间快速显示当前数值                      | `恢复策略` → `newest`（最新）                      |
| 补齐必须具备崩溃安全性且尽量减少重复工作                              | `恢复策略` → `oldest`（最旧，默认）            |
