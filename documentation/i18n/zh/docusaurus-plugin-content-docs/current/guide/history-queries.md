# 历史查询

历史查询允许您使用与实时流式传输相同的南向和北向连接器基础设施，检索过去某个时间范围内的数据。
这在需要回填实时系统启用之前的数据，或需要重新导出特定时段的数据时非常有用。

## 创建历史查询 {#create-a-history-query}

在**历史查询**页面上，点击 **+**。南向端和北向端分别独立配置，各自都有自己的开关（**从现有 South 创建** /
**从现有 North 创建**）：

- **禁用**（默认）——为此查询选择一种连接器类型并从头开始配置。
- **启用**——选择一个已有的南向或北向连接器。对于南向端，其所有项目都会被复制到历史查询中。

任意组合都是允许的——例如，将一个全新的南向连接器与一个已有的北向连接器搭配使用。

您也可以从历史查询列表中**复制**一个已有的历史查询——这会将完整的南向和北向配置、项目以及转换器
复制到一个新查询中。

## 设置 {#settings}

### 常规 {#general}

| 设置     | 说明                 | 示例值                   |
| -------- | -------------------- | ------------------------ |
| **名称** | 历史查询的唯一标签。 | `Backfill Jan 2024`      |
| **描述** | 可选的查询说明信息。 | `Re-export after outage` |

### 时间范围 {#time-range}

| 设置             | 说明                                                                       | 示例值                     |
| ---------------- | -------------------------------------------------------------------------- | -------------------------- |
| **开始**         | 要检索的历史时段的起始点。                                                 | `2024-01-01T00:00:00.000Z` |
| **结束**         | 要检索的历史时段的结束点。                                                 | `2024-02-01T00:00:00.000Z` |
| **最大读取间隔** | 单次子查询的最大持续时间（秒）。整个时间范围会被拆分为这个大小的多个区块。 | `3600`                     |
| **读取延迟**     | 连续两次子查询之间的暂停时间（毫秒），以避免对源系统造成过大负载。         | `200`                      |

> 有关如何设置**最大读取间隔**和**读取延迟**的指导——包括在处理大量积压数据时两者之间的权衡——请参见
> [历史连接器的高级调优](./advanced/history-query-timing.md) 中的
> [最大读取间隔](./advanced/history-query-timing.md#max-read-interval-bounding-how-much-a-single-query-asks-for)
> 和 [读取延迟](./advanced/history-query-timing.md#read-delay-pacing-consecutive-sub-queries) 部分。
> 历史查询项目没有分组、偏移量或恢复策略，因此该页面的其余部分不适用于此处。

:::caution SQL 连接器
对于基于 SQL 的连接器，您的查询**必须**包含这两个时间变量：

```sql
SELECT * FROM sensor_data
WHERE timestamp > @StartTime
AND timestamp <= @EndTime
```

:::

### 南向和北向配置 {#south-and-north-configuration}

一个历史查询内嵌了一个完整的南向连接器和一个完整的北向连接器。北向端（设置、缓存、转换器）的配置方式
与实时北向连接器完全相同。南向端的连接设置配置方式也相同，但项目被简化了：历史查询项目只有
**名称**、**启用**标志以及类型特定的设置——没有针对单个项目的扫描模式、分组或限流覆盖设置。
每个项目都改为共用上面提到的统一**时间范围**设置。

项目在与南向项目相同的三步弹窗中编辑——**常规**、**设置**（含测试面板）和**检查并保存**，并可通过**保存并继续添加**
连续创建一系列项目——参见[创建和编辑项目](./south-connectors/common-settings.md#creating-and-editing-an-item)。对于支持该功能的
连接器，**浏览**可以只读方式浏览数据源：历史查询没有**添加为项**，也没有项同步。

## 执行控制 {#execution-controls}

| 控件         | 说明                                                                                                                              |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------- |
| **开始**     | 当查询处于 `PENDING`（待处理）状态时可用。从开始时间起启动查询。                                                                  |
| **暂停**     | 当查询处于 `RUNNING`（运行中）状态时可用。暂停执行；每个项目的进度会被保留。                                                      |
| **恢复**     | 当查询处于 `PAUSED`（已暂停）状态时可用。从每个项目最后记录的位置继续执行。                                                       |
| **重新开始** | 当查询处于 `FINISHED`（已完成）或 `ERRORED`（出错）状态时可用。从开始时间重新运行查询——在此状态下启动查询总是会重置已跟踪的进度。 |

这些控件可在历史查询列表及其展示页面中使用。

编辑现有历史查询时，保存操作也会提示您是否重置缓存。选择**是**将清除所有已跟踪的进度，
下次运行将从开始时间重新开始；选择**否**则保留当前进度。

## 监控 {#monitoring}

展示页面显示查询的南向端和北向端的实时指标。南向端报告的内容取决于连接器执行查询的
方式——是作为整体范围，还是逐个项目。

**南向（检索）指标——批量连接器：**

大多数连接器一次性查询其整个项目/分组范围，并将整个范围内的进度作为一个整体来报告：

- 已检索的数据——查询的整体进度条
- 区间进度——当前子区间编号 / 总子区间数，及其时间窗口

**南向（检索）指标——逐项查询的连接器：**

基于 SQL 和 REST 的连接器（参见[兼容的南向连接器](#compatible-south-connectors)）逐个查询
其项目，因此进度是按项目而不是按整个范围来报告的：

- 已处理的项目——当前正在查询的项目名称，及其在所有项目中的位置（`当前 / 总数`），并附带进度条
- 当前项目进度——当前项目自身的子区间进度，及其时间窗口
- 指标下方的**项目状态**表，列出每个项目及其状态（`待处理`、`运行中` 或 `已完成`）、最后检索到
  的值，以及迄今为止检索到的记录数

:::tip 从列表页面跟踪进度
历史查询列表页面也会在正在运行的查询的状态图标旁显示一个 `(当前 / 总数)` 的项目进度指示器，
无需打开其展示页面。
:::

**南向（检索）指标——两者共有：**

- 每秒处理的数值/文件数量以及预计剩余时间（查询运行期间）
- 检索到的数值和文件数量
- 上次连接时间
- 上次检索到的数值（点位 ID、时间戳、数据）
- 上次检索到的文件
- 上次运行开始时间及持续时间

**北向（传输）指标：**

- 缓存大小——当前、累计缓存、累计已发送
- 错误大小——当前、累计出错
- 归档大小——当前、累计归档
- 上次连接时间
- 上次发送的内容
- 上次运行开始时间及持续时间

## 自动恢复 {#automatic-recovery}

每个项目（或已同步的分组）都会独立跟踪自己最后一次检索到的时间戳，因此查询可以在发生故障或重启后恢复，
而无需重新获取已经检索过的数据。进度会在 OIBus 重启后保留。

:::caution 重置进度
重置缓存会清除每个项目已跟踪的进度。下次运行将从原始的**开始**时间重新开始，这可能导致向北向连接器
发送重复数据。
:::
